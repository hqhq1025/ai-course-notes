上一节课我们讲了软件工程的来龙去脉：什么时候碰到了软件危机，为什么大家发现软件开发不下去了，需要工程化的方法解决软件里的问题。我们也读了 Royce 的老论文。我们希望从 intent 走向 spec，再走向 implementation，最终产出软件。有了 implementation 以后，还需要维护它，软件的生命周期并没有结束。所以很自然地，就有了一个一路向下、像瀑布一样的过程。

在需求和设计阶段，我们会得到对软件的一些认识；这些认识逐渐进入 specification 的空间，形成依赖关系。系统实现时，又会有模块、函数、代码、测试等各种软件 artifacts。它们之间存在直接或间接的 data dependency，形成错综复杂的网络。这就是软件工程的一个起点。Royce 批判了简单地按这个顺序开发的模式：如果到后面才发现错误，回溯发现前面的需求或设计有问题，比如某个设计不合理、实现达不到预期，那么后面受它影响的一大片内容都会失效，需要重做，带来大量成本。

软件工程就在这样的背景下诞生。它研究做需求分析、系统设计和系统实现时可以采用哪些方法。从有人文关怀的方法，比如 checklist、产品经理应该怎样管人，到写代码时怎样写测试，能否自动化测试、自动化分析，展开了一整个软件工程的故事。

AI 到来之前有一个很有趣的尝试。人和人很难对齐；如果不写文档，只剩一份代码，出错时甚至不知道该追溯到过去的哪个决定。因此软件工程提出了很多重要概念，比如 traceability，可追踪性。理想情况下，每个测试用例、每个代码片段，都能关联到过去发生的事情或做过的设计。这样才能维护整个系统里发生了什么、改代码会影响谁、改设计会影响哪些测试。如果有一种结构化、有语义的语言来表示这些关系，显然更好，于是有了 UML。它试图对齐整个世界的软件工程实践，这些尝试都有智慧。

回头想，软件工程困难还有一个本质原因：软件并不“软”。什么东西是软的？教室里的椅背是软的，有弹性。你靠上去，它瘪下去；你站起来，它又弹回来，下次坐还是好的。但软件和物理世界的椅背很不一样。它是纯粹的逻辑制品，容不下细微的差错。程序有形式语义。你们写代码时，考虑过内存中发生一个 bit 翻转以后，程序还对不对吗？

比如程序从标准输入读一个 N，输入 N 等于 1，接下来循环从输入中读一个元素到数组里。如果软件运行在卫星上，宇宙射线击中内存，那个 unsigned integer 的最高位变成 1，N 就突然变成巨大无比的数，整个程序就崩溃了。它会不断从输入里读数；没有输入，可能就一直等，表现为程序 hang 住；也可能读了一百、一千个数以后产生 memory error。所以软件一点都不软。

这是运行环境不可预见的一个极端例子。但在 data center 里也能观察到：随着处理器制程越来越先进，某些电路密度特别大的指令，在热噪声下可能产生 silent error。同一条指令在两台机器上执行，结果不一样；有时服务器运行一段时间，才暴露出制造时留下的缺陷。

软件被认为集成了人类智慧，同时又要承载客户的需求。今天我会花时间讲教务系统应该怎样设计，怎样防止它堆积成屎山。这就是软件工程。在这样的背景下，也许听课的有软件工程专业的同学，计算机专业的同学也肯定要上软件工程课。它是一门关乎整个软件生命周期的学科，但你们被迫只能从底下开始学。你不理解代码、写不出代码，没有体会过码农开发软件的痛苦，就很难做好产品经理。某件事能不能办到、需要多少成本，没有一手经验，确实很难判断。

所以你们上来先学 C 语言，学一种最基础、很老的编程语言。说没人用了，也还是有些人用。在此基础上不断产生新知识，知道世界是怎么失败的，新的语言为什么被创造出来，再一点点往上走。而今天要讲的需求、产品和架构，处在从 intent 到 spec 的设计阶段，是决定软件系统从零开始走向的最关键部分。

前面为什么先讲版本管理？因为总要从一个空项目出发，先讲软件怎样从空项目向前走，再把控它的方向。你的船究竟向东南西北哪个方向开？最初的选择对后面的影响很大。但需求、产品、架构这些事情很难做出好的研究，也很难讲。要么只能举案例，要么讲一堆概念，说需求要做 A、B、C，架构要做什么，产品要满足什么。

学校里有很多做软件工程研究的人，我们还号称南京大学软件工程世界第一——在 CSRankings 里数 ICSE 论文的话。但大部分研究集中在编码、implementation 相关的问题上。有些做 NLP 的研究会说，traceability 在软件世界里非常重要，这没有错；然后问能不能训练一个神经网络模型，直接从数据里推导出这些关联。但这样的事情，也许用 GPT-6 就能做到。

今天我还是要讲这些我认为很重要的内容，尤其是在 AI 时代，生产目标明确的代码已经很便宜。现在让 AI 生成代码，只要把边界划清楚，我真的已经不看实现了。一会儿会给大家看 GPT-6 昨天写的代码，那个实现已经超越人类容易理解的范畴，但 somehow 它是对的，我还能比较好地信任它。如果边界划得清楚，又知道怎样做好 validation，就能把 Agent swarm 铺开，帮我实现有一定质量保证的软件。

剩下的压力是什么？什么能决定软件系统最终走多远？我们总说先做 minimum viable product，没有问题。MVP 能快速找到一条从 intent 到 specification 再到 implementation 的切片，走完整个软件开发流程，但它并不完备。做 MVP 时，你一定想着先做最重要的功能，不会先想某个按钮应该是什么样式。这也是 dependency：按钮样式依赖界面设计，界面设计又依赖功能。如果上面的设计不确定，现在就去调按钮样式，设计改变后，样式可能就不合适了。每个人都有不做无用功的本能，不愿研究马上就要扔掉的东西。因此，做 MVP 时应该选最重要的功能。

AI 会给你一个能运行的版本，但至少今天的 AI，并不会主动从需求、产品设计、架构的角度考虑，除非你显式地用 prompt 告诉它。哪怕只有几个字，也会产生很大影响。从零开始，给它同样的 MVP 需求，再告诉它用 client-server 架构，或者用 CLI，就会得到完全不同的 MVP。功能上看起来差不多，都实现了一个 coding agent，或者 Lab1 的学生助手，但这几个字的 prompt 会膨胀成许多东西。

如果要求 CLI，项目里可能就有一个 `cli.py`，或者依赖 JavaScript 里的命令行库，像 Claude Code 使用的那种；如果要求 client-server，它可能先设计数据存储，给你选一个数据库。只要 `db.ts` 这样的文件写下来，就会进入 Agent 的上下文。每次继续做下一个需求，都会带上以前的所有历史。软件工程有个术语叫技术债，technical debt。你做决定时就背上了债务，因为做 MVP 时，还不知道未来会怎样。

这些决定首先来自需求。比如我到底要什么样的个人代理？实验里当然写了需求，但你要有自己版本的需求。你可能只是想帮助自己学习，也可能已经进入课题组，对阅读研究论文有很强的需求。需求不同，软件走向肯定不同。其次是产品设计，要想象最终的产品。假如产品只有自己用，我就有很多这样的工具，自己用得很顺手，给别人用却不舒服，因为其中有我自己的知识和偏好。喜欢命令行的人觉得方便，普通人可能完全不能接受。

除此之外，还有一个隐藏的东西是架构：这个软件会变成什么样。这三个方面是撬动软件生产力的真正杠杆。可能只有很短的几个字，却会对 AI 生成的 slop 的走向、技术债的累积产生巨大影响。所以我会花两节课讲需求和架构。

我让 AI 诊断一下刚才的翻车。系统 UI 还在工作，OBS 还在推流，但所有输入设备都不能用了，鼠标、键盘没用，插上一个新鼠标也没用。这也是软件工程实践：出了问题要看日志，意味着写软件时需要输出足够多的日志。如果不告诉 AI，它也不会主动做，可能生成一个没有任何日志的系统，留下这样的技术债。我不确定能否找到问题。

回到今天的需求工程。以前它很难讲，因为学生不会见真正的客户，也做不了相应规模的软件系统。从刚开始学编程语言，到毕业时，能力的增长可能还不足以面对真正的软件客户。现在有点变了。AI 之前，只有少量精英独立开发者，经过几年开源社区的洗礼，终于觉得可以独立开发，也会有一些付费用户。现在独立开发者数量爆炸了，付费用户却瑟瑟发抖。

今天要讲的软件系统例子，是我比较喜欢的教务系统。我把它称作“史诗级的需求爆炸”。我昨天趁机看了一下。登录已经失效了，让我扫码登录。我发现教务系统这几年一直在进步，这是我的界面，放大一点。最近有个史诗级的更新：我可以直接搜索“仙林教学楼的灯一直没有解决，我应该打电话给谁？”它显示“正在理解您的问题”。它给出的好像是基建处，但我在平台上提过，基建处把我打回来了，说不归他们管。回头再打电话。

再问：“我现在在上什么课？”我不确定它有没有载入我的上下文，猜测可以，因为我登录了。它给出了本科教师课表，这是我的课表。这确实是个很大的更新。大家可能也不知道什么时候加了这个功能，曾经肯定没有。我平时只在快捷搜索栏里等下一个界面弹出来，直接点进去，不会这样搜索。

这是非常典型的需求爆炸的系统，肯定花了很多钱。某种程度上，我觉得这些钱还不如变成 token 补贴发给大家。它要买算力、买开发，而我刚才如果用 pi Agent 查一下，可能就花一两毛钱。把 token 送给大家，不实现这些功能，也许更便宜。

这是一个典型的业务系统。除了课表，还能找到我的教学任务，我把它收藏了。这里可以看到大家的信息，就不点了，点开以后似乎会显示电话号码。在学生名单里能看到电话号码，我觉得这是个比较糟糕的 feature。上次给大家演示过，直接用 AI slop 填满教学周历，到现在还没人审计我填的任何内容。我觉得他们更应该先把教室的灯修好。

这个界面里有无穷多的功能，比如编辑联系方式、当前教学学期、最新排课学期、历史授课信息。历史授课信息里要选择学年、学期，感觉不太好用，又还算好用，确实做过需求分析。比如“期末考试签到表”，也是一个需求点：期末考试期间允许点击，没到发布时间，就弹窗告诉你无法打印。

再看“编辑教材”，应该进入另一个页面，有个弹出窗口。我再试一次，以前好像可以，现在成功发现了一个 bug。再看大纲、教学安排，提示仅展示最新一个教学班。哦，等了很久才把页面刷新出来，可能不满足非功能性需求的要求。看看还有什么能点，我不用 Agent，还是用古法手动点。

和本科生相关的功能还有助教管理。我这门课好像没有助教。能搜我的名字吗？不对，这里要填学号。课表内教学班没有助教。让我看看这里是什么：教学班名称里看到一些“JX”，这名字堪比 Agent 生成的。需求不断叠加：曾经没有慕课功能，疫情时领导说需要为老师添加慕课；添加以后，又需要慕课助教，不能把它当普通教学班的助教，要单独算慕课助教。于是就有了这些东西，也出现了我不知道原因的、史诗级的 bug。

点删除可以吗？点新增呢？提示“请在可维护时段内操作”。课内教学班也一样，现在已经不能申请助教了。这就是你们看到的教务系统。所以你能理解我说以前很难讲需求工程：你们不会见真正的客户，也不敢拍胸脯说，给我二十万，我找几个同学把南大的教务系统包下来。你承担不了这个责任。签合同以后，如果逾期交付，达不到功能或非功能要求，怎么办？你就傻眼了。当然，作为成年人，你们可以成立公司、跟学校签协议，但你们不敢。

你们不敢不要紧，Agent 敢就行。我让 GPT 去探索教务系统中和教师相关的功能，注意，只是教师相关的功能，得到一份需求说明书。就像刚才说的，也可以用 pi Agent 去查资料，帮我生成一份给校务信箱的投稿。

我们看看这份《南京大学本科教学服务平台需求说明书》，这是一个真实的需求报告案例。软件工程课也可能给你看来自真实企业的需求说明书片段，而这个就是我们身边的实际案例。AI 很好用：要教需求工程，当然可以找经典案例，也可以直接把身边的案例变成需求说明书。

目录有很多项，从调研方法、证据边界，到业务目标、成功标准，再到详细用例规约、功能需求目录，最后还有术语文档与配套文件。GPT 是懂软件工程的。为什么要写这么多？对一个已经做好的系统，看起来好像突然写了好多 slop。但它懂得，做真正的工程、面对客户时，术语很重要。客户看不懂，可以查术语，就能对齐。这还不是 UML，仍然处在早期意图沟通阶段，但这些东西显然有用。

看看功能需求目录，它是有 traceability 的，遵循了比较好的软件工程规范。每个需求点和前面的角色、参与者、业务目标，都用有意义的编号关联起来，建立可追踪性。你当然可以用自然语言说“教学班和学生管理有关”，但用编号、用有明确含义的 ID，就在一定程度上帮助建立了 traceability。

例如门户与身份：提供分类服务、检索和应用入口；当服务支持多种已分配身份时，提供身份选择，并显示当前身份。真正做软件时，复杂的地方就来了。你可以不写这些，但系统里到底要不要有？它应该是观察到了身份选择。刚才打开某个课表界面时，确实让我选，我选了下面的本科生教师身份。

又比如，服务页面明确当前学期、学年、届次或业务批次，允许在授权范围内切换。这也是设计。在意图阶段，领导或者一线教师会想：打开这个页面，什么样的界面用起来舒服？刚才的教务系统是有一定设计感的，它会考虑你做这件事时还想做什么，在那里留一个下拉框，让你选学期或其他条件。

还有教学周历、课程与大纲、教材选用。你就知道，这是一件非常 tedious 的事情，繁琐到你根本不想干。做这些看起来对拿学分、拿学分绩、获得长进都没有本质好处，还不如做一道没想过的算法题，提高解题能力，保研机试时比别人多拿一点分。在这里一条条写需求，像是 nonsense，你自己不会想写。

但量变会引起质变。课程作业也会给需求文档，比如数字逻辑电路、计算机系统基础。在计算机系统基础课上写 full-system emulator，挺好玩的。这是你们遇到的第一份比较长的需求文档。设计这门课时，在它之前大家接触的 OJ 需求都很短：明确输入、输出接口，而且很简单，通常输入一个整数或空格分隔的整数，用 `cin` 就行。

在计算机系统基础课上，你第一次看到较长的 specification guide。首先，需求是实现 NEMU。第一个 lab 可能实现调试器，还不需要解释指令；第二个实验需要实现指令解释。这也是一句话，但到底什么是指令？指令行为写在文档里，于是又得到一个更大的需求文档。系统大到一定程度，各种训练是相通的。学计算机系统基础时，你其实也在一定程度上学软件工程。

需求工程还有验收场景、结构化的需求清单。为了挣钱，你需要这些东西。最终可以把 checklist 拆开，前二十个需求分给一个团队，后二十个分给另一个团队，跟踪每个人的进度，知道哪个团队落后。有了 traceability，管理者就能把团队管起来。这些在本科课堂上通常学得不多。

AI 的魅力时刻来了。我又让 GPT 起一个 sub-agent，不看其他教务系统，只根据这份需求说明书，实现一个假的教务系统。突然你又有信心了，觉得自己好像也可以拿二十万跟学校谈合同。它和刚才看到的系统还挺像：返回全部教学任务、我的教学任务、本科教材管理、编辑记录。改一下演示数据，保存，确实保存成功了。

再看学生名单，能看出 GPT 起名字的偏好，名字挺文雅，也有它自己的偏执。这里记录缺课次数，试着输入一个数、保存。它没有阻止我，但这个数字已经超过整个学期上课次数的总和，其实不合理。不过你能看到软件工程的魅力：需求清楚、需求文档写到这个程度，编码、traceability、测试，AI 都能帮你搞定。你只需要一份需求。我们一会儿还会回到这里。

从入学到毕业，教务系统包含权限、规则、版本、数据同步、操作留痕等各种功能。需求无非是通过不断与客户沟通，把客户想要什么想清楚。小到界面上要不要放当前学期、学年，哪里要不要有修改按钮，都需要和用户对齐，因为用户不是你自己。

做设计，尤其是做需求时，要有同理心。这是 computer science 同学可能普遍缺少的软技能。不能因为自己是 geek，就假设所有人都会写程序。你要考虑教务员：她可能本科学历，今年 53 岁，还有两年退休，是位优雅的女士；她上大学时可能没操作过电脑。教务系统既要为她设计，也要为我和年轻人设计。怎样得到那张需求表，是另一个问题，不是这门课的重点。

这门课的重点是：当教务系统按刚才那样长的需求列表做下去，其实已经进入泥潭了。如果真的要做教务系统，你被迫从零开始。这也是行业的壁垒和经验所在：在行业摸爬滚打二十年的公司，有资质、有领域知识，知道教务员想要什么。你是一个本科生，不知道她究竟想要什么，做的需求就可能有偏差。公司有经验，对学位授予流程比你清楚，知道怎样把它变成需求文档。

但某种程度上，做软件仍是被迫的。空项目刚开始时，没有东西发生漂移；一旦写出需求列表，无论 AI 还是人实现了一版，像刚才那个教务系统，你就背上技术债了。我们的定律是：需求永远不可能完全说清楚，而且需求不是一成不变的。

这里有个 AI 虚构的案例，我能体会，它真的可能在学校发生。比如我们把离散数学课拆开，因为觉得第一门离散数学课没有教会大家数学语言。但拆开会带来后果：准出条件、保研要求改变了，新旧衔接不上。原来系统要求计算机系或计算机学院学生毕业，必须修离散数学，很合理。现在一学期的一门课变成上下学期两门，怎么办？是不是要增加规则，允许修过原来的离散数学，或者新的离散数学（一）？这里出现了“或”的关系。

第一版沟通需求时肯定没想过。原来的 checklist 可能是：有一个“毕业要求”界面，给教务员一个下拉框、一个“增加一条”的按钮，可以选一门课程。在最初那个时间点，这当然合理。但需求一旦固定下来，后来离散数学拆成两份，旧设计就不能适应新需求了。对不起，重构吧。把需求文档调出来，这里不能这样了，要加一个“或”。每叠加一个东西，屎山就开始累积。

写过软件的人都懂，让我做东西不要紧，改需求真的受不了。原来整体一致的设计，一旦出现裂缝，就会传递到系统各部分。一个看似很小的需求，牵动整个系统，最后一团乱麻。

还有更多例子：重修、交换、课程抵扣。有学生从别的院系转来，那个院系也有离散数学。软院好像仍是一门课，能不能抵扣计算机学院的离散数学？抵扣（一）和（二），还是只抵扣（一），还要再上（二）？一旦面对开放的物理世界，就有无穷多种情况。

最终，系统没有表达的事情仍然可能通过特殊处理解决，总要有 override。比如某位学生读了六年，就差离散数学，拿不到本科学位，恰好碰到课程拆分；眼看要毕业，需要补的课这个学期又不开，怎么办？最后教学主任认为两门课可以存在替代关系。系统里怎么处理？可能就是打电话给工程师，把数据库里这个学生的毕业条件改成满足。这件事仍然有档案可查，层层审批都在，最终由教学院长认定，学过的旧课程可以抵扣新课程。在人类世界里，它是合理的。

这就是软件系统的复杂性。一旦做需求分析、实现需求，就背上技术债。我记得 2018 年开始上课的第一天，用的还是老版教务系统，和我上学时差不多。我以前只用学生端，第一次用教师端，发现可以设置学生缺课次数。我不知道为什么要做这个需求；如果我来做，就不会把它放进教务系统。老师有签到表、点名表，留下证据再扫描，不一定要专门记录在系统里。学生手册里也写了，无故缺课达到一定次数可能受到处分乃至开除。

我当时试着绕过前端校验。刚才 GPT 实现的版本，校验质量还不错，输入非常大的缺课次数时会直接拒绝，我相信它前后端都会做校验。但在当年的系统里，我把一位同学的缺课次数从 0 改成 -1，所有能查询到这位同学选课记录的页面立刻全部 crash，直接返回 500。我只好打电话给教务，说教务系统崩溃了。不知道最后怎么解决，可能第二天工程师登录数据库，把那条记录修好了。之后我再也不碰它。这就是真实软件系统里的需求。

需求部分只能给大家这样一个 lesson。完整的需求和产品设计，也许该由另一门产品课来讲，这门软件工程课不适合展开。AI 时代做 MVP 没问题，而且前所未有地容易：先实现最重要的功能，看到产品，就知道哪里设计错了，这时推倒重来的成本较低。但这也给你一种已经驾驭 AI 的错觉。迭代三个版本，AI 确实都能继续修；可真实系统运行足够长时间，比如计算机系变成计算机学院，原来的设计不再起作用，麻烦就来了。

这是所有软件工程都面临的问题：there is no silver bullet，没有银弹。所谓银弹，来自吸血鬼、狼人之类不能用普通方式杀死、需要银弹的故事。但软件工程没有银弹。随着软件增长，最初的决定会持续产生影响。软件要生存、要挣钱，不像课程项目随时可以清零重做。一旦上线，就开始与物理世界交互，必须背着 technical debt 维护下去。如果前面的决定不够有前瞻性，成本会不断恶化。

怎样应对？架构。刚才已经透露了一点：项目刚开始、还处在 MVP 阶段，没把所有事情装进去时，想想第一步应该迈向哪里，最有利于软件长期生存。第一步要做的不仅是 MVP，还有软件架构。刚才 AI 生成的那个东西，已经不只是 MVP，算一个小型产品原型了，维护会变得很困难。

要驾驭复杂性，一开始就该想：怎样做一个最小的软件，使它随着需求膨胀和变化，仍有一定韧性？哪怕最小的代码，也有架构。说白了，就是把耦合解开。比如一开始就决定用一个数据库存所有需求，可以很快得到能运行的原型，AI 也做得出来。但如果不仔细想系统中哪些概念可以分开，就很容易进入维护的泥潭。

说到架构，大家觉得玄学、高大上，其实不是。第一次设计代码和系统，无论多小，都可以有架构思维。它本质上是在控制复杂性。代码稍微有点规模，就能考虑怎样分解复杂性。写 OJ 时，你们会不会把 `main` 分成读取输入、处理输入、输出结果？

再比如命令行程序。`main` 有 `argc` 和 `argv`，这是操作系统与进程之间的约定，以字符串参数向量的形式传入参数。你怎么处理？一个个做 string compare 吗？想象保研机试要求处理 `argv`，你会怎么写？你可能会想起世界上有个东西叫 `getopt`。上课见过，实验写过，研究实际项目，比如 coreutils、`ls` 的实现时，也会遇到它。这也是架构，是分解复杂性的方法。

`argv` 本身就很复杂，比如 `npm` 有很多子命令，刚才用的是 `npm run dev`，还有长选项、短选项。在 C 的时代，自己写 parser 很复杂。用 `getopt` 就能把复杂性隔开。参数有一些标准约定，比如 POSIX 标准；用相应工具处理，最后只要写 `while` 循环和 `switch`，就能解析参数。你就学到了一种 parser 的架构模式。

这是很小的例子。任何符合 best practice 的好代码，背后都有架构设计，都映射到需求。刚才用教务系统讲需求，可能显得太大了；但做任何软件工程活动，都有 intent、specification 和 implementation，不一定要面对教务系统那样的 monolithic 系统。在一个模块里，也可以谈需求、谈架构、谈优雅。

所以我很讨厌那种“语言律师”式的授课方式。以前和学院老教师有过比较大的分歧。那还是 pre-LLM 时代：如果讲 C++，至少应该讲 C++11、14、17 的一些特性，以及它们应该怎样用。对方说：“我讲了，怎么没讲？”怎么讲的？写个 lambda，参数 a、b，返回 `a + b`，就没了。讲了和没讲有什么区别？

你们学习时看到的每个东西，不管是 GitHub 上好项目的 README，还是一个 `getopt`，都可以再往后想一想。这样的 parsing 模式，把复杂的字符串变成简单的解析状态，就是抵抗需求变化的方法。`argv` 可以有各种变化，而 parsing state 把问题隔开了。

我们从最小的十行代码讲几个典型架构。为什么说大模型还不太掌握架构，或者架构是一种品味？因为架构和需求连在一起，没有需求就不用谈架构。需求面对开放世界，架构也要为未来的需求做准备。能设计出什么样的架构，取决于对需求掌握到什么程度。

举我最喜欢的例子：非递归的 Tower of Hanoi，汉诺塔。以前开始上课时，我问过保研的研究生，能不能写出来，研究生摇头，于是它就成了课堂例子。十行代码背后的架构，正好联系到大家为什么写不出来：非递归汉诺塔为什么这么难？

看看人和模型怎样处理它。我给模型这个 problem，让它写非递归汉诺塔。猜猜 GPT-6 写了什么？它简直说：“我不做人类了。你写不出来，是因为数学不如我好。”它找到了汉诺塔的数学性质。GPT-6 显然沿数学这条路狂奔，希望数学能力能解决人类世界的问题。

它说，盘号等于 1 加上步号二进制末尾零的个数，每个盘子的移动方向固定。方向真的固定吗？We don't know，反正它应该是对的。你看不明白，但 highly optimized，极度优化。除非我明确叫它模拟栈，否则它就这样写。

同样的 prompt，DeepSeek-V4-Flash 更有人感，写出非常优雅的标准答案。要写非递归汉诺塔，这是一个干净的架构：递归时把还要继续执行的任务留在栈里，总是执行栈顶任务，不断往前。我还特意试了豆包，它选了差不多的方案，但代码有瑕疵，就不展示了。

我作为架构师，想法又不同。架构关乎对需求的掌握。写非递归汉诺塔时，我首先想大家为什么写不出来，是因为对递归理解得不够深。上过我课的同学见过这份代码：我故意强调，程序实际上是状态机。可以回头看操作系统课，我花了一整节课讲 C 语言的状态，以及状态的 single step，也就是 operational semantics，操作语义。一次 `hanoi(n - 1)` 调用，是程序语言世界里定义清楚的一步操作。

我们只需模拟它，可以写一个 C 语言解释器。理解解释器以后，就很容易把代码转换过去。我当时讲的甚至是两个函数相互调用，F 调 G、G 调 F，也没有难度，因为只是把 C 语言的小步语义翻译成状态机。如果觉得对汉诺塔而言这份代码 overkill，毕竟它能翻译任意程序，还可以做 simplification，优化成另一份等价代码。

在我看来，这是理解 C 语言形式语义的好机会。不同的人会这样看待问题，所以现在我还能守住自己的品味。GPT 其实懂，只是不一定往这个方向想。我有比较强的信心，强化学习能够引导它，一旦学会，也能在适当的时候做出这样的实现。

最后有个搞笑的例子。我在百度搜“非递归汉诺塔”，第一个条目还是递归汉诺塔；再往下找，第一个 CSDN 的非递归实现，看到的代码甚至比 AI slop 还严重。这里定义了 `move`，但 `std` 里已经有 `move`。右边的评论也不知道是不是 AI，营造出博客质量很高的感觉。如果上学时被这种 slop 污染，还不如跟 AI 学，跟 DeepSeek 学都很好，GPT-6 则已经不做人了。

同一个汉诺塔，可以有四种表达。架构控制复杂性，也关乎抽象。站在不同层面考虑，叫跳出问题看问题。GPT 也跳出了问题：一切都是数学规律，只要理解程序背后的数学，似乎什么都能解决，我服。DeepSeek 学到了人类反复强调的“递归是栈”，做了正确的事。我则再往外走一步：对编程语言世界的理解，投射成递归与非递归的区别，再投射成代码。至于那份糟糕的实现，大概属于训练还没收敛。

任何一个小地方，都能看出架构水平。这是十行代码的架构，再大一点，看看两千行。我们还是要跳出问题看问题：代码之外有客户的规律，客户之外有社会的规律，社会之外有宇宙的规律。架构能力从哪里来？从你学过的每个东西来。如果它是好的、优雅的，促使你思考问题，你把它压缩成理解。压缩就是智能，再从 first principles 推导该怎样做。学校学习和社会积累，共同赋予你这种能力。

你必须和教科书、做题之外的人打交道，才能知道那位即将退休、优雅的教务老师怎样看教务系统。你的想法可能是最好的数据库、最高的性能，而她只是希望字大一点，点鼠标时别误点旁边的按钮。这需要共情能力。

两千行的例子，是以前上课讲过的 QR code generator，用 Excel 生成二维码。第一课展示过，把一个长字符串编码成可以直接扫描的二维码。用今天的概念看，这是一个和教务系统不同、需求很明确的例子：Excel 里有输入单元格，有输出 0、1 序列的单元格，非常确定。但它仍然有架构上的考虑。

Agent 对自己能力有一定估计，任务足够困难时，就不会直接一把做完。比如两个 sheet，第二个是学生实验成绩，第一个是录好的期末成绩，让它写公式，根据学号把实验成绩拉过来，这是能力范围内的，可以直接做。而生成二维码超过这种难度，它会试图分解问题，也会做架构，只是至少今天的模型在架构上还稍微落后。

如果直接写成一个公式，公式会特别长。有个笑话说偷到一份 Lisp 程序，看到最后一页全是括号，就是这种感觉。Excel 的计算方式有限，像让你用 Brainfuck 之类的语言实现一个 nontrivial 程序，甚至《毁灭战士》游戏，写出来就会这样。这时需要抽象。

我看到的前两个 AI 版本没有考虑到：看似明确的需求，其实有很多坑。比如 Excel 有版本，不断增加新功能。刚才根据学号找成绩，以前用的函数叫 `VLOOKUP`。有同学知道吗？不知道，说明你们不是 Excel power user，太好了，你们是 Agent 时代的人，想干什么只需告诉 Agent，不必再学难用的语言。

微软后来也受不了了，在某一年推出 `XLOOKUP`，让查找方便些。我记不准是 2019 年还是 2024 年。Excel 在演化，需求马上就模糊了：到底兼容旧版，保证各种人的电脑都能打开，发给教务老师也能打开这个二维码；还是做一个只有自己用、用完就扔的工具，可以采用最新语法，实现最简单的公式？究竟是哪一种？

需求一变，维护就极度痛苦。假如 AI 按较新版 Excel 的公式给你 vibe code 了一份实现，突然要求改成 2019 版，甚至 2003 版，原来的设计和实现可能全要重做。两千行的项目可以重做；但如果这两千行已经嵌进巨大需求、嵌进教务系统，与其他部分关联，项目经理就得说：加钱、加人，我只能这样满足需求。这是现实，也是架构没有设计好的表现。

还有别的变化：结果生成后，我不满意它的位置，要整体右移一格。如果所有单元格都硬编码，就会立即崩溃，对需求变更的抵抗力非常糟糕。跳出问题看，其实这是一个编译问题。

我开个 Agent，让它给一份从字符串到二维码的伪代码。问题本身很清楚，二维码有完整规范，它却还要读文件。生成的伪代码很短：版本、纠错等级、掩码、大小、数据编码；这里有 `0100`、字节、纠错码，还有多项式运算、码字，最后加上 ECC，把它们放到二维码空间里。

为什么这么容易用算法描述的东西，在 Excel 里实现却很难？gap 在哪里？跳出问题就能看到：二维码算法很容易写，用一个 Python 文件实现，再容易不过。明年保研机试甚至可以出这样的题，让大家实现算法，最后打印一个 0、1 矩阵。如果一定要求脱网，这是不错的测试题。

但我们的要求是 Excel，没有现成的翻译器、编译器能把这里的 Python 程序直接编译成 Excel。Excel 本来是为财务、报表设计的，管理学生成绩，相当于一个小数据库，并不是围绕通用的图灵完备计算设计的。这里没有一个可直接使用的 Python-to-Excel 编译器。如果把伪代码或自然语言直接交给 LLM 编译，我们也看到了问题：它直接上手做，需求漂移时就会遇到很大麻烦。

所以可以想到：能否在 Python 和 Excel 中间构造另一种语言，既容易翻译成 Excel，又保留一定的 Python 功能，能够描述刚才伪代码中的计算？我需要的其实是一个中间编程语言，支持这些运算。我做了这样的设计：这门语言可以翻译成 Python。

你们都写过表达式求值程序吧？我就构造表达式树，比如 A、B 的异或、加法，或者取出字符串中的某个元素。这就是一门小语言，很容易翻译成 Python。递归翻译左右子树，再根据当前节点把它们拼起来，dump 出表达式就行。它也可以翻译成 Excel，只需为每个节点定义翻译规则。把两个输入放进任意单元格，再用单元格公式算出结果。

这样就好办了。我让大语言模型用这门语言生成二维码计算逻辑，再翻译成 Python 验证，看看公式是否正确。公式写对以后，再生成 Excel。这个架构不就和最小例子里的 `getopt` 一样吗？命令行工具先通过 `getopt` 得到 parsing state，再从这个状态做下一步，都是同样的设计。

你们作为 unsupervised learner，作为神经网络，多看好的东西，自然能泛化。但看的时候要有意识地想为什么这样做。也许读某个 blog，或者有一天听课，突然就想通了：原来大家做的事情差不多。

一份中间语言，两种执行方式。我的架构就是让 LLM 生成中间语言，构造一次，再分别用于验证和交付。在这个架构上，还可以发展优化。既然有语言，如果性能不好，或者某处生成的代码太长，就可以通过改写规则，把程序从一种形态改成另一种。

比如循环中反复计算的变量，每次值都一样，就能把计算移到循环外。编译器可以自动做，你自己也可以手工做。有了中间语言，还可以让大语言模型优化它。计算机系统里学过的 profile-guided optimization 也能用：先定位性能瓶颈，再用 profile 指导代码该怎样改。学过的概念又用上了。

好的架构可以承载需求变化。未来 Excel 版本变了，无非是把部分算子换一种实现方式。说到算子，会发现今天 AI inference 也在做类似的事情。人类就是这样，各领域有很多领域知识，也有很多好设计，值得学习。

十行、两千行讲完了，五十万行的架构应该怎样设计？我觉得还是同一件事：跳出问题看问题。提到架构师，你可能想到画框图、数据库、微服务、流式数据处理、应用框架，选几个框架搭起来就解决教务系统问题。先看看 AI 实现了什么架构。

这是它生成过程中的结果，我当时就发了小红书，说 GPT-6 “不做人了”。像刚才的汉诺塔，数学上想清楚、数学上正确，它就觉得毫无破绽。写代码时，一个 `function applications()` 后面就挤了一大串。后来它还很贴心，用格式化工具帮我格式化了。

现在看教务系统 demo，仍然是一个 monolithic 系统，一个 83 KB 的 TSX 文件，一个 38 KB 的 service 文件。格式化以后看起来正常一些。虽然如此，我真的觉得它很厉害，竟然能把这些东西做对。

问问“D 老师”，让它评价 GPT 生成的教务系统用了怎样的架构。当时我惊了，另开了一个独立 session，问还在运行的 GPT：“这软件能维护吗？”它说能，只不过把业务逻辑挤在几个大文件里，维护完全没问题。

评价说，这是经典三层单体、前后端分离，而且有几个生产级的横切设计：乐观锁、幂等性、事务、审计、统一错误码。我肯定会在某次课讲这些。它确实做了你们现在做不来、可能要摸爬滚打几年才能理解的设计，有软件工程直觉。还有数据驱动、横向扩展，扩展性很好，当然也有不好的一面。挺有趣，AI 生产软件的方式很快可能超过人类。

但如果跳出问题看，我觉得这还不是特别好的架构，因为本质上它是 CRUD，也就是增删改查架构。它来自什么基本原理？软件是物理世界的过程在信息世界里的投影，而物理世界有状态，everything is a state machine，我自己也是状态机。所以软件很容易被建模为 state transition system：有状态，有状态迁移。

持久化状态一般用数据库表示。一张表表示学生，有学号、姓名、院系；另有学院表、选课表，各种东西都用二维表表示。这是数据库课学过的。数据库设计要求消除冗余，把它分解成 normal form，范式。

什么意思？学生有唯一学号，比如 1234，也有姓名。另一张表要引用学生时，尽量不用姓名，因为会重名，即使不重名也有麻烦。更好的方式是去掉重复的姓名，放一个学生 ID，相当于链接，指向学生信息；学生信息又能链接其他表。这样最小化信息冗余，也是去掉冗余的 dependency：改一个地方，不必同时改别处。

比如学生真的改名字了，这种事情是可能的。用分解的方式，只改学生表里的姓名，再记一个曾用名；如果两处都存姓名，就必须知道两处都要改，代价很大。

我们通常把这样的世界建模为状态，代表此刻南京大学有哪些学生，哪些学生选了哪些课，有哪些老师。信息系统采用经典的前后端分离架构。假如今天我没买到 token，选择退学，就通过数据库更新，从一个状态迁移到下一个状态。原来 A 还在，下一个状态 A 的记录没了。这样始终有个 consistent 的视图；打开教务系统网页，看到的是这个状态的投影。这是非常经典的架构，本身没有错误。

但想想教务系统为什么可能不适合这样的 CRUD 架构。看当前状态，一片祥和；可它把历史丢掉了。比如某处存了两次学生姓名，这很正常：一处并不是关联字段，而是拼接出的字符串，“授予某某……”连同当时的学号等写进数据库。这样数据库内部就可能不一致。

GPT 还给了个例子：学生表有 student ID，也有一列“是否允许毕业”。你们现在学分大概还不够，不允许毕业；有的学生修够了，就允许。这个结果是由许多其他状态算出来的。每修一个学分，或毕业设计状态改变，都可能触发重新计算是否满足毕业条件。

这对信息系统很重要，因为教务员、辅导员需要导出到现在还不能毕业的学生，逐个谈话。这是典型的需求。但这样的结果存在历史计算中的 dependency，当前状态里却没有保存。你知道某个学生能毕业，却不知道为什么能毕业；知道另一个不能毕业，也不知道为什么，计算过程丢了。

软件是现实世界物理过程的有损投影。计算过程丢掉以后，物理世界中建模不了的事情，就只能通过其他途径解决。比如政策更新、领导批准了，新培养方案、新数据却还没导入系统。大家经常碰到这种不一致：物理事件已经发生，培养计划通过了，学期开始、已经上课，系统却没有相应模型。

教室也是例子。第一周仙林教学楼那一片还在修，教室不能用，这件事没有被系统建模，最终靠人工修改、重新安排，我第一周就去了另一个教室上课。随着时间积累，系统里出现大量不一致数据，最后变成无法解释的黑洞：明明某个学生不应该毕业，为什么毕业了？明明还没交学费，为什么也能毕业？系统里会出现无数意想不到的不一致。

面对这种需求，CRUD 就会出问题。再比如“南大没系了”。网页提示当前环境异常，我知道它害怕 Linux。我们是最后一批“系”，现在已经成了计算机学院。

南大院系调整时，教务系统就瑟瑟发抖了。CRUD 把当前数据库当作一个 point of truth，所有事实都在这里。现在 department 变了，原来的对象——虽然用表表示，本质仍是对象——要把 name 从“计算机系”改成“计算机学院”吗？改也不对，不改也不对。

如果改了，现在确实是计算机学院，但查询我的毕业记录，可能变成“2011 年毕业于南京大学计算机学院”，与事实不符。系统打印证明时就会出错。不改也麻烦，现在学生的 department ID 仍指向计算机系，需要创建新对象、迁移数据库，还要想清楚新旧对象的关联。

如果假设世界的投影不会变，CRUD 当然是完美的架构。但需求一旦发生破坏性变化，每次都要考虑数据库迁移、业务逻辑重写。代码可以重写，历史却已经消失。数据库 transaction 更新后，状态彻底变成新的状态。迁移时必须考虑历史上所有可能情况，何况库里已经存在许多不一致，很难写出一个迁移规则，还要冒迁移以后系统坏掉的风险，就像我把缺课次数改成 -1 那次。测试环境里迁移，和迁移学校全部真实数据，难度完全不同。

所以你们能理解，为什么 ERP、教务系统这类软件的设计、实现、维护都是手艺活。我调侃教务系统做得不好，它确实有不好的一面；但反过来想，一个公司可能在 2000 年成立，当时唯一的选择就是参考已有企业架构，做一个教务系统，抢教育市场的第一桶金。做出来是 CRUD，背上技术债后，就得在此后几十年的中国大学教育改革里，不断扛下所有变化。

这里还有个故事。我读 PhD 时在软件所，隔壁软件工程组接了学校研究生院教务系统的订单，可能二三十万。大家觉得挺大，在定制软件里其实很小，因为需要不停维护这个屎山。后来维护不下去了。我刚读 PhD 时，室友做这件事，我经常和他抬杠，聊研究生院系统怎么设计。那是典型的 CRUD 架构，我说以后会面临各种问题。

果然，那几年研究生大规模扩招，多了很多研究生类型、培养类型，管理方式不断调整；研究生压力也大，经常有各种调整，都是需求设计时始料未及的。系统最后彻底变成屎山，后来不再用了，现在统一成公司维护的系统。他们有领域知识，知道怎样把这些系统撑起来。

如果让我重做教务系统架构，我会觉得这个 single point of truth 太危险：一旦发生不一致，不知道该怎样把原因找出来。于是想到数据结构课上一种神奇的东西，persistent data structure，可持久化数据结构，可以保留所有历史版本。

存一棵树，操作后进入下个状态，就像经典 CRUD，数据库也是数据结构。但还有另一种做法：原节点保留，变化时创建新节点，共享没有变化的部分。某个节点要修改，就沿着它到根的路径创建新版本，未变的子树仍可指向旧节点。即使树很大，也不必每次完整复制，历史可以保存下来。

可以保存状态，也可以保存操作，还可以保存操作带来的状态 delta，这三种视图是等价的。保存日志，像数据库、操作系统课学过的 write-ahead log 或 journal；保存 delta，则能联系到 Git、SVN 这些版本管理思想。只保存当前状态，就是 CRUD；如果保留相应历史，就能通过回放得到当前状态。

想设计更好的架构，最好先把干过的事情都记录下来：今天张三退学，今天张三又复学。假设以前没有“复学”操作，退学就是把张三从数据库抹掉，某些记录也删了；后来加复学，要重新建立他和其他部分的关联，代价就很大。现在他又买到 token，想回来了，怎么办？

如果记录所有操作，就能通过 replay 得到张三退学前、复学时需要恢复的状态，把状态拿回来，历史没有丢。业务逻辑不会凭空减少：以前没考虑复学，仍然要写复学逻辑。但事实不可篡改，系统里的东西都是事实的投影，你就更有底气，不像迁移数据库时手发抖。做错了，可以回到过去的快照，修复逻辑再来。

计算机系改计算机学院的问题也相对容易解决。某个时刻发生“院系调整”事件。查询过去的人，就查过去的版本；要看毕业时的情况，查毕业时即可。要看更新的信息，可以投影出与这个人有关的历史：比如 2007 年入学、2011 年毕业，当时都是计算机系，2024 年改成计算机学院。你可以截取与所需事实有关的历史，replay 出现在要的状态。既能查询过去，也能查询现在，这就是好的架构设计。

祝贺你，你发明了一个经典设计模式：event sourcing，事件溯源。想法很简单，从历史事件生成状态，而不直接维护 CRUD 的当前状态。可以回去在 Agent 带领下了解它。你马上可能想到，replay 很多事件，会不会有性能问题？这些通常可以通过快照、缓存等技巧优化。

已经站在屎山上，再改成 event sourcing 会很困难；如果一开始就这样设计，很多问题可以更好地解决。由此也有很多 fancy 的软件工程概念，比如 CQRS，Command Query Responsibility Segregation，但它和 event sourcing 是独立的；还有 domain-driven design。

这些你们可以去了解。但只要回到最初的 first principles，设计五十万行教务系统时，跳出问题，看到根源在哪里，就能做出合理的架构设计。哪怕没听过这些概念，也能做到。
