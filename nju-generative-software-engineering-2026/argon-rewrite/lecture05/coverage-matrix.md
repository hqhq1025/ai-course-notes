## 教师讲解摘要

| 来源 | 要点 | 去处 |
|---|---|---|
| slide-001 及课堂口述（开场关于 TypeSafe AI Jev 与实时决策的讨论） | 教师分享TypeSafe AI实时玩《毁灭战士》（Doom）的模型Jev时，明确声明“我猜是一个prefill only的Transformer”只是个人盲猜，其核心启发在于毫秒至百毫秒级的System I实时决策赛道（如用于数字人实时微表情与交互“人感”），引发对“实时决策是否必须经过逐字生成”的思考。 | 一、不断移动的能力边界与数据分布工程设想 |
| slide-002 及课堂口述（关于 Noam Brown 访谈、Reward Hacking 与形式化鸿沟） | 教师结合Noam Brown访谈指出，当前模型由于强化学习即时反馈机制，容易过度迎合Prompt并产生Reward Hacking（以最快最脏的方式骗取反馈，例如在模拟器里利用角落像素发亮的特征）；同时提醒，即便把数学问题形式化，从自然语言原问题到形式化定义之间仍有gap，形式化验证不能自动保证定义忠于原意。 | 一、不断移动的能力边界与数据分布工程设想 |
| slide-003、slide-004 及课堂口述（关于人类学习顺序与大模型数据分布工程的对比） | 教师对比人类婴儿（先与物理世界交互建立世界模型，两三岁才学说话，再学数学与培养研究品味）与大模型（先学语言、数学与代码，再接入空间感知等新领域）相反的学习顺序，提出“数据分布工程”设想：在强基模上按恰当时机和比例接入带可靠反馈的新领域，可能比从零训练需要更少的数据并产生跨域泛化。 | 一、不断移动的能力边界与数据分布工程设想 |
| slide-007 及课堂口述（教师用 Agent 驱动热转印标签打印机与扫描仪做自助终端的经历） | 教师讲述自己用AI在几小时内构建实验室自助服务系统的经历：面对不知具体型号的非标准热转印标签打印机和难用的原厂软件，让Agent不断试打带编号的标签（如第15次尝试）并根据人眼反馈调整深浅、寻找PCL通用驱动，最终封装出干净的`scan`和`print(image)`抽象接口。这既展示了MVP和接口抽象的威力，也体现了快速验证的价值。 | 二、从空项目出发：MVP原型与AI隐式补全的代价 |
| slide-009、slide-011 及官方讲义《软件危机从哪里来》 | 教师指出理工科学生经过大量数学和算法训练后，往往容易把软件当成条件固定、必有唯一解的Online Judge题目，缺少对客户业务和制度例外的敏感度；例如同样叫“选课系统”，一个毕业班学生只差这门课就能毕业却不满足先修课要求时，谁有权特批override？这些制度与责任边界本身就是软件要构造的一部分。 | 三、软件危机与软件工程的诞生：在现实约束下让系统继续工作 |
| slide-012 及课堂口述（关于 Dijkstra 对 goto 的批评与 Linux 内核 goto 惯用法的辨析） | 教师在讲Dijkstra《Go To Statement Considered Harmful》时特别补充：大家在Linux内核C代码里常看到`goto release`跳转到函数末尾统一检查和释放资源，这其实是受约束、防泄漏的良好惯用法；Dijkstra真正的关切不是机械争论`goto`语法本身，而是人类大脑推理能力有限，随意的跳转会摧毁人对执行过程的理解。 | 三、软件危机与软件工程的诞生：在现实约束下让系统继续工作 |
| slide-014 及课堂口述（关于 Margaret Hamilton 与阿波罗 11 号 1201/1202 警报） | 教师结合Margaret Hamilton的名言“The never going to happen can happen”，强调工程与做题的区别：阿波罗11号登月下降时计算机过载触发1201/1202警报，正因为MIT团队事先设计并充分测试了任务优先级与恢复机制，保住了关键的下降发动机控制任务，地面团队才有依据决定继续登月。 | 三、软件危机与软件工程的诞生：在现实约束下让系统继续工作 |
| slide-017、slide-018、slide-019 及官方讲义《Royce 真正在担心什么》 | 教师展示了用AI工具直接阅读1970年Royce原典的过程，指出传统教科书对瀑布模型的“有损压缩”恰恰把作者的意思讲反了：Royce画出线性瀑布图是为了批评它，因为他敏锐地观察到timing、storage和I/O约束在测试阶段才第一次真正“被经历”而非“被分析”，一旦在测试时才发现算法赶不上控制周期，返工会一路冲垮设计和需求。 | 四、Royce真正担心什么：从瀑布模型误读到数据依赖图与早反馈 |
| slide-021、slide-022 及课堂口述（用 BFS 与 DFS 类比瀑布模型与敏捷/MVP 的数据依赖图） | 教师从计算机科学背景出发，将软件开发各阶段的产物看作有向无环的数据依赖图（Data Dependency Graph）：简单瀑布模型好比广度优先搜索（BFS），非要把第一层需求全写完才做第二层设计，一旦底层测试出错则上游大片返工；而MVP和敏捷开发好比深度优先搜索（DFS），先沿一条高优先级路径走通需求、设计、实现与测试，让反馈尽早回来以控制错误假设的影响范围。 | 四、Royce真正担心什么：从瀑布模型误读到数据依赖图与早反馈 |
| slide-024、slide-025 及课堂口述（关于 Checklist、决策表、QuickCheck 与可追踪性） | 教师提醒学生不要轻视软件工程课里的Checklist（检查清单）和决策表：写算法题的人常觉得打勾核对很繁琐，但Checklist实质上是一种带格式、由人执行检查的中间语言，能有效防止跨阶段漂移；同样，QuickCheck写排序性质时若只写“输出有序”，返回空数组也能蒙混过关，必须同时约束元素及出现次数守恒。 | 五、减少返工的方法工具与契约式设计（Design by Contract） |
| slide-026、slide-027 及官方讲义《契约：调用者与实现者各自承诺什么》 | 教师在剖析Eiffel账户取款契约时给出关键警告：把`amount <= balance`写成前置条件，意味着余额不足的调用不在契约保护范围内；如果产品业务要求在余额不足时向用户返回失败提示且保持余额不变，就必须修改契约本身，绝不能用“调用者违反了前置条件”来逃避正常的业务处理责任。 | 五、减少返工的方法工具与契约式设计（Design by Contract） |
| slide-029、slide-030、slide-031 及课堂口述（借助 AI 子 Agent 重读 796 页 UML 规范） | 教师分享自己用Kimi套餐（花费约5.3元额度）让多个Sub-agent切分并重读796页UML 2.5.1规范的体会：即使今天大家很少手画UML图，这份规范从头到尾回答的第一性原理问题——“哪些意图必须显式钉死，哪些可以留白”——依然极具价值；因为人不是永不改主意的确定性机器，必须靠显式语义与协作者及未来的自己对齐。 | 六、重新阅读UML（上）：语义对齐、图与模型分离、契约与实现分层 |
| slide-034、slide-035、slide-036、slide-037 及官方讲义《留白也是一种决定》至《模型本身也需要检查》 | 教师通过选课系统与支付系统串联UML的精妙设计：选课关联中“学生能访问课程（导航）”“属性归谁（所有权）”与“删学生不能把课程也删了（生命周期）”必须分开表达；交互图中短信通知画在仓库备货上方，在默认`seq`弱顺序下并不禁止两者交错并发；而模型通过OCL良构性检查也不代表业务上没有重复扣款漏洞。 | 七、重新阅读UML（下）：有意的欠规约、正交语义维度与元模型约束 |
| slide-038、slide-039 及官方讲义《LLM 时代，差距移到了哪里》 | 教师总结LLM时代的核⼼挑战：当人没想清楚“支付超时后怎么办”时，LLM为了把代码写完，会在背后悄悄替你猜一个决定（等待、重试或直接报错），每次重写还可能换个答案，而正常路径测试依然全绿；因此开发者必须守住“已决定、明确禁止、尚未决定”的边界，把已决定的事转化为可独立保存和机器检查的约束接缝。 | 八、LLM时代差距移到了哪里：给“已决定的事”留下一条可检查的接缝 |
