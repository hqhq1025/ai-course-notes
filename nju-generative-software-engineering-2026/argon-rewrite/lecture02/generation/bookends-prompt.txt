# 提示词与上下文工程

第一讲留下的问题是：Agent 已经能做很多事，我们怎样才能驾驭它？这一讲从最常见的交互方式——自然语言指令——出发，讨论怎样让模型理解目标、遵循要求，以及在没有确定答案时继续探索。

不过，先处理一下第一讲留下的意外。“没有 token 的 CS 学生应该立即退学”上了热搜，也引来了朋友们的问询。当然不会真的让同学们退学。课堂上这句话要推动的是立即实践：不要把等待完美工具、等待别人给出评价，变成一直不开始的理由。离开现场，截图只剩下一句狠话，这本身也提醒我们，同样的文字放进不同上下文，会被理解成很不一样的意思。

## 模型看到的，远不止你刚输入的一句话

我们习惯把给模型的输入叫作 prompt，中文称“提示词”。从语言模型续写文本的角度看，前面的文字既是开头，也是控制后续生成的条件。进入聊天界面以后，用户更容易把 prompt 理解成对话框里的一条要求。

但对 Agent 来说，指令分散在很多地方。运行 Agent 的外围系统，也就是 harness，会提供系统指令与工具说明；仓库里的 `AGENTS.md` 可能约定项目规则；加载的 skill 会给出特定任务的方法；用户会不断补充目标。与此同时，代码、文件、历史消息和工具返回也会进入上下文。

第一讲里的 `Pr[token | context]`，其中的 context 就包含这些内容。模型下一步做什么，受到整份上下文影响，而不是只由最后一句话决定。这里还要区分指令和材料：工具返回的一段文章可能是分析对象，并不因此拥有给 Agent 下命令的资格。来源、作用范围和优先级，也属于我们组织上下文时需要考虑的事情。

所以，“提示词工程”逐渐扩展成了“上下文工程”：关心模型在做决定时能看到什么，哪些是目标，哪些是约束，哪些是证据，哪些只是过时的过程记录。写好一句话当然有用，但把相关文件、已有实现和验证结果放到合适的位置，往往同样重要。

课堂提出了一个可以立即做的小实验：让 Agent 按照需要遵循的指令类型，说明当前任务有哪些目标、工具规则、项目约定和输出要求。这个实验可以帮助我们理解它正在怎样组织任务，但模型的自述不能当作实现机制的完整说明。想知道某个行为为什么发生，还需要检查可以访问的配置、代码和实际操作结果。

例如，为什么有些命令执行前会询问用户，有些不会？不能只从“模型觉得安全吗”来解释。Agent 提出动作，外围程序还可能检查权限和审批规则，操作系统则执行实际的访问限制。提示词中的要求与程序中的机制一起决定行为；一句“请遵守规则”，并不等于已经实现了一个可靠的执行边界。

## AI 降低了开始学习的成本

上下文工程听起来像开发者才需要关心的技术，但学生每天都能用到。微积分里有一步推导不想验算，数字电路有一条数据通路没看懂，计算机系统基础里始终没搞清链接发生了什么——过去，这些问题很容易被暂时搁置，一搁置就是整个学期。

现在可以立即把具体问题交给 Agent：给出一个最小例子，逐步推导，运行一段程序，再根据结果追问。课堂把这种能力称作“拖延症的克星”。过去的自我驱动，常常意味着对挫折有很高的容忍度，愿意花很久寻找一个解释；现在，我们可以把同样的精力投入到更快的尝试与反馈中。

但学习仍然需要自己的活动。一个可行的循环是：先借助 AI 弄清一个问题，然后合上资料，用自己的话重述；让它追问含糊之处，找出反例，再用推导、原文或程序结果核对，最后重新解释一遍。复述时卡住的地方，往往比读答案时觉得顺畅的地方更能暴露知识缺口。

这可以理解为让 AI 做一个随时在场的听众。它帮助你开始，也帮助你发现哪里还没讲明白。真正推动理解的，是这个循环里不断变得具体的问题和不断接受检验的解释。

## 写清楚“完成”是什么

模型具有很强的指令遵循能力，但首先要有值得遵循的指令。上下文中的要求越明确、越容易验证，模型就越有机会判断自己距离目标还差什么。不明确的要求，则可能让它很早就认为已经完成。

“一句话生成极品飞车”可以产生很漂亮的演示。但你心里想的，可能是有真实地图、特定美术资产、某种驾驶手感的赛车游戏。模型交出的，也许只是一个能移动、会碰撞、有速度感的网页。它未必在任何一步明显违背了指令，却在一连串默认选择之后，做出了另外一个产品。

这就是第一讲的 Intent、Spec 和 Impl 之间的缺口。镜头怎么跟随，车怎样转向，地图从哪里来，撞车以后发生什么，每个省略都留下了选择空间。模型可以把这些选择做得相互一致，但“一致”不意味着“正好是你想的”。

个人主页是另一个例子。“根据我的公开信息，制作一个现代风格的主页”，看似清楚，其实“现代”并没有排除多少可能。模板、渐变、卡片和装饰都能被解释为现代风格。如果你在意的是特定字体、颜色、留白、信息顺序和排版，就应当给出这些具体要求或参考。几个形容词，通常不能代替设计。

课堂的经验法则是：**写清楚你的指令，承担一切“不明确”的后果。** 它要求我们意识到，没有说明的地方，实际上是把决定权交给了模型。并不需要把所有细枝末节都提前决定，但要知道哪些地方允许它自行发挥，哪些地方决定了产品是不是你要的。

一个实用的检查办法是：让另一个人只看要求和最终产物，能否判断任务已经完成？“做得专业一点”很难判定；“页面首先展示研究方向和近期工作，手机上无需横向滚动，所有项目入口都能打开”，就提供了可以检查的行为。不能完全机械判断的品味，也可以通过示例、对比和反馈逐步说明。

完成的语义还包括失败。如果关键条件无法验证，合理的结果应当是报告哪里没完成、缺少什么证据，而不是交出一段肯定的总结。只有把这些状态说清楚，Agent 才能更可靠地决定继续尝试，还是需要新的信息。

## 一步有限，为什么还能完成复杂任务

一个疑问随之而来：如果模型只是反复计算下一个 token 的概率，它怎样同时满足很多约束？

一次模型前向计算的结构和深度是有限的。它不会在这一瞬间任意增加计算步骤。但模型可以把中间结果写进上下文，再利用这些结果继续生成。遇到不确定的地方，可以先尝试一种分解，检查后发现不合适，再修改。这就是课堂用来理解思维链的直觉：把一串输出看成能够存放中间状态的工作纸。

这样，更多 token 就可能换来更多计算深度。它是否有效，取决于模型有没有找到能推进问题的步骤，以及能不能识别错误。课堂借“找解常常比验解难”说明这种方法的吸引力；这是一种理解搜索过程的类比，不是在证明某个复杂性理论结论。

为了把指令遵循的难度具体摆出来，课堂给了几道故意刁难人的写作题。第一道要求写八句中文诗：句首依次是“计算机学院真牛逼”，讲一个与动物相关的故事，“二零二六九月一日”八个字还要依次出现在八句中，并且押韵。生成素材给出了这样的尝试：

> 计成二兔越山冈  
> 算到零时雪满塘  
> 机警狐衔二袋粮  
> 学随六雁辨风向  
> 院中九犬忽声扬  
> 真到月明逢恶狼  
> 牛守一夜迎晨光  
> 逼得日升狼遁荒

检查时，可以先竖读句首，再逐句寻找指定字，最后看句尾和故事。藏头与嵌字都能对上，句尾也有相近的韵感，但“方向”的“向”与其他句尾在普通话拼音中并不完全相同，读起来有些句子也明显是为了凑约束。它展示的是模型能够寻找并修补一个多约束解，而不是宣告模型已经写出好诗。

第二道题要求一句话有十八个汉字，全部带相同偏旁，还要有意义和故事性。素材中的例子是：

> 洪涝淹没江港渔浦，油污漂浮，沈涛泅渡济溺。

去掉标点，可以数出十八个字，都带三点水；把“沈涛”读作人名，故事就是洪灾与油污中有人游过去救助溺水者。这里的检查比较直接，但“都含三点水”和“词典中都归为同一部首”仍然是不同要求。要交给程序验收，就得先决定检查的是哪一个。

第三道题要求所有字都同音，写一段有现代背景的文言故事，不能照搬已有的同音文。素材尝试用不同声调的 `yi` 音字，写一个翻译器误译、送修、恢复正常的故事。这立即暴露出另一项规格选择：“同音”是否要求声调也相同？作者靠字形区分意思，读者看文字还能猜出情节，念出来却可能几乎无法理解。

这三道题把两类评价放在了一起。藏头、字数、指定字和读音可以逐项检查；通顺、趣味和文学性则需要更丰富的判断。模型通过形式检查，说明它能够搜索和纠错，但形式检查没有覆盖的质量，并不会自动出现。软件测试也有类似的边界。

## 上下文中的规则，也会争夺注意力

把要求写进上下文，可以让模型在生成过程中反复利用它。项目约定使用中文，或者提交信息不添加某种署名，模型就有机会在相关时刻纠正自己的输出。不过，“在上下文里”并不保证“每次都会正确遵循”。

提示词还会带来副作用。你说“白色背景，不要半透明效果”，模型可能把这句话变成代码里的注释：“白色背景（不要半透明效果）”。它完成了背景设置，却也把原本只用于沟通的要求带进了产物。

于是，一个看似合理的修补办法出现了：再加一条永久规则，禁止把用户要求写进注释。但每遇到一次问题就增加一条规则，上下文会越来越长，约束之间也越来越难协调。这不是免费的增强。

更合适的做法，是区分长期适用的简短规则与当前任务需要的细节。项目层面留下真正稳定的约定；特定任务的方法按需加载；能够直接检查的要求，则尽量落到代码和验证结果上。白色背景可以由具体样式和渲染结果确认，不必依靠越来越长的自然语言劝诫。

上下文工程因此也包含取舍：删去一段无关说明，有时和增加一条关键要求同样有效。模型需要的不是尽可能多的文字，而是此刻做决定时用得上的信息。

## “你是一位审稿人”，还不够

课堂接着把任务换成论文审稿：假装自己是 ICSE 的审稿人，阅读指定论文，写一份约一千英文词的 review，并判断是否应该接收。

模型很容易写出一份看起来像审稿意见的文本：总结贡献，列出优点和不足，再给出一个建议。问题是，它究竟完成了多少判断？“扮演审稿人”可以提示语气和输出结构，却没有把一个好审稿人的方法自动交给它。

论文的信息密度非常高。作者不仅给出了答案，也替读者选好了问题、术语、比较对象和衡量标准。如果顺着文章走完一遍才开始评价，很容易在不知不觉中接受了作者的整个框架。你以为自己在批判性思考，其实只是在作者划好的场地里打转。

可以把审稿工作拆成三条不同的路线。第一条从判据出发，先还原论文声称的贡献，再问每项贡献需要达到什么标准，证据在哪里。第二条审查证据，把核心主张、实验支持、未验证假设和替代解释一项项对应起来。第三条站到复现者或反方的位置，重算一个关键结果，寻找最小反例，明确什么观察会推翻结论。

这几条路线的价值来自问题不同。若一开始就共享同一个总体印象，最后可能只得到同一个判断的三份润色。独立形成初步意见，再比较分歧，才更容易发现原先没有看到的东西。

这也说明人的方法论如何影响 AI 的结果。你不必替它读完每一行，但需要知道什么算有根据的判断、哪些证据缺失值得追问。短程任务里，把方向带对、把标准说清楚，往往已经能显著改变产物。

当一套做法多次有效，就可以把它沉淀成 skill。Skill 看起来是一段提示词，真正值得保存的，是成功经验中的搜索策略、判断标准和检查点。它帮助 Agent 复用一种做事的方法，而不是每次重新凭第一印象发挥。

Skill 也不是越长越好。如果把所有想得到的要求都塞进去，它本身就会变成一道复杂的指令遵循题，和前面的藏头诗颇有相似之处。保留真正影响决策的内容，把机械工作交给脚本，把需要时才看的材料单独放置，才能让经验更容易复用。

## 为什么大仓库有时比空项目更容易

课堂提出了一个有趣的观察：从零做一个看起来不难的产品，AI 可能在某个时间点开始不断翻车；进入一个成熟的大型系统，反而能够完成相当复杂的修改。

可以从上下文的角度理解这种差别。成熟代码库已经做出了许多决定：怎样命名，模块如何分层，错误怎样传播，测试放在哪里。Agent 在解决局部问题时，可以学习附近的例子，沿着现有结构补充实现。代码量虽然大，当前任务需要自由选择的事情却可能更少。

空项目恰好相反。没有已有结构约束选择，每次局部实现都可能顺手做出一个长期设计决定。如果最初就形成了混乱的惯例，后续生成又以这些惯例为上下文，AI slop 就会不断叠加。**代码库本身也是提示词。** 它会示范怎样做，也可能示范怎样把问题继续藏起来。

这里不能推出“大仓库一定好改”，或者“模型会自动认出最佳实践”。它也可能模仿历史包袱。课堂进一步提出了一个未经实验验证的猜测：给 Agent 看一个相近领域、设计优雅的成熟系统，再让它实现自己的需求，能否提高质量？

这个猜测值得做实验，但还不是结论。相近领域到底有多相近？应该读整个项目，还是几个关键例子？如果参考项目的约束与当前任务不同，会不会把不合适的架构也学过来？一种比较方式是给同一任务设置无参考、完整参考和精选参考三种条件，比较实现后的修改代价与缺陷，而不仅仅看第一版能否运行。

这又把问题带回了学习。处理器、操作系统、编译器和数据库里有很多设计智慧。理解接口、不变量、状态和失败模式，才能知道该把模型引向哪里。对所做的东西“有概念”，仍然是驾驭它的前提。只是现在，学到一个原理以后，可以更快地把它用到真正的系统里。

## Token 花完了，研究为什么还没有推进

能够执行长程编程任务，意味着模型在遇到错误后仍能继续：修改、构建、测试、观察，再修复。这样的闭环依赖反馈。测试失败提供了具体方向，编译器报错指出了局部问题，模型可以据此不断尝试。

但把任务交给更强的模型、投入更多 token，并不保证任何长程问题都会收敛。课堂讲了一个研究失败案例：希望优化一个符号执行引擎，已经有一个初步想法，于是把想法和 benchmark 一起交给 Agent，花了很多 token，最终没有得到结果。

原稿没有给出已经查明的失败原因，因此这里能做的是提出待检验的解释。一个可能的问题，是总 benchmark 分数提供的反馈太粗。没有变快，究竟是主要时间花在求解器里，路径搜索策略有问题，缓存没有起作用，还是修改引入了新的开销？如果这些因素混在一起，下一步应该试什么就很难判断。

另一个可能的问题，是任务把“把这个想法实现好”当成了目标，但研究真正需要回答的，可能是“这个想法是否成立”。如果原始假设就不对，继续完善实现也不会带来期待中的进展。一个能否定原想法的实验，有时比更多代码更有价值。

因此，更有用的起点可能是先测量主要瓶颈，把想法写成一个可以被实验推翻的预测，再构造能够快速反馈的小实验。确认局部机制确实有效以后，才把它放回完整系统，检查收益是否仍然存在。研究中的“推进”可以是缩小未知，也可以是排除一个方向；不能只把它定义成最终分数必须上涨。

## 人应该盯住哪些地方

既然人了解领域，随时干预是否最好？课堂给出的经验恰好有点反直觉：我知道怎样让某个任务更快完成，却越来越少干预了。

原因在于，单个任务的完成时间与一天能完成的任务总量，是两个不同目标。如果 Agent 走一点弯路最后也能完成，我可以把注意力移到另一件事上。机器多花一些时间，换回人的时间，整体产出反而增加。

这种取舍需要有边界。接口已经看过、结果可以检验、实现出了问题能够替换时，可以让 Agent 自己探索。相反，一个会扩散到许多模块的接口决定，一个昂贵或难以恢复的动作，就更值得提前关注。人的注意力应当按照决策影响和返工代价分配，而不是平均撒在每一行代码上。

长任务还会不断产生日志、补丁和工具输出。上下文能容纳这些材料，不代表模型在每个时刻都能同样有效地使用它们。课堂观察到，随着上下文增长，指令遵循可能下降，而最近的要求或刚加载的方法往往更容易被执行。具体表现取决于模型和任务，但工程上可以主动缩短关键要求到关键决定之间的距离。

例如，在阶段切换时重新确认目标、接口和未决问题；把能检查的不变量落实成测试；让错误在继续传播之前暴露。上下文压缩也要保存当前约束和证据，而不只是把过去发生的事情写成流水账。这样，人的放手才有可以依靠的反馈机制。

## 在不确定性中探索

到这里，我们一直在讨论怎样把任务说清楚。但许多有价值的任务，本来就没有确定路线。我们希望 AI 帮助探索，而不仅仅执行已经写好的计划。

“帮我考虑几种方案”通常有效，却可能过早结束。模型给出几个听起来合理的答案，已经满足了“几种”的数量要求；更有意思的方案，也许仍在它没有走到的方向里。此时，多沿一条思路想一会儿，与主动探索更多不同思路，是两种不同的算力使用方式。

课堂用取名字作例子：给一个蒋姓的小孩取好听、又有寄托的名字。如果直接要几个答案，模型可能给出自己偏好的高概率组合；许多家庭同时询问，又可能迎来 AI 时代的新一代“子涵”。

要扩大探索，可以先划分空间：从典故、音韵、方言、时代感等不同角度生成候选，再检查出处、谐音、书写和个人偏好。也可以让不同 Agent 独立提出候选或负责挑错，最后再汇总。关键在于它们是否看了不同方向、提出了不同问题，而不在于开了多少个看起来相同的窗口。

这里仍然离不开人的判断。“给更多名字”解决的是候选数量，“哪些名字值得留下”则需要评价标准。没有分辨率的筛选，可能只是把一个平庸答案变成一百个平庸答案。探索空间与评价方法应当一起设计。

人类社会其实一直在通过类似方式扩展自己的视野。每个人的教育背景、生活圈和经历都有限，也都带着偏向。与舍友讨论，去会议上听别人怎样提出问题，价值往往来自发现自己的默认前提。交流之后，每个人仍有自己的偏向，但它已经被新的经验改变。

课堂借“世界很大，人很小”的视角提醒我们，没有人能独自穷尽所有可能。群体的价值可以来自不同的局限相互补充。把这个思想带回 Agent：增加计算资源时，应当考虑怎样增加探索的差异，而不是只增加同一种思路的重复次数。

如果计算资源能够持续转化为探索能力和判断能力，这也带来了一个令人不安的未来问题：拥有大量算力的人或组织，会不会获得远超普通人的智力资源？课堂用“墙里面是超人，墙外面是动物世界”表达这种担忧。这是对未来可能性的追问，并非已经发生的终局。

对于正在学习的我们，可以从眼前开始改变做事方式：让模糊愿望获得可检查的表达，把有效经验沉淀成可复用的方法，在需要探索时主动扩展方向，又用证据筛选结果。提示词的价值，最终要落在这些行动如何改变任务的结果上。

【第三方字幕校订，仅补口述；第2-8讲未标人工校对，与官方材料冲突时以官方为准】
今天我们来讲一个和生成式软件工程关系特别大的主题，也就是你和 AI 沟通的渠道：自然语言提示词。这基本上是大家和机器沟通的唯一接口。从 ChatGPT 时代开始，大家在聊天窗里跟 ChatGPT 对话时，就知道我们要用 prompt 给机器一个指令，然后 AI 会返回很多内容；文字、代码、图片都有可能通过 prompt 生成。

我第一次感受到 prompt 的力量，是在 2023 年上操作系统课的时候。当时正好是 2022 年底 ChatGPT 刚发布不久，我试图让 ChatGPT 帮我讲一讲 inline assembly。现在应该已经没有人写 inline assembly 了，它已经成为一个传统艺能。我发现它解释得出奇地好，而且我给它的应该是一个没有出现在训练语料里的东西：我故意做了一个地球人应该不会实现的 inline assembly，但它做得相当好，虽然确实不完美。那一刻我突然感觉时代要变了，只是还没有像今天这样清楚地感受到时代会怎样变化。

提示词就这样成了一个新词。在 ChatGPT 之前，我们好像没有用今天这个意思讨论过 prompt。你们可能会觉得，在聊天框里输入的那段东西叫提示词，例如“帮我生成一个游戏”或“帮我把这个作业做完”。但提示词并不仅仅存在于对话框里，agent 看到的是一整个上下文。在你和 agent 聊天之前，它就能看到 system prompt，这也是提示词。system prompt 之后，它还会加载很多东西，例如你的 `AGENTS.md`、一些 skills；`AGENTS.md` 里还可能要求它读取别的文件。实际上，在 agent 第一次停下来和你对话时，它的上下文里已经有很多内容了。

从最初的系统提示词开始，可能有 agent harness（例如 Codex、Claude Code）内建的内容；除此以外，所有工具调用和工具调用的结果也会出现在上下文里。它是一个线性的上下文，直到后来 user 对它说：“给我做一个游戏吧。”所以提示词是非常长的。这也意味着今天 agent 的能力很离谱：它可以看到一个非常长的提示词。比如你可以在最早的 system prompt 里要求它用中文回答。为了上课演示，我就会这样设置，所以哪怕我的 user message 是用英文写的，它输出的仍然是中文。

因此，当我们说优化提示词或提示词工程时，并不仅仅是给它一个指令；我们真正表达的是“上下文工程”，也就是对模型的整个上下文进行工程设计。模型做的是 next-token prediction，每次预测下一个 token。这个 token 可以是工具调用，也可以是输出的字符；无论如何，它会不断向后推进任务的执行。

大概从 Claude Opus 4.5 这一代开始，Anthropic 发现模型依靠强化学习和后训练，学会了非常强的指令遵循能力。即使上下文非常长、接近百万 token，它在很靠后的地方依然能遵循指令，也能在一定程度上看到前面的内容。有一个很著名的梗：你可以在最早的 prompt 里加一句“每说一句话都要在后面加一个喵”。等你跟它工作了很久，突然发现它说话时的“喵”丢了，你就知道它可能因为上下文溢出被截断、被压缩或其他原因，开始不能遵循指令了。这时就需要重新想办法。这些都是大家在工程实践中发现的、有趣的上下文工程或者提示词工程方法。

我上这门课最希望告诉大家的一件事，也和“没有 token 就应该退学”这个玩笑有关：所有事情都应该立即开始尝试。AI 给我们的一个能力是，任何时候你觉得事情有一点麻烦，都可以立即行动，因为 AI 是一个非常耐心的老师。

我上大学的时候，如果有个东西不会而室友会，我跟他沟通的成本很高，而且可能会担心在室友面前暴露自己很菜。虽然菜也很正常，但对于 AI 这个老师来说，它不会嫌弃你，而且你可以任意追问。比如我刚才说 agent 有一个很长的上下文，里面不仅有 system prompt，还有各种各样的东西；下一秒我就可以立即打开一个 agent，直接问它：“老师上课时说，agent 的上下文里不只是一两个提示词。你能检查一下你的上下文里都有些什么吗？”它可以检查自己，甚至可以检查自己的日志。agent 经常会给你惊喜：当你问出一个问题时，它解决问题的手段可能出乎你的意料。

agent 恰好能看到自己的上下文。根据刚才所说，它在做 next-token prediction 时能看到这些内容，所以原则上应该能把它们读出来，除非有明确指令禁止。例如有些模型 provider 会禁止你套取系统上下文：它们既会通过模型微调，也会在 system prompt 前面写明确指令，要求对任何询问 system prompt 的请求都予以拒绝。但这里用的是完全开源、可以调试的框架，所以它可以说明系统提示词来自哪里，以及其中的工具使用指南、回复要简洁等要求。

接下来它会打开我用户目录下的 `~/.pi/agent/AGENTS.md`。这是我自己写的。因为这台机器用于上课演示，所以我在全局上下文里放了“用中文回答”，还要求结尾必须写一个 recap。大家可能已经注意到，模型跑完后最先出现的是对本次工作的总结。之后还有项目级的 `AGENTS.md` 指令，而且目录里可以继续放 `AGENTS.md`，所以它是一层一层的。

上下文里还有 skills 的索引。skill 是模型能够执行的功能，比如我有一个叫 make-slides 的 skill，它可以渲染我按 F5 播放的幻灯片。但模型起初只能在上下文里看到它的元数据，包括名称和简略描述；完整的 `SKILL.md` 可能很长，只在匹配任务时按需读取。那一轮结束以后，完整 skill 内容也会从上下文中被抹掉。除此之外还有工具定义，它们也直接以文本形式出现在上下文里；再往后还有对话历史。

每次执行还会注入当前环境，例如模型，甚至当前时间。这是很多同学不知道的。如果你和 DeepSeek Chat 对话，可以尝试把每次注入的环境套出来；这不属于系统提示词，是可以问出来的。所以，上下文是一个非常长的序列。所谓上下文工程或提示词工程，就是把所有这些内容安排好。

刚才其实也演示了 AI 时代应该怎样学习：不仅可以把问题问清楚、在不明白时追问，还可以反过来运用费曼学习法。怎么判定自己是否真正理解了知识？可以反过来当老师。过去做这件事的成本很高，因为你需要一个听众来检验自己，而室友可能不想听你讲，可能对这个话题不感兴趣，也可能已经太了解它。

现在你可以先把 AI 当老师，不断请教，直到自己认为弄懂了；然后再反过来让 AI 扮演学生，对它说：“我要把这个东西给你讲懂，你假装什么都不知道，看看我的逻辑哪里有错、有漏，并在这时纠正我。”正着一遍、反着一遍，基本上就能把概念理解得很清楚。我觉得你们作为 AI Native 的一代人，一定会把我们这一代人彻底卷死，因为你们有更充足的时间。你们现在的任务就是学习，不像我还要负责其他事情、对别人负责。这是你们最好的时代，所以也可以把费曼学习法用起来。

在学习这些东西的过程中，你们会留意到很多有趣的小细节。使用任何 agent 时都可能面临一个问题：如果要执行危险操作，它会要求你确认。当然，pi 在默认配置下是 YOLO mode，所有事情都直接执行。如果提示词给得不好，它有可能直接把我整个环境删了，那我今天就可以直接下课了。这是一种平衡：你可以让它在更安全的沙箱里运行，但如果观察过 Codex，会发现它经常先在沙箱里尝试一件事，失败后意识到这件事不能在沙箱里做，于是申请到外面再做一次；再做时，它甚至会问你是否允许这项可能有危险的操作。

这很讨厌。比如你要去吃饭，先把三个 agent 任务想好并运行起来；回来却发现它只跑了一分钟，就一直停在那里等你确认。这既浪费 agent 的时间，也浪费自己的生命。你们经常会看到这样的小细节，而对小细节的注意力，在一定程度上决定了你能走多远。这也是 AI 时代最好的地方。

比如我留意到 Codex 的一个细节：有些命令会被认为不太危险，可以直接执行。它并不是每次调用 Bash 工具都要求确认，例如它可能认为 `ls -l` 是安全的。但实际上，这个命令未必安全，因为在某个环境里，`ls` 可能被重新定义成另外一条命令，比如 `rm`。当然，正常人不应该这样做，但恶意环境里可能出现这种情况。

你可以好奇它是怎么做到风险判定的，然后直接下载一份 Codex 的代码来读。这就是现代软件工程和过去很不一样的地方。我在大二、大三刚接触 Linux 内核时，光是把内核下载下来、搞清楚怎么编译，就花了很长时间，而且还是在有一定 Linux 使用经验的基础上，完全是一种劝退。某种程度上，我能从那个时代坚持下来，是因为对这种劝退的东西有“一定还要试一试”的执念。

今天，如果这是一个好东西，例如 Codex——也许你们更喜欢 pi，pi 确实更轻量——你们不再需要害怕任何一个软件系统的复杂性，因为可以直接问。比如可以输入：“我留意到一个很有趣的问题：调用 Bash 时，有时会向用户确认，有时不会。这里有一个风险判定，但风险其实很难，因为你并不知道具体的命令语义。所以你是做了分析，还是让大模型给出风险评级，或用了其他方法？读一下相关代码。”这就是一种提示词。

当 pi 看到我的提示词之后，它前面的提示词也都有，就会开始试图解决这个问题。它会搜索代码；如果有 LSP 之类的工具，它还可以使用工具，像你们在 IDE 里面点来点去一样。

你们用过 IDE 的功能吗？我记得上操作系统或者计算机系统基础课的时候，我都会说，我发现有很多同学从 PA1 做到 PA4，VS Code 里面都还是有红线的。有红线就意味着你没有做正确的配置。虽然有红线也没有任何问题，你还是可以在我们的受控环境下编译，把所有东西都完成，但这不是正确的 practice。你应该花一点时间配置 VS Code，加上 include path。因为我们有一些 `-I` 这样的选项，会指定编译时的路径。把这些配置做好以后，你就可以得到 IDE 的所有功能：可以用 Ctrl 点击，也可以 rename symbol，用重命名符号的方式一次性重构很多东西。哪怕在大语言模型之前的时代也可以这样做，而在今天，配置这件事变得更容易了。

你看，它确实会让大模型做风险评级，也有一层静态分流：沙箱内的低风险命令会直接执行，命中网络 allowlist 的也会直接放行，不需要审批。如果只是一个 `ls`，你可以想象 Codex 里面会有一个 parser，也就是语法处理器。这个 parser 会处理 Bash 命令；如果发现命令在某个白名单里、绝对安全，就会直接放行。如果不在，它会在 prompt 里面 inject 一小段话，同样也是 prompt engineering，让模型给这个命令的安全性评级。

我现在也可以直接把安全评估的 prompt 打印出来看看。我事先完全没有准备，也完全不知道它是什么。我们可能不能百分之百相信我现在用的 DeepSeek-V4-Flash 模型，但是这个方法非常有用。如果你不相信它，可以让它把 prompt 改一改，比如改成让以前某个不会被拒绝的命令被拒绝，或者让以前某个被拒绝的命令不再被拒绝。这些都可以由 prompt 控制。改完以后，你可以观察它行为的变化，这就成为了一个证据。你也可以让 agent 来做这件事。

它这里有一些 untrusted evidence，可能还有其他内容，我就不再花时间看了。前面基本是在告诉大家 agent 的上下文是什么，以及我们应该怎样做提示词工程。下面再多讲一点：怎样写一个好的提示词，或者写一个好的模型上下文。

我们都知道，上下文包含非常复杂的要求。这又让人想到软件工程里一个老大难的问题：我们有 intent，脑子里想的是做一个国民级的应用；从 intent 可以到 spec，包括软件的架构是什么、应该选什么语言实现，以及很多细节。当我们把这些细节定好以后，还要做 implementation。

任何时候，我们用模型完成一个软件工程任务，都会把整个大流程里的一部分塞到模型的上下文里。就像刚才我让 agent 帮我读 Codex 代码时，它读到了 Codex 的一些设计原则。比如一般会有一个文档说明为什么需要这个安全策略、安全策略总体是怎么考虑的；然后可能还有一个 spec 文档说明安全策略怎么做，以及 implementation 是怎么实现的。这是一个互相印证、逐步向后输出的过程。

如果我们想写一个好的模型上下文来完成软件工程任务，原则是什么？还是要去想这个 gap。如果你只给模型一个模糊的 intent，它就很容易认为自己已经完成了。比如你说“给我生成一个 CS:GO”，它就给你生成一个 CS:GO，这时就可能发生漂移。但如果你能给模型完整的系统设计和 spec，假设模型能力无限大，它遵循系统 spec 的结果就会更加确定，也更容易验证。比如你说要用 C++ 实现，最后它却给出一个 Java 实现，你一眼就能看出来；你认为不满意，模型也应该认为不满意。但如果你在 intent 里只说“给我做一个东西”，没有说用 C++，它也不了解你，于是写了一个 Java 实现，那就发生了很大的漂移。

所以，模型上下文最重要的原则是：如果任务明确、可以验证，尤其是机器可以验证，比如有一个脚本能判断测试通过还是不通过，那么 agent 就可以不计代价地一轮轮、一次次尝试，把事情完成。甚至多轮失败以后，它可能会在系统里安装别的工具，或者去网上找答案。

最近有一个很有趣的复盘，讲的是 OpenAI 的 agent swarm 怎样通过非常长的多轮对话，攻破 Hugging Face 的漏洞。大概是在一个 CTF 竞赛里，给它们一个不可能完成的任务，有上千个 agent 一定要完成，于是它们去找系统漏洞、提交非法请求等。我看过一个很长的复盘，非常有趣。也就是说，一旦任务可以验证，虽然任务可能几乎不可能完成，但只要非常明确，agent 就会不知疲倦地一直向下做。

回到刚才 CS:GO 的例子，如果你想控制漂移——这里是 Kimi K3 生成的。大家很喜欢这种评测：能不能用一句话生成一个游戏，比如 CS:GO 或者《极品飞车》。可以看到 Kimi K3 的表现非常好，包括物理、碰撞和逻辑的制作；顶上还有一个后视镜，看起来也没有问题，做得非常逼真。

但这依然可能不是你想要的那个游戏，因为你脑子里的游戏是你每天打开来玩的那一个，而 AI 生成的是它收到指令后自己生成的东西。它没有办法补全你脑袋里模糊的约束。比如你可能想复用真实地图和美术资产，如果真的把这句话说出来，它可能就会去 OpenStreetMap 之类的网站下载一个开源地图。比如你真的想在南大仙林校区里面开车，这件事是能做到的。指令给得越清楚越好；如果你能找到南大仙林校区地图文件的格式，它就真的能把这个世界重新建模出来。美术资产也一样，有很多公开可用的车、城市、树等资产。如果你不告诉它，它会认为自己需要做一个 self-contained 的东西，所有内容都由它自己生成，这其实可能是早期就出现的误解。

所以，一个 rule of thumb 就是：写清楚你的 prompt，把所有东西都写清楚——我要什么、用什么实现、怎样才算正确，然后帮我把它搞定。你要设计整体的约束能力。这也是我这个学期最重要的教学内容：你怎样约束它，怎样只给一点方向性的引导，就让它一下子 get 到。因为它是模型，可以想象成一个非常聪明、博士水准的人，而且在各个领域的知识都非常好。这样的模型基本上永远会给你惊喜。

在这个模式下，模型要么完成任务，要么终于有一天会说：“对不起，这件事对我来说太难了，我们可能需要重新做一个规划。”它自己也可能会制订计划。

我举一个具体的例子。上节课讲到，我现在的想法是：这门课结束时，每位同学交一份简历给我。中间会有一些 project 给大家选做，然后每个人交一份简历。我会用 AI 评估简历，判定大家通过还是不通过，就像第一节课时展示的那个不好的简历案例。

简历里首先会有一个链接，可能指向你的 GitHub 或者个人主页。我应该已经试过用一句话让模型生成主页。先忽略它生成的内容，我不知道 DeepSeek-V4-Flash 是从哪里找来的。从美术效果看还是非常好的，非常专业。比如你们上 PyPI 或者 Homebrew 的网站，也会看到类似的漂亮界面。而且它应该读过我的主页，知道我的主页是一个 terminal。

但你又会觉得这个页面 AI 味很重。你说不出来具体原因：它确实做得很好，滚动和浮动效果也都很好。只用一句 prompt，说“一个现代风格”，它也的确满足了“现代”；但如果你给它一句“不要那么有 AI 味”的 prompt，它可能也不知道应该怎样遵循。

这是我的一个 PhD student 的主页，我觉得很干净、很舒服，但你也说不出那种 AI 味到底是什么。在 AI 之前好像也有人这样写主页。再看一下我的主页，就有点不一样：这是一个真正的终端，可以使用管道。如果放大看，这些字并不完美，不是特别工整。我在所有 xterm.js 内容渲染完以后做了一个很小的后处理，让它有一种真正的打字机打出来的、不完美的效果。这样看起来 AI 味就没有那么重，因为它确实不像 AI 的风格，虽然我一行代码也没有写。

这个页面关不掉，它捕获了我的键盘，可能是一个小 bug。还是刚才那个原则：你的指令给得越清楚，agent 完成得越好。如果你能给出具体的风格——需要一个什么样的终端，背景、前景是什么，渲染以后怎样处理，样式和排版是什么——基本上就可以去掉 AI 味。

所以这些设计仍然掌控在大家自己手里。你们需要读很多前端的书，甚至读很多设计的书，再看一些好的网页。每次看到谁的网页设计得好，就把它记下来，想想它为什么好：是不是两个按钮之间使用了不常规的间距，或者用了不常规的样式。你们有时间，可以漫无目的地探索；探索过程中有惊喜，是非常好的事情。

现在我比较担心的是我们的孩子这一代人。你们这一生还是见过很多 non-AI、做得非常好的东西的。上学期结束时，我最后一次接孩子，进到学校里面。学校大概在欢送毕业生，那张图片满满都是 AI 味。我发现不仅这里的图片有 AI 味，计算机学院楼下欢送毕业生的图片也是同样的 AI 味，还有短视频里女主角永远是同一张脸的感觉。

当所有人都被 AI 生成的东西同化时，就有一点危险。但至少数字世界里还保存了足够多 pre-AI 时代的东西，有足够的多样性。大家可以多留意一点。每当看到一个设计好的网页、简历或者任何东西，都想一想设计者到底是怎么想的，它的解空间到底是怎样被约束住的，怎样防止 AI 像收到“做一个现代风格个人主页”这样的指令后一路发散。

这基本上就是生成式软件工程主要要学习的东西：明确你的意图。只有你跟 AI 玩过，让它“生成一个现代风格的主页”，你才会理解。公众号上各种文章都在说 Kimi K3 的前端能力又增强了，达到了世界第一；OpenAI 好像又要发新模型了，这当然也可能是非常可怕的事情。但无论如何，模型就是模型，它的品位基本上是固定的，尤其在你不控制它的时候，它会朝一个固定方向发散。

这也是为什么我们鼓励大家跟不同的人聊天，为什么学校里有不同的老师上不同的课程。多样性是好的。见识过以后，你就能越来越明确地知道自己到底想要什么，然后把它精确地说出来。

这其实需要软件工程的支持。如果你已经走到这一步，比如理解了技术选型，明确知道不同技术选型的优劣，那么具体的选择反而没有那么重要，你真的可以和 AI 讨论。比如，我现在有两种选择，谁好谁坏？你可以像费曼学习法那样引导 AI。假设你承接了一个教务系统，后台应该用 Python、Java 还是 TypeScript？如果你知道这几种语言的差异，以及将来上云时可能遇到的问题、哪一种更方便等，就可以和 AI 讨论。你当老师，告诉它你现在要做什么，请它挑战你，看你能不能说服它这个学生。这是上下文工程的内容。

讲了应该怎样写 prompt，我们还要稍微讲一讲模型是怎样遵循指令的，也就是“听指令”这件事到底是怎样完成的，这样我们就能更好地让模型听我们的指令。我们讲过，模型是一个概率分布，它根据当前上下文 predict next token。这里有一个很有洞察力的角度：模型每输出一个 token，做的其实都是有限的计算。虽然现在可能有 3T、1.5T 这样参数量很大的模型，但模型为了输出一个 token，也只是让其中被激活的部分跑一遍，所以它是一个固定大小的计算。

你们刚上计算机系时可能听说过图灵机，也可能听说过图灵机的计算能力非常大，但不一定完全理解邱奇—图灵论题背后代表的意义。你们也知道有限状态机，在数字电路课上做过。比如一个计数器，在有限个状态之间转换。有限状态机和图灵机之间的区别是什么？图灵机有一条无限长的纸带，它有记忆，像是有一张草稿纸，可以把东西记下来。

我很喜欢一个说法：你的脑子是一个有限状态机。我们脑子里的神经元是有限的，每一次思考也是有限的。这有点像模型：模型能力很强，但它 predict next token 时的计算量也是有限的，就是那次推理所激活的所有参数。Manuel Blum 给研究生的建议里说：你是一个 finite-state automaton，是一台有限状态机；但当你有 paper and pencil 的时候，你就是一台 Turing machine。你的计算能力会得到跨越式的增长。

这是为了启发你们把想法记下来。一边思考，一边记录，可以随时回看自己的思考。随着时间越来越长，你记的东西越来越多，知识就会积累。今天的 chain-of-thought，也就是往后输出思维链的模型，做的就是这件事。它直接把模型的上下文当作 paper and pencil，当成纸和笔。当然，这个纸和笔有缺陷：它只能往后写，是 append-only，不能擦除。它依靠模型的注意力把写错的东西忽略掉。这也许有一天能改变，但无论如何，模型学会了利用它的上下文。

如果遇到“1+1 等于几”这种很简单的问题，它的 next token 马上就会告诉你是 2。但如果遇到一个很难的问题，它会像人一样说：这个问题有点难，我要先想一想；为了解决它，可以先尝试什么。它理解自己可能无法立即解决这个问题，可能需要把思考过程写下来，直到把可能正确、也可能错误的解完整写出来。一旦解答写出来，它就可以判定解答对不对，然后继续往后走。

这就是现在 chain-of-thought 模型做的事。它用 token 数量换取思考。它可以直接回答，但直接回答就有错误的风险。最早的 ChatGPT 没有思维链，就是这样。它被调成了一个“人类的舔狗”，人类不管说什么，它都一定要给出一个东西，才可能让人满意。训练时，如果人类问它一个问题，它不回答，人类一定给低分；如果它随便给一个回答，就有概率是对的。答错了当然是低分，答对了就是高分。所以幻觉就是这么来的：它无论如何都一定要给你一个东西。

现在带 chain of thought 的模型有了强化学习，它知道必须给一个正确答案，因为答错的惩罚很大。于是 AI 真的会像人一样一步一步逼近目标，这就是 test-time scaling。和我们每次用 pi 的 session 上课时看到的一样。

我举几个例子。这些例子其实不在模型的训练数据中，还挺好玩。我让它用中文写一首押韵的藏头诗，藏头本身是一串 nonsense；还要求它讲一个和动物相关的故事，并且让“二零二六九月一日”这八个字分别按顺序出现在八句里。这是个 nonsense 任务。如果高三期末考试出这种题，你第一眼就会骂出题老师，但模型不会，它会照单全收。

它会开始尝试，先想韵脚。因为它知道自己一把写出来的东西一定有可能是错的，但它可以先写一个。写出来以后，它的 next-token prediction 足以判定这个东西写得对不对；如果不对，它再想办法改；如果试了很久仍然不行，就从头推，换一个韵脚。它在不断验证。最后的结果相当不错，虽然品味上可能不完美，但通过这样的任务，可以很清楚地看到它遵循指令的过程。这就像把它的大脑拿出来做核磁共振，能看到它思维的偏好。

课件上带星的内容都是 AI slop，也就是 AI 补充的东西。我还是用了一些 prompt，试图让 AI 味稍微轻一点，但无论如何，这些是 AI 生成的。GPT 换了一个韵脚，而且没有把“二零二六九月一日”完全对齐在同一列，但它的指令执行仍然非常好。

强化训练里这样的东西相对少。模型训练用的绝大部分应该是代码、数学题这些有明确反馈的东西，结果它在这个任务上直接把人类“杀死”了。这也很好玩：如果高考遇到这样的题，让你写一句 18 个字的话，所有字都要求相同的偏旁或部首，你会马上想骂出题人。我们也知道，模型对空间结构的感知非常差，通常需要视觉模型。但这样一个文本模型，依然可以强行通过思维链完成。它先枚举字，选择三点水，然后写出“江湖游泳渡河，波涛汹涌，泪流满溢，洗涤污泥”。写得还可以。它后面继续写的内容甚至还挺有故事感。

但我觉得，人类在这种任务上还是有更强的天赋。人类的群体智慧给出过更有意思的答案，在做这件事上还是 a lot better。当然，也许你可以通过让 AI 更多地收束 spec 来改进结果，但这已经是一个非常困难的 spec，AI 仍然能做到。

还有可能是世界级的任务：你们已经知道《施氏食狮史》和《季姬击鸡记》，它们所有字都用同一个音。我竟然发现 GPT-5.6 依然能做到。虽然它的故事性和这种千古流传的作品还有一定差距，但这个差距依然可以缩小。它能写出一个，就意味着我可以引导它写出一万个，然后在那一万个里再微调，有可能达到接近千古流传作品的水平。

所以，chain of thought 在数学和编程上训练，却得到了一个非常意外的效果。你们可以看到，写 prompt 最重要的是 verifier。今天模型的能力已经非常强，如果能给模型一个非常明确的 verifier，就像前面三个任务一样，再加上一个足够强的模型，那么不管是编程任务还是教学任务，都有可能做得很好。

当然，教学任务是最难的，因为它很难给出 verifier。我经常说，我的数字人切片翻车了：做了第一个切片，第二个切片却一直做不好。无论怎么调，我都很难定义“这个东西要好”，而且“好”是多方面的。首先 AI 味要淡一点，这可能用我的 text-to-speech 模型就做不到，但它可能还不是本质。

我在上课时有情绪的波动和起伏。有些时候讲事实，比如一开始讲模型的上下文是怎样构成的，你们听了可能觉得都是废话，这些事情我已经知道了。这时我就给你们一个小 surprise，去 pi 里让它自己看一下上下文。我说出这句话时，对你们来说可能是意料之外、情理之中。这就是老师组织课堂时要做的事，某种程度上我是在表演。我知道这个 principle，需要把课堂内容组织成一个有起有落的 flow，但这不是一个可以 formalize 的东西。

到底什么程度需要和你们共情？我是从学生过来的，每一个人都是从学生过来的。我自带人的属性，自带人对这个世界的体验。因为有对世界的体验，所以我更懂你们，也许可以有一个更符合大家的上课节奏。但这个东西没有 verifier，不像数学和编程那样有 verifier。所以目前来说，我们还是更容易用 AI 实现有明确 verifier 的部分。在有 verifier 的事情上，你完全可以认为 AI 已经超越了大部分人做这件事的极限。所以我们更多的是要和 AI 协作，做好手头的任务，或者把模型当成我们能力的一个非常重要的放大器。

思维链带来的这种指令遵循能力，还可以往深里想。模型每输出一个 token，现代模型的 self-attention，也就是注意力机制，和人还是很像的。它有一层层叠起来的 Transformer 注意力。当它要输出一个 token 时，会看到过去的某些 token。为了输出这个 token，过去某些 token 会特别引起注意，有些 token 就可能没那么受到注意。

我举个例子。假如我在前面的 system prompt 或 `AGENTS.md` 里写了“用中文回答”，现在又在 user prompt 里要求“帮我实现一个极品飞车”，agent 就会开始写代码。在写代码时，它的注意力会倾向于已经写过的代码和当前需求；相对而言，“总结时用中文回答”这句话得到的注意力会下降。

当然，这是模型训练带来的 magic。整个上下文是一个非常高维、很糟糕的表示，但里面存在低维结构，注意力机制能够把它捞出来。这意味着思维链中的每一个 token 都会注意到过去的某一部分。随着输出阶段变化，比如代码写完、需要总结时，模型会像人一样“喘一口气”，注意力也随之变化。

人集中做一件事时也是这样。比如化简数学算式时，所有注意力都在算式上；化简完成、停下来调整时，注意力就变了。模型写完一段代码后，也可能重新注意到用户还要求用中文，或者还要求做另一件事。输出进入不同阶段时，注意力会变化。这就是模型训练希望收敛到的结果：在正确的时候注意到正确的东西。

思维链不断向前走，模型就会在不同时刻注意到上下文的不同部分，最终在一定程度上满足上下文里的所有指令。它可能会犯错：专注于当前任务时，向后输出了一些不满足要求的内容；但当它停下来时，注意力就可能同时看到当前的错误输出和过去的要求，于是发现“我错了，要纠正一下”。所以，当你真的让 AI 写藏头诗时，会看到它不断纠错。哪怕上下文 scale 到 100 万 token，它依然能够保持一定程度的注意力。

当然，指令越多，给模型的压力也越大。上下文是一种会抢夺注意力的资源。早期的 ChatGPT 3.5、GPT-4 遵循指令的能力实在太差，所以网上出现了很多 prompt engineering guide，告诉你要写“你是一个专家”，还要详细描述是哪一种专家。这些很长的提示词某种程度上是在 hack 模型的 self-attention：当注意力看到“你是一个什么专家”，模型就会假装成那个专家来说话。

但从 GPT-5 时代开始，chain of thought 模型已经训练出来，也知道怎样收敛到好的思维链，所以不再需要那种奇怪的提示词。你只需要把明确的 verifier 写在上下文里，模型就被训练成一定要看到它，并产生一种很强的执念，反复检查 verifier、确认要求是否解决。

这是因为模型在训练时会受到惩罚。只要有任何指令没有遵循，verifier 就能发现模型没有做完，于是给它惩罚。不断训练之后，它就像真正的做题家，会不断核对上下文里的各种指令。这也带来了一些很有趣的后果。

比如写前端时，我们很自然会说：“要白色背景，不要半透明效果。”前面是主要要求，后面是补充解释。AI 当然会照做，因为这是一个有明确 verifier 的指令：可以检查有没有玻璃效果、背景是不是白色。甚至在 prompt 比较严格时，例如要求每做一个设计都截图并用视觉模型检验，它也真的会照做。

但它做完以后，可能会在代码后写一条注释：“白色背景（不要半透明效果）。”这能看出模型在强化学习时知道这件事非常重要，却没有完全转过弯来，不明白这是人提出的设计要求，而不是需要原样写进注释的文字。模型在共情方面，因为后训练的强化学习，确实还稍微差一点，所以有时会让人觉得它不说人话。

这里仍然存在 trade-off。为了禁止这种情况，我可以在 `AGENTS.md` 里描述注释应该怎样写，或者写一个 skill，规定生成注释时的行为；但这些额外内容又会污染上下文。所以这是一个权衡。到目前为止，我认为还没有一个通用方案能够解决所有问题。

大家可能觉得网上有这么多 skills，随便拿一个过来即可。拿来的东西第一次用时确实会有改进，下一次却可能仍然不够好，于是你就会上手修改，逐渐陷入某种泥潭。我的建议是，当你发现自己进入泥潭时，还是要回到亲自给指令、亲自想清楚问题，也就是回到模型的 chain of thought 和注意力机制怎样工作。根据模型的行为，大致判断它注意到了什么、得到了什么结果，做一个不严格的可解释性分析，然后自己写 prompt。后面还会有很多这样的案例。

关于上下文工程，我来讲一两个具体案例。如果你想把一篇论文放进上下文里并阅读它，可以把 PDF 放到临时目录，避免自己的 `AGENTS.md` 等内容污染它。这里我用的是我们最近一篇论文的 journal extension，并故意换成了匿名版本。然后向 agent 输入：“我想读一读 `paper.pdf`，帮我做个总结。”这应该是大家最常见的方式。

根据刚才关于 self-attention 的推论，这样读论文会有什么问题？每次做 next-token prediction 时，注意力都会看向之前的内容，而论文是一种逻辑非常自洽、经过反复修改的东西。假设它不是 AI slop，那么它在上下文里的注意力污染极强：文中说 A，所以 B，所以 C，所以 D，所有内容环环相扣。模型很容易接受这些看起来正确的论述，并顺着它们继续生成。

因此，你让 AI 总结论文时，得到的基本都是作者的观点。这不限于论文。任何你不太明白的项目、想读的教科书章节都会如此。比如你想学习计算机系统基础里的链接和加载，上课时没有完全看明白，模型的注意力也会被这个逻辑很强的材料污染，然后来回说材料里已有的车轱辘话。虽然这确实也是总结，但内容基本只是把原文换一种方式说出来。

AI 模型还有一种“墙头草”倾向：你说它好，它马上就说好；你说它不好，它马上就说不好，来回摇摆。即使你想纠正它，告诉它不能完全信任作者——虽然作者大概率成熟、诚实，也有可运行的 artifacts，我们不是那种论文不开源的作者——希望它进一步评估研究贡献，它仍可能绕来绕去，只揪出“实验还可以再增加一点”之类的意见。AI 最喜欢在这种不重要的点上疯狂发力。

如果真的用 GPT 来读论文，最好做交叉验证。那么，怎样抵抗一个已有材料对上下文的污染？这是我的个人经验：面对一个对象，比如一篇论文，我希望 AI 能与我对齐，站在我的立场上理解这篇 paper，而不是站在作者的立场上理解它。

例如刚才的模型开始检查文中的 stack trace 是否真实。这个例子是我自己论文里的，我不至于虚构一个不存在的例子，所以模型显然已经跑偏了。一般来说，如果我读一篇 paper，或者允许我用 AI 审稿，我会这样提示它：“我们站在人类已知知识的边界看这个问题。它不是一个完全崭新的问题，相关的已有工作是什么？问题已经解决到什么程度？这项工作试图解决哪些不同的增量问题？”

这是一个很好的 grounding：先让 AI 和我站在一个平齐的位置、达成共识。我 review paper 时会这样写 prompt。对你们来说，需要对齐的是 AI 和你自己。你们是学生，例如还不了解计算机系统基础，就应该告诉 AI：自己学到了什么程度，编程水平怎样。你可能要维护一个数据库或 memory 一样的东西，在 `AGENTS.md` 中说明自己的学习进度，然后让 AI 从这个基础出发，用你学过的知识把材料重新解释一遍。

这样，模型就可以开始找出已有工作的边界，而这些相关工作对我们很重要。比如论文做的是软件状态可视化，你要问清楚这个问题为什么值得解决，以及现有工作为什么都有无法实际使用的痛点。

再比如回到链接和加载。你可以从已有知识出发问它：“我有一个 `.cpp` 文件，也有程序可以把它变成 `.exe`，这不就结束了吗？为什么还需要链接？”这样就回到了你和 AI 能够对齐的知识点上。如果觉得一步迈得太大，还可以继续拆小。用 GPT-5.6 这样的一线模型读 paper 时，它基本能把相关知识整理得足够好；换成 Flash 模型，我可能就不会特别信任它。

在合适的上下文工程下，确实可以大幅提高 AI 和你协作时的对齐程度，它不再自说自话。你一定要把自己的知识告诉它。接下来相当于让 AI 做一步推理，而一步推理正是 AI 最擅长的。我们训练了 chain of thought，每一步都是根据过去所有事实——无论是 paper、教科书内容还是已有知识——再向后推一步。

这一步是可以 verify 的。推理最重要的就是有 verifier，就像程序能通过测试一样。虽然这里不像测试那样严格，但你相信 AI 拥有人类知识，能站在人类知识边界上向后推理，并审视这一步的合理性。

刚才模型批评了我们的实验。这类工作的实验确实很难做，这也说明人类和 AI 还是有些不同：这篇 paper 已经被接收，人类 reviewer 认为它是可以的，因为它做了一件新的、合理的事情。当然，你总可以用“实验不够好”拒绝一篇 paper，但我自己几乎不会仅仅因此拒稿。

我 reject paper，大部分是因为论文在逻辑上断开了。这可能也是我作为审稿人比较可怕的地方：审稿的时候，我站在人类的立场上看，你有没有给人类提供新的知识。当然，AI 还可以帮我找 related work。但如果你做的问题不新，方法也不行，结果也就那样，甚至逻辑链条还有问题，那就不行。

比如我昨天才 reject 了一篇 paper。因为不能透露具体内容，大概说一下：作者要做一件事情 A，A 分成 A1 和 A2。A 很重要，这没有问题。A2 是一个大家没有很好研究的东西，所以他们在 A2 上做了一个 A2'，然后介绍 A2' 有哪些特点。这是一个非常标准的 roadmap。

但它有一个很大的问题：它优化的是性能，而我估算 A1 可能占 99%，A2 占 1%。也就是说，它优化 A2 的故事本身可能成立，确实优化了 A2，实验可能也没有问题；但是放到整件事情里，这个意义不成立，因为你应该去优化 A1。即使把 A2 优化 10%，这 10% 也像 noise 一样。

如果所有东西都成立，作为一个学生作业，我觉得也挺可惜的。作者肯定是学生，老板肯定是做 A 的，然后学生可能被分到 A2，或者自己想到做一个 A2。如果这个东西做得特别漂亮，我觉得也挺好；但为了做 A2，他只是从 A1 里面搬了一些 X、Y、Z 到 A2 里，然后说 A2 的效果也可以变好一点。问题是：这些 GPT 也知道，那为什么要发一篇 paper 呢？这其实是我的 central question。把这些东西都摆到台面上，你为什么还要为此写一篇 paper？

所以我觉得，学术界的发表和评审体系很快就要崩溃了。即将读研的同学，我非常认为这个发表体系马上就要崩溃，因为 AI slop 开始大量涌入 community。如果我们用 AI 写文章、用 AI 审文章，AI 写文章时又会被上下文里的故事污染；如果它不能像我一样，通过很多轮去理解这个工作对整个世界的意义，最后就没有人读文章了，人人都用 AI 读，最终变成完全的 slop。

你看，这是 GPT-5.6 给我写的审稿意见。如果让它审稿，它会怎么做？你会发现 GPT-5.6 做得并不好。它还是非常原始地先说论文写了什么，再判断论文的 claim 是否成立。它更多是在验证论文的逻辑有没有闭合，是不是一篇 invalid paper。当然，如果每个人都用 AI 写，论文应该不会是 invalid paper，每篇都是 valid paper。但你真的要读它吗？

尤其是你们很快要进入研究生阶段、开始读论文。有一天，有人在 ICSE 或 AAAI 上发表了一篇文章，你会说这是顶会论文，决定花一个小时读一下，读完却发现是这样的东西。其实它不是不能发表；如果需要 publish，可以让它 publish，但可能不要让大家花时间去读它比较好。

这就引申出我是怎么学习的。这节课虽然讲 prompt engineering，但通过这个例子也可以告诉大家我们是怎么学习的。学习的过程就是不断扩展我的世界。所以我现在还读 paper，还在不断学习。我的学习方法是对齐过去的自己：如果我读到一篇好的 paper，哪怕是几十年前的，甚至是另一个领域的一篇博客文章或任何东西，只要觉得很有启发，我就会试图去想，为什么以前的我不知道，它落在我的哪个盲区，我缺少哪些前置知识。

首先，我心里会多一些已经知道的 fact：这个世界上还有这样一个学科。我读过很多跟 computer science 没有关系的 paper，而且很喜欢；这些是我做了 faculty 以后才读的。有一套很厚的《百年科学经典》，大概把 Nature 杂志从十九世纪开始到某个时代特别好的 paper 都收集起来了。我从中看到了很多闻所未闻的东西。

有些事情你们可能知道。比如生物有一棵家谱树，最终会追到一个共同祖先 LUCA，那么这棵家谱树是怎样算出来的？这是一个很好的问题。这里涉及一些 fact，比如线粒体是母系单遗传的，所以靠突变就可以向上追溯。这是一个很有意思的 fact；然后再看这个 fact 怎样利用一些已知的东西推导出更多东西。你的知识圈就这样不断向外生长。无论学任何东西都是这样。在 AI 的帮助下，你可以非常快地扩展自己的边界。

所以一定程度上，你们还是需要自己实践。我给你们讲没有用，讲完你们只是听了一个故事，觉得这个故事挺 fancy，然后就结束了。实践非常重要，因为只有在阅读时失败过才行。今天你去读一份资料，AI 解释了半天，你还是没有懂，这是非常正常的。有时候 AI 也要我经常纠正它：“你这样说人话。”要在多轮对话里慢慢先和它同步共识，再把完整的推理 picture 建出来。

你可以看到，我们从遵循指令、写一首藏头诗这样的短程任务开始：只要把 verifier 写清楚，任务就完成了。再往后，verifier 其实可以是非常 non-trivial 的，例如验证模型有没有按照你的思维方式重构你的逻辑，或者扩展你逻辑思维的边界。

这是我的玩法，也是我学习东西的玩法：在一个混沌状态下经历若干次三观尽毁。我觉得每位同学在这个年纪都会经历，这是你们的世界观可以重塑的时候。看完某一本书以后，你突然觉得三观尽毁，过去所有东西都重新组织了。以前知道的 fact 不会改变，但它们以一种新的方式连接起来。下一次，你就会带上这个新的理解。

这是很有意思的事情。你们有无限的时间、无限的可能性，可以把自己蒸馏成一个 skill。我说失败很重要，因为可以从失败的过程中蒸馏出越来越成熟、越来越成功的 skill。这就是我给自己蒸馏出来的、关于我自己的 skill。这一部分讲的是用好大模型遵循指令的能力。

现在已经知道怎样让模型遵循指令了，接下来就可以看怎样处理真正的 long-horizon 任务。像计算机系统基础的 PA 作业，可能这种有明确 verifier 的任务都不能算真正的 long-horizon。Long-horizon 任务多多少少带一点未知：从一个初始状态出发，可能大概有一个 intent，但 specification 和 implementation 都不太清楚，最终目标却是交付一个高质量的 implementation。

这时不应该让 AI 一口气一路向后做。模型的反馈信号来自强化学习，所以它有一种着急的执念：赶快通过 verifier 满足你的要求，然后结束。这里其实有一个平衡，因为如果它做的 planning 太多、太长，就会做不完，上下文也会满，用户会不满意。所以在目前阶段，它最擅长的还是“帮我把 PA2 做了”这类任务，你也会非常开心。

这导致一个很有意思的观察。就像我刚才在 Codex 里面跑了一遍：从零开始做产品看起来不难。做一个小的 proof of concept，AI 马上就能给你一个。无论是个人主页还是产品，你们应该都试过。比如刚才那个《极品飞车》，one-shot 说“给我一个《极品飞车》”，然后真的就能跑了。

但是，当你继续维护它，一个功能、一个功能地加，你会观察到 AI 从某个时间点开始翻车。随着复杂度到达某个点，它的 cost 会越来越大。这在软件工程里已经发生过无数次，《人月神话》讲的就是这件事。

但这里有一个悖论：在大型复杂软件系统里面，AI 反而像砍瓜切菜一样。我觉得 hack 这种比较大的系统，比如 Linux 内核，现在的内核已经不同于我刚接触时的内核了。我以前上操作系统课会说，我很幸运，在零几年的 Linux 2.6，甚至 2.6.2x 时代接触了 Linux 内核，那个时候源代码我还看得懂。今天打开 Linux 内核源代码，立刻就会被劝退。

比如你要学文件系统，想看文件是怎么打开的，第一个就是函数调用，点进去又是一个函数调用，再点进去还是函数调用。点了十层以后，最后只是一个 `x = y`，你马上就崩溃了。大型软件系统经过长时间演化，为了能够继续维护，被迫变成了现在这个样子，结果却恰好让 AI 在大型复杂软件系统里游刃有余。

为什么？这跟刚才说的上下文污染正好相反。一篇论文放进上下文以后，可能把整个上下文都扭过去；但如果上下文是人类维护的、特别高质量的代码，模型会迅速看到里面那些好的东西，照着写、照着学。它的注意力也能发现：我要写的这个功能，很可能在内核里已经有几个地方实现过类似版本。它强大的注意力机制能马上找到那些地方怎样实现、应该调用哪个 helper、按照什么顺序上锁。

这些对人类来说都是巨大的心智负担，尤其当你不了解那个 subsystem 时，根本不知道该上什么锁。但 self-attention 可以在加载几十个文件以后发现：“这三个地方都是这样写的，我把这三个组合起来就可以了。”

所以，越强的系统越是如此，比如 Linux 内核。以前我们 hack Android Runtime、修改 JIT 编译器，是非常痛苦的事情。在我手上，因为改编译器而“死掉”的同学——也就是最终决定不再做这个方向的同学——不在少数。他们觉得这实在太恐怖，放弃了，不愿意再写这样的代码。但 AI 特别擅长这种任务；反而让它做一个小游戏，就可能翻车，非常有意思。

这就是 prompt engineering、上下文工程，都是上下文和今天的模型结构带来的，有一条逻辑推理关系。随着新一代模型发布，我今天上课讲的所有东西可能又没有用了。然后我们再去想新模型怎样训练、它的 personality 是什么、我们应该怎样更好地和它相处。

但我觉得有一点基本不会变：模型不会开倒车。无论是什么模型，在大型、复杂、维护良好的软件系统里，它永远可以看到该看到的东西，并且把事情做对。因为模型遵循指令的能力不会倒退，这一点还是可以相信它的。

所以我有一个歪招，但还没有实验过。我觉得这可能是一个比较好的 research……

我们有没有可能收集人类经验？比如在人类历史上最好的二十个项目中，或在每一个领域找到最好的十个或二十个项目，然后把它们好的设计经验全部提取出来。你想，那不就是我第一节课拿的《A Philosophy of Software Design》吗？那里面就是人提炼出来的经验：类结构应该怎么写，什么时候应该封装，什么时候应该做成继承关系。它们都是从系统里总结出来的“碎碎念”：这样写符合需求，所以是好的。

如果我们能把这些切片切出来，甚至直接以“污染上下文”的形式，先把一个和你的需求相近的好代码放进来，然后再放入需求。你就赌 self-attention 终于能在某一个 token 上看到：我实际上要满足的是这个需求，而不是原样复制那份代码。虽然它会污染上下文，但也会把好的经验带过来。这样是不是可以让 AI slop 稍微延缓，更有可能做出一个可以长期维护的东西？我不知道。

也许还需要更好的微调。比如，不要把项目的所有代码都放进去，而是像《A Philosophy of Software Design》一样精简、总结，把里面好的模式提取出来，以文档的形式放进来。但这也没有那么容易，因为不同的设计会打架。软件可以设计成完全松耦合的消息发送方式，也可以另外设计一个统一的 gateway，把所有函数统一在里面，然后查表。这两种设计不能同时存在，只能选一个。

也许我们需要一个更好的方法：把好几个软件的设计都放进来，然后由 AI 多轮迭代，收敛到一个好的结构，放到我们的代码库里。我觉得这可能是一个还不错、而且比较新的方向。它比刚才看到的那种“我有 A 问题，分成 A1 和 A2，然后在 A2 里做排列组合”的东西看起来更有趣一些。

这节课的核心观点是：我们今天还没有那种有超能力的 AI。你还是需要有概念，知道上下文里有什么，以及上下文里的每一个东西会对 AI 产生什么结果。唯一的途径是，第一，你对自己玩的东西要有概念。你还是得学处理器、操作系统、编译器、数据库，这里有很多设计的智慧，只是学习方法会变，你会用更高效的方法来学。

理解了上下文以后，我们会用一个学期来解释，怎样用软件工程里各种各样的方法给出一个正确的指令，去监控 AI 运行；怎样给 AI 好的 verifier，什么叫好的 verifier。今天我只是提到，你要在上下文里放进 verifier。至于什么是好的 verifier，你们可以有自己的想法。我今天只有一些比较松散的想法。

今天我们还是需要把模型引导到自己认为合适的位置上。但这已经比我组一个工程团队、雇很多人，然后和他们“拉通对齐”这种互联网黑话要简单。你不需要模型非常聪明，它已经见过那些知识。你只需要把正确、精炼的提示词放在上下文里，让这个提示词一直能被看到，把模型往那个方向引导就可以了。

我这里有一个很好玩的故事，是“AI 没有超能力”的非常典型的案例。我们要做一个研究项目，大概是做符号执行引擎的优化。你不需要知道这是什么，大概来说，我们要写一个程序，自动分析、证明或验证一个不算很大的程序的正确性。现在这个东西的执行效率比较低，所以我们希望提出一些有效的优化。这也是一个合理的、incremental 的、适合学生做的题目。

我们有一个原始 idea，大概是用某种方式可能会有效。但有些东西是 open 的，比如到底怎么做、什么东西有效，可以从这里开展一个 research。那位同学很开心，他认为这个 idea 有道理，GPT-5.6-sol 也认为这个 idea 有道理，看起来确实不错。然后他就开始跑，跑了非常多 token。

按照那位同学的说法，GPT 不断地给我反馈，但我无法验证它给我的反馈是正确还是不正确。当它给我 negative result 时，我也不知道应该怎样打破。这份总结本身就是 GPT-5.6 生成的。它的错误犯在一句话上：上下文里有一个地方没有做好，就把整个方向引导错了，模型成了一个 reward hacker。

有一个需求说，这位同学想证明 A 方法是有用的。GPT 看到这句话，就忘记了我们有一个更大的 research big picture。作为审稿人，我是站在人类的角度和立场上评审这篇论文的；而我们站在构建者的立场上，没有办法从结论反过来。我们只能一点一点地从小处开始，证明这个方法有用。

模型就是在这一步做错了。因为有那样一句 prompt，它太想证明这个 idea 有用，于是构造了很多小 benchmark，在小 benchmark 上做一些微小的改动，试图得到一些正面或负面的结论。但这些结论对整个问题是没有用的，它犯了一个方法上的错误。

我们后来纠正了：应该从一些真实的工具和 state-of-the-art 算法开始做 benchmark。哪怕要跑几个小时，直到 timeout，timeout 之前产生的搜索路径对我们来说也非常有价值。它揭示了什么样的程序结构对于现有的探索方法是不好的。这是一个还挺好玩的 research failure，它告诉你：今天人还是有用的。

我们没有办法把所有事情都交给 AI，但与此同时，我们的工作方式可能也要发生变化。第一，这些知识很重要。如果你对操作系统和编译器没有概念，就提不出正确的问题，找不到正确的引导方向。如果对人类知识没有概念，也很难引导它解决一个 open question。

但我也发现，和 AI 合作时，有些东西发生了变化。一般来说，如果我盯着 Codex 的 session，它一旦跑偏，我就立即纠正，可以更快地完成任务。比如我今天要在教务系统上做某件事，如果我及时纠正它，只把自己的领域知识注入进去，总体上可能会完成得更快。但如果我浪费更多 token，给它更多时间，它一般也能完成。

这里就有一个 trade-off。每个同学的时间和精力都是有限的，都应该思考，要把宝贵的精力用在怎样处理 AI 上。我发现自己有一个问题：纠正 AI 是一件会产生多巴胺的事。它给我一种感觉：虽然 AI 很强，我好像还是比 AI 有一点用。它会产生一种非常微妙的心理安慰。

而如果我直接开一个 YOLO mode，然后等我回来，也不看历史，反正它搞定了，我只验收一下；它真的搞定了，我就不再看。这可能在非常长的时间里都会成为同学们工作的一种常态。你们只有把 AI 用在合适的地方，把自己的时间留给收益最大的事情。这个时间是不能省的。对一个不知道的东西，把它弄明白，这几乎是你作为学生要花百分之百时间做的事情。剩下的事，比如你已经知道怎么干，AI 也能把它干好，就放手让它干。

在 pre-AI 时代，大家就已经说不要“假努力”。自我感动的努力没有用，要有有效的努力。在 AI 时代，这个效果的差距会拉得更大。你每一秒钟的假努力，如果有一个 peer 在真努力，都会让你损失非常大。这是我自己的一点小心得。

你们也会发现，随着指令上下文增长，指令遵循能力确实会下降。但现在的模型有一个很有意思的特点：一般来说，最后的 prompt，也就是留在最后的指令，还是可以遵循的。对前面的指令，尤其是上下文中间的指令，它可能不遵循。所以它干活还是很好用的，因为一般最后一个短窗口就是一个具体任务：帮我把什么东西修了。它确实还是可以把这件事做完，所以模型仍然非常值得使用。

如果你真正想做一个 long-horizon 的、非常难的任务，它不是解决一个问题，而是在不确定性中探索，那么 chain of thought 其实就解决不了。Chain of thought 能解决的，是一个有 verifier、可以确定地一直往后走，最终解决的问题。但如果你让它考虑几种方案，判断哪个方案最好，它很有可能给你一个不是最好的方案。

为什么？因为模型已经被训练成“舔狗”了。它完成任务才有奖励，不完成任务就没有奖励，所以它会给你一个有限的方案。就像 P 和 NP 是两个 complexity class，甚至还有更大的 complexity class，有整个 polynomial hierarchy。对 NP 问题，验证一个解比较容易，是 P 的；但找到那个满足条件的解很难。比如找一条 Hamiltonian path，给你一条路径，验证它是不是 Hamiltonian path 很容易；但想要找到一条满足条件的路径，是 NP-complete 的。3-SAT 也是这样的问题。

搜索是困难的，验证是容易的。模型为了完成任务，势必只能做有限的搜索。这有点像你在考场上时间不多了，无论如何都要把考试题写完。马上要交卷了，写了的分数就比不写高，所以你一定要写点什么。这个时候，你就可以用一个“算力换智力”的循环。

我举个例子。你们这一代人有很多同学叫“子涵”吗？好像还没有。比你们再小五岁的一个班里，可能有五个甚至十个子涵，现在叫子涵的反而少多了。AI 给我的名字还是很好的，它知道要去《诗经》里找，现在模型的品味确实提升了。但你还是不敢用，因为你用 DeepSeek 起名字，别人也用 DeepSeek 起名字，你就会成为“AI 时代的子涵”。大家都用 DeepSeek 起名字，DeepSeek 也都起了同样的名字。

我的经验是，如果你真正要做一个非常 long-horizon 的任务，就需要一个系统性的调研过程，和你们上科研实践课时学的那套很像。进入一个科研领域，第一件事是文献调研，穷尽与这个问题相关的所有文献。AI 想要快速完成任务时，暂时还不会花这么大的代价。

但名字是可以枚举的。你可以先选音，把不好的音筛掉；选完音，再用 subagent 一个个检查字。比如你喜欢《诗经》，可以选一个《诗经》里的词。这样就实现了算力换智力。一个开放问题有非常大的空间，如果直接让 AI 用 next token 的方式解决，它会给你一个由它的偏见带来的结果。但如果你把空间分割成很多个 disjoint 的部分，每个部分就会变成一个有 verifier、更明确的问题。有更多算力，你就有更大的智力。但这有一个缺点：烧 token，烧得头疼。

这就涉及我对人类社会的一个很有趣的理解：世界很大，人很小。每个人的品味都不一样，因为我们带着很大的 bias；我们在不同的城市、不同的教育背景和生活圈里长大。Rich Sutton 有一个 big world hypothesis：我们就是学不到这个世界上所有的东西。但正因为我们带着这些 bias，才有了一加一大于二，我们才能形成最大的群体智能，在一起实现智能。

但这会带来一个未来的危机。我不知道，先把这个问题抛出来：如果真正有价值的问题可以用算力换智力，可能会发生什么样残酷的现实？有一类人可以获得无限的计算资源，他就有无限的智力；他可以砌一堵墙，墙里的人有智力，是我的朋友，墙外的人是普通人。

假设计算机 AI 模型比人类的智力更高效，那么墙外的人就变成动物园里的猴子，让他们自生自灭。他们无论如何也不可能赶上墙里的人产生智力的速度。墙里是超人，墙外是动物世界。大家已经快要走到 AI 的这个关键奇点，我们可能需要思考怎样防止这件事到来。
