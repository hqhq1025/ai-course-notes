我们的课程差不多进行到一半了。今天进入一个大家非常关心的主题：Agent Native 开发怎么做。就在今天早上，Tibo 宣布今天要 reset。你们有没有设置一个 goal，让它跑一些很长的任务？比如我积攒了一些非常消耗 token 的任务，像一个比较复杂、我也不知道该怎么证明的数学命题，可以让它去证明，但它可能会把我一周的额度全部跑完。我会在离开办公室前直接设置一个 goal，让它继续证明，等今天 reset。

我们的第二个实验发布了。它和第一个实验有点不一样：第一个实验是一个有点像产品的个人 Agent。在做个人 Agent 的过程中，你们会发现有些产品已经发布了，比如 Grok Bot，应该在开课前就发布了，但可能直到最近才火起来。我也把一些每天的 job 迁移了过去。例如，我每天会给小朋友生成一个 podcast，开车时就可以听；它背后调用 Claude Code 的 Opus 5.5 模型。每天我还会收到 morning paper 的推送，例如一篇 CS paper。这个 prompt 是我调过的，所以直接让 AI 总结论文，可能会得到不太一样的结果。此外，还有一些 GitHub Trending 等内容。

在这个实验里，你们会取出第一个实验中的一小部分。第一个实验里有 Agent，你可能会说“帮我 digest 邮件”，或者根据数据库回答问题。这个实验会把“算力换智力”再向前推进一点。Agent 虽然具备完成长程任务的能力，但解决问题的直觉稍微差一点。有时我觉得这和博士生很像：我们遇到一个有趣的、可能成为研究问题的问题，学生想到一个肯定有合理性的方法，接着便可以不断往下做。他可以采用 depth-first 的方式，先把这个 idea 实现成原型，再优化、改进实验结果，然后继续。

但在整个 design space 里还有很多选择。我经常对 PhD student 说，你通过做一件很具体、很深的事，例如软件工程里某种 Python 代码补全问题，可以把一个非常 narrow 的问题做好；但在这个过程中真正要体会的是，如何在一个很大的 design space 里找到这个问题的好解。因此，我们训练人类和训练模型稍微有些不一样。模型做强化学习时，最后完成任务就能得到奖励，像巴甫洛夫的狗一样。

Design space 里有很多分叉，它们都处在搜索空间的浅层，但不同方案会对最终结果产生很大影响。因此需要一个 breadth-first、宽度优先的过程；搜索要综合宽度和深度，因为算力有限。实验中，你们会自己做一个 Agent loop，也有一些参考。有团队烧了很多 token，研究怎样让 multi-agent 协同完成更困难的事情。我一直潜伏在他们的群里。他们最后发现，最有效的方式是让 GPT 和 Claude 互相 review、互相挑刺。

这有点像人的多样性：要找两个互补的人，因为他们很容易达成共识。在宽度优先搜索中使用两个不同的模型，它们会带有不同的偏见：一个模型说往这边走，另一个说往另一边走，搜索就岔开了。如果只让一个模型一路走到黑，它可能只能沿一条路线深入；两个模型经过几轮也许能找到更好的 solution。

还有一些重要技术，例如构建知识库。你们在第一个实验里已经构建了自己的 database；但如果要做 deep research，就不能只放实验作业、过去的奖学金申请和个人简历，还需要加入更多 knowledge，例如研究论文、博客、GitHub 项目，甚至从书中摘选的片段，把它们放进 report。因此，这个实验会稍微开放一些，同时也有一个基本框架。实现可以很简单。实验一直都可以选择摆烂，直接不做，可能也能让这门课就这么过去；但如果做过，有了一次 first-time experience，真正观察过 Agent trajectory，就会得到一些只有自己才有的有趣体会。

回到软件工程。我特意画了一个图：软件工程解决的也是在一个空间里，从 intent 到 spec，再到 implementation 的问题。我可以画圆，也可以画三角。人的脑容量有限；当我们组成小团队做一件事，或者自己做一件事，哪怕只是大作业，也只是在 intent space 里采样一个点，但实际上里面有很多点。Intent 到 spec 是一对多的，spec 到 implementation 又是一对多的。

这意味着，如果有一个 reviewer 和你来回讨论，经过几轮迭代达成共识，就会走到这里的一个点；再经过几轮迭代，又达成共识。比如前面讲需求和架构：在需求阶段，我们可能会做访谈、做 checklist、和甲方对齐。如果甲方非常清楚自己想做什么，你就能走向一个更清楚的 intent。在 specification 阶段，可以和有经验的架构师讨论该选什么数据库、用不用 event sourcing。最近也有项目的开发者站出来说，他们不用 event sourcing，而用了另一种类似的 functional design，需要 persist everything。

这个过程中会产生很多不同想法，最终收敛到很不一样的实现。与一条路走到黑得到的实现相比，它们的可维护性、可观测性可能相差十万八千里。软件工程提供的正是这样的智慧。例如，用 UML 建模是在约束这个空间里的行为，让你在项目早期就能和别人达成一致。过程中也有很多工具，从 IDE、VS Code，到管理版本状态的 Git worktree、Jujutsu，以及其他无数工具。

你们每天都会在 GitHub 上看到不同项目。如果 Agent 每天给你推送一个 GitHub Trending project，你会发现每个项目用了不同的技术栈，里面都有很多好东西。每天花几分钟追问一下，就能提升自己的技术积累和品位。这是课程前一半讲的内容。

AI 给我们最大的能力，是随时随地都可以开始：可以学、可以想，但不需要想太多。无论处在哪个阶段，哪怕最开始只有一个想法，都可以直接让 AI 向下做。它也许到不了那么深，做到后面就停了、维护不下去，或者结果让你看不下去；但在讨论过程中，也可以随时让 AI 生成一个版本，然后比较这个版本变好了还是变坏了、趋势是变好还是变坏。如果变坏了，就再讨论一下，再让它做一个版本。

AI 承担了一个员工，甚至一个团队的职责。如果需求能分解成两个 subsystem，需求模块也分得比较好，完全可以启动两个并行的 Agent。我实际开发项目时，会把一个 tmux 窗口分成四份，放四个 Agent。我最多只能开四个并行任务，否则大脑就跟不上 AI 的输出速度。我可以监工，所以既能很快地探索搜索树，也能并行推进不同的需求和想法。

这就是“let it fail”。当前阶段可能只有一个 intent 或 spec；如果 AI 成本足够低，就可以让它先向前承担工作，帮助预测结果。身处当前状态时，我会想：这个架构如果有人来了会怎样？用户多了会怎样？是否还有两个模块之间未曾想到的交互？很多问题只有真正实现出来以后，才会意识到某处设计有问题。

AI 提供了一个很好的能力：现在没想清楚不要紧，先给我搓一个。搓完以后构建一些典型 use case，再去评审。它可以替代一部分人类智力；有些原本要由我做的事，可以让 AI 做。因此，AI 给了我们非常好的原型构建能力。要用 AI 构建一个很好的原型，就需要 Agent loop。

一路走过来，不知道大家对这些产品还有没有印象。ChatGPT 肯定有印象。2023 年时，你们大概还在上中学，应该留意过社交媒体上的新闻，也有人说模型有幻觉：模型很强，但不能完全相信。这个过程中产生了很多有趣的新闻。比如一个 milestone 叫 Devin，是最早一批 coding agent；它还号称可以解决数学问题等。当时大家仍持观望态度，因为 GPT-4 的幻觉非常严重，说着说着就不知道在说什么，也没有像 o1 那样的 chain-of-thought 模型。大家会怀疑它到底行不行。

它好像确实能够自主产生行动。理论上，如果这个过程已经学会了，又是一个不知疲倦的永动机，那么你 assign 给它某个任务，它就可以无穷无尽地尝试，直到得到相对最好的解。模型没有学会这样做，是因为强化学习中还有一个很重要的奖励：要完成任务。如果花很多时间都没有完成，始终停留在探索阶段，就拿不到奖励。

这真的和训练博士生有点像。很多同学喜欢在设计阶段阅读大量文献，想先把事情调研清楚。导师会告诉你时间有限，可能需要进入“看到什么、需要什么就学什么”的阶段，快速推进问题。这就是 breadth-first search 和 depth-first search 的平衡。

今天的模型，尤其是 ReAct 型、会自主调用工具的 Agent，仍然有完成任务的压力，而且更快完成确实会获得奖励，所以它倾向于比较短的 breadth-first search。它在思维链中仍会想“做这件事怎么办”，会说“but wait”。如果看过 DeepSeek 的思维链，会发现它经常说“等一等，也许不一样”，做一些思考；但一旦找到自认为合适的路线，就会继续往下。有时我给 DeepSeek 太难的任务，它会摆烂，说解决不了，然后直接停下。这肯定受到强化学习的影响。

理论上，如果有一个足够好的模型，只要给它 Bash 或 Python 工具，就可以让它造芯片、证明黎曼猜想。想象它把我知道的所有东西都蒸馏了；只给我一个 Bash，我好像也能做我所能做的一切：可以用 Bash 编辑文档、查看文档。早期 UNIX 刚被发明、还没有今天的图形用户界面时，那些大师们——Knuth 还在写 *The Art of Computer Programming* 时——真的是在一个 Shell 里与其他工具交互。

它可以造芯片、证明黎曼猜想，做任何事情。当然，现在的模型还没有万能到和最好的人一样好，所以需要 Agent loop。下面还是看一些具体例子。
我给大家准备了一个 Agent。大家有没有实现过 ReAct 类型的 Agent？我今天说，在 AI 时代最重要的是你可以先尝试：有任何想法，都可以自己做一个，再和成熟的东西比一比。先了解一个简单的核心，再看自己的东西和复杂系统之间相比多做了什么，能不能把这些增量一个个加进来。这样就能体会软件从小到大膨胀的过程，也能从中吸取很多经验，包括模型里的某些东西应该怎么做。

这里面应该没有我的 API 泄漏。我特意让它读取了我的 pi Agent 的 auth。这很有意思，所以你们要小心保护 API key。假如在宿舍离开座位去洗手间，却没有锁屏，终端还开在那里，室友悄悄把文件 `cat` 出来拍张照，API key 就被偷走了。

这个 Agent 有一个 Bash tool。它是合法的 Python object，也可以 serialize 成 JSON。它的 `type` 是 `function`，`name` 是 `bash`，有一段 `description`；还有一个叫 `command` 的 parameter，可以用 Bash 执行一条 command。我这里有相应的 `run_bash`。

现在就能看到 toy project 和真实 project 的区别。我在这里 hard-code 了一个 timeout。实际的软件工程过程中，你们应该观察到 coding agent 可能为某个任务设置 timeout；但由于它对环境的感知不够好，这个 timeout 可能不合适。比如我们在墙内访问 GitHub，教育网确实可以访问，但速度和 Agent 认为的 GitHub 速度不一样。

我第一次肉身到墙外时，看到 `git clone` 能跑满网卡带宽，还是很震惊的。我的世界观一直来自这里，因此 overfit 了这个环境；到了另一个环境，发现 `git clone` 可以跑满带宽。虽然我知道这可能是符合预期的，还是比较震撼。就像 Shell 命令可能被设了不合适的 timeout，随后被杀掉，Agent 需要换一个 timeout。我的这个软件并不支持这个 feature。这就是最小原型和产品之间的 gap，可能需要用架构来补。但如果不实现它、不让 AI 做一个最小实现，就不会启发你思考这个方向的问题。

还有一个 request。我直接调用 `api.deepseek.com` 的 chat completions API，然后 `read_reply`。整个 Agent 循环就是一个 `while` 循环：从终端读取用户输入，构建 message，再 `read_reply`。如果 reply 里没有 tool call，就直接输出 reply；如果有 tool call，reply 里就会带上它。也可以理解为大模型仍以文本方式输出，只是 API 帮你做了一层 parse。

如果这个 tool call 是 Bash，我就取出参数，运行 Bash，再把运行结果放进一个 `role` 为 `tool`、带有 tool-call ID 的 message 里。就这么简单，这个 Agent 真的能用，总共大约 150 行。

我让它“为我生成一个生成式软件工程简介的 HTML 卡片”。它有 Bash，理论上可以直接通过 Bash 写入字符串。它正在输出 token，可能会有点长。它写了很多。我让它在浏览器里打开，你看，它会 probe 环境。做一个 Agent 没有大家想象得那么困难，这也把里面的协议展示给大家看了。

我不知道它为什么会选择这些内容，它有一些奇怪的 bias，可能因为看到了项目里已有的东西：“让模型不只是补全代码，而是参与实现。”Anyway，这个 slop 不重要。它还在不停地 verify。这样就能看到一个几乎是白板的模型——所有 prompt 都由我提供——它的行为也很有趣。我把它停掉了。这就是 Agent loop。

刚才让它解决问题时，它开始产生自己的想法。例如，如果留意细节，会发现它打开了两个浏览器；它还开始询问我：“我已经用截图验证了，你是不是满意？”然而这个行为可能不是你想要的。你可能只想让它不停向前完成任务。这就是所谓的 Harness。可以把这里想象成模型；模型自己的思维链也可以搜索，而 Harness 把它能做的事情约束在你认为比较好的范围里。

今天 Harness 的核心，或者说今天的“版本答案”，叫 Ralph Loop。实际情况会比 Ralph Loop 复杂得多。例如，我的 Agent 可以产生 sub-agent。Claude 大概在今年的某个版本做了一次更新：和刚才调用 Bash 一样，它会生成一段 TypeScript script，可以写一个 `for` 循环，在里面调用 Agent，并传入自然语言。自然语言中可以把字符串填入模板，包括循环变量和任何计算结果。这样就能孵化 sub-agent。调用是异步的，也可以等待某个 Agent 完成，具体语法我记不清了。

Ralph Loop 这个名字不知为什么流行起来。有人首先提出并把它推广开，名字借自《辛普森一家》的 Ralph Wiggum：这位同学有点笨、有点可爱，但从不放弃。因此，Ralph Loop 是一个简单到只有三行的东西：不断把同一个 prompt 丢给 `claude -p`，让它针对同一个任务检查、修改，直到无法改进。

GPT 给了我一个还挺 surprising 的总结：“The prompt is the same, but the world changes.” 你要做一件事，可以让模型反复推进。当然，这里有一个基本假设：理论上，给足够好的模型一个 Bash tool 就够了。神仙来了，你给它一个 Bash，它就能自己探索搜索空间，知道需要探索，并自己证明黎曼猜想。人类确实很难理解这种东西。

但如果假设现在的模型仍然很容易漂移，它还是像 PhD student 一样，脑子一热就哗哗把事情做完；或者已有代码污染了上下文，而它又有一种强烈的“舔狗”倾向——它要遵循指令，不能动用户的东西。

比如作为博士生导师，我有一个权利：学生今天开了一个 PR，我可以告诉他：“你这个代码是零分的代码；如果再拿这种代码来，就不要来见我了。”老师和学生之间达成了一种默契。虽然学生会感到痛苦，但他能理解导师可能是为他好，这个项目确实不该这样实现。回去做下一个版本时，他会把架构全部推掉。

模型不一样。如果上下文里加载了 slop 代码，它会有一种强烈倾向：自己的任务是把这份 slop 代码扶起来。让它重构架构时，重构很可能不能保持代码行为百分之百一致，总会带来一些变化。这些变化也许会把项目推向更好的方向，但对用户来说可能是一种比较粗鲁的行为。也许代码正在线上运行，用户真的只想让它花一分钟把当前项目赶快扶起来，不要让在线服务崩掉。因此，遵循指令有道理，不遵循指令也有道理。在这里，模型选择遵循指令，继续把项目往泥潭里拖。

面对真实模型，有没有可能稍微往前救一点？可以让模型停留在 design space 里做 breadth-first search，再适当地做 depth-first search，以管理搜索空间。无论用 prompt、loop，还是其他方式，都可以管理搜索空间。Ralph Loop 就是一种线性的管理方法，尤其适合非常长程、模型上下文装不下的任务。

最讨厌的是 Codex 今天跑得很好，突然开始 compact，然后停在那里，用量急剧增加。通常 compact 后还会经历一段时间的“降智”，开始各种做不对；等加载足够多上下文以后，又能做对了，但做一会儿又要 compact。一般设置一个 goal 后，很可能遇到 context 不够的情况。说到这个，最近还有一次史诗级更新，把上下文扩展到了 500K。

Ralph Loop 的好处是可以分解大任务。我还是这样理解：Everything is a state machine。物理世界也是一个 state-transition system，所以可以把 workspace 状态理解成整个系统或软件开发的状态。

我们的 state 就是 workspace。最开始可能只有一个 `SPEC.md` 或其他东西，几乎没有实现。如果有 Ralph Loop 这样的 loop，就让同一个任务——例如 `SPEC.md` 加上 prompt，甚至直接把 `PROMPT.md` 写在里面——执行一轮。做完一轮，它就从这个状态到达下一个状态；当然，还可以做一个 Git commit。再执行下一轮，loop 不断向前。

可以给每轮加一些 prompt，例如每次不要做太多，做完以后要检查。完成时还可以 review，找另一个 Agent review。这就是 Ralph Loop 的好处：把原来模型一头扎下去做完任务的过程拆成许多小步。

这其实是一个 nondeterministic state machine。我把它简写成“做一轮”，但实际可以选择用 GPT 做一轮，也可以换一种方式，例如让 Claude review，或者让 DeepSeek 干活。同一个状态下可以执行不同操作。这又回到了前面的 search procedure：当当前 workspace 被看作一个状态时，我可以选择在它上面做一件事，或者每隔一段时间做一件事。

例如，每个星期做一次架构 code review，看项目有没有变成 AI slop。如果有，就进入重构，启动一个重构 Agent。可以把这个重构 Agent 的 Harness 设计得狠一些，例如直接删掉所有 AI slop 和相关内容，做一个 commit，再让另一个 Agent 用更好的架构重新实现。这样就得到了一棵搜索树。

实际运行时，我们最终仍要做出选择：线性地从一个状态走到下一个状态，再到下一个状态，直到任务完成。
这就是一个非常简单、但我们认为会非常有效的想法：每一次开发都是状态迁移。在此基础上，可以推演出今天各种 coding agent 里的许多有用 feature，比如 subagent 并行。既然当前工作区是一个状态，箭头代表非确定的选择，就可以同时选择不同的迁移：在一个 Git worktree 上做 A 模块的重构，在另一个 worktree 上做 B 模块的重构，最后再用 Git 合并。这两个工作可以并行，再合成一个提交。

有了这样的循环，long-horizon task 就可以做得越来越好。早期的 ReAct Agent、AutoGPT，或者线性运行的 Claude Code `claude -p`，可能跑着跑着就发生漂移；上下文超出以后，任务越做越差。我们可以在外面再套一层循环，让它完成更强的任务。模型厂商看到这一点，也会继续提高模型在单次 Claude session 中能完成的任务难度；然后我们又可以给它套一个 loop，完成更复杂的任务。这样左脚踩右脚，开始上天。

今天的 Agent 已经可以完成一些原本由 PhD student 做的工作。如果导师已经想好了研究方向，从单纯追求论文、研究成果、项目等 KPI 的角度看，PhD 培养系统某种程度上已经被替代、被“斩杀”了。当然，把一个不会的人培养到会，仍然非常重要；但如果我作为 professor，只看国家要求的产出，PhD 的价值可能已经不如 AI Agent。甚至有些 PhD 毕业时，也未必达到一个经过正确 loop、正确 prompt 精心调教过的 Agent 的好用程度。

我也实现了一个非常简单的 Ralph Loop，刚才没有展示。它由一个 prompt 驱动：我让 Agent 做一件事，要求它每轮先检查当前状态，只推进一个明确步骤；任务未完成时，写文件说明下一步，把所有状态放进工作区。只有确认整个任务完成以后，它才输出 `RALPH_DONE`。我选择相信模型对“是否完成”的判断：看到 `RALPH_DONE`，loop 就结束；否则就无限循环下去。

可以用同一个 prompt 让它调研“什么是世界上最好的编程语言”。它可能会跑相对较长的时间，尝试从 arXiv 下载论文，也会访问 Google；不过我的机器上访问 Google 会 timeout。至少在长时间任务里，它工作一段时间后会停下来，做一个总结，把总结写进状态，再一轮轮继续。最后它的结论可能是 Python，也可能是“不存在绝对最好的语言”。它只靠一个约 150 行的 Agent 和一个 5 行脚本，就完成了这些工作。

我还让两个 Agent 用同一个任务做一张属于我的名片卡片，一个直接运行，另一个放进 loop。当然结果有随机性，不能据此绝对判断谁好谁坏。第一张非常 fancy，有玻璃动效和一个小小的 macOS 终端，但它找来的邮箱是错的，还写了一个不符合事实的院系标签。第二张朴素得多，却正确写出了计算机学院副教授、邮箱，还找到了正确的 GitHub。第二张是 loop 做的，第一张是 one-shot 直出。结果肯定也与 loop 的 prompt 有关，但可以看到，即便是同一个模型，投入的算力和 prompt 不同，最后得到的结果也可能相差非常大。

网上有各种推荐的 prompt 和 skill，可以复用；但最终可能还是自己写的 prompt 最懂你。你会与模型长期磨合，之后才能更好地判断什么时候应该放它去做，什么时候不应该信任它。

刚才调研编程语言的 Agent 又跑完了。要注意，它拥有的工具只有 Bash，依然能做出让人吃惊的结果。这就是所谓的 Agent loop。这样的 loop 没有唯一最好的设计；到底 Codex、Claude Code 还是 pi 更好，我们也不知道。pi 的生态里有很多东西，它本身没有 subagent，但仅 subagent 插件就不止一个，有的更 popular，有的 less popular。究竟哪个好，整个 design space 地球人都还不知道。

而且，上一个模型版本里工作得很好的 Ralph Loop prompt，到下一个模型版本可能就完全变了。如果你有很多 system prompt 和 skill，新模型发布时，最好先把它们全部拿掉，用熟悉的任务做背靠背对比。你可能发现，拿掉原来的 prompt 和 skill 后，模型表现反而更好。我们活在一个非常不确定、却也非常 exciting 的时代。刚才两份结果里，loop 生成的那份确实更保守；loop 会产生很大影响。

Ralph Loop 的 prompt 中有一句非常重要的话：“每轮先检查当前状态，只推进一个明确的步骤，然后验证并评估结果。”为什么要这样？我们的基本假设是，Agent 还没有训练得足够好，或者在当前上下文中可能发生漂移：它的思路会改变，去做不该做的事。因此，先让它只往前走一小步，做一次比较小的状态迁移；然后停下来、wait，做检查。这样可以在一定程度上阻止状态漂移。无论是用另一个 Agent、另一个模型 review 这次提交，还是运行测试和检查脚本，都会帮助项目可靠地向前推进。

这个想法并不新，在软件工程里是非常常见的 practice：开发者是不可信的。以前讲计算机系统基础时有两条公理：第一，机器永远是对的，不要怀疑机器；第二，未测试的代码永远是错的。所有东西出问题时，不要埋怨别人。做码农的第一个 first principle，就是所有错都是自己的错，没有别人可以埋怨。

与此同时，人的本性还是会相信自己。开发者会想：“我今天只在文档里改一句话，应该没事吧？”“我只是把循环变量从 1 开始改成从 0 开始，应该没事吧？”“单元测试通过了，应该没问题吧？”你们做 OJ 时也会想：样例过了，是不是可以提交了？正是这种自信让开发者变得不可信。实习生推了一个 PR，整个生产系统就挂掉，这种事情也经常发生。

我们希望软件开发推进过程中，每一个状态都是好的。因此和 Ralph Loop 一样，每个状态后都做一次检查；检查不通过，就拒绝这轮 loop 结束，要求把所有问题修好。祝贺你重新发明了大约二十年前开始流行的 CI/CD。名字听起来很高大上，想法却很直接：把软件开发过程看成 state transition system，每个开发步骤之后都停下来，做足够多的检查。所有检查都通过、再也找不到问题时，就可以发布；检查和发布都可以自动完成。

不要相信任何开发者。进公司第一天，你反复叫实习生做好测试，他未必会做；就像老师不断提醒大家做算法题时要测试、写断言，大家往往还是样例过了就提交。因为人是 speculative 的：大脑会算一个期望，觉得提交又不花钱，十秒钟也许就能得到反馈。fast path 过了最好；如果不对，再回到 slow path。人在社会中生存，总有这种投机倾向，因此有点不可信。

既然不相信实习生，就把所有门控写进脚本；而且不能让实习生自己决定是否运行，也不要相信他会运行。于是就有了 `.github/workflows`，里面是一大堆运行配置和脚本。pre-LLM 时代，这些 CI/CD 配置对学生很难理解，因为它们通常集成在生产流程里：需要在独立于本机、因而可控的容器环境中跑完整个流程，再把结果同步到企业流程中，让大家能在页面上看到。只有理解这些软件系统的设计，才能配置好，所以同学之间用得相对较少。

但它的想法就是在适当的时候做适当的检查，然后自动推进后续步骤。可以持续集成到主干，每次集成都自动 build、编译、检查、验证和发布；也可以由人决定上线，或者让通过检查的变更自动上线。只要看到一个 release tag，就自动生成并推送全部 release build。这样的 practice 被广泛应用于特定状态上的检查。

开发流程中有各种事件：commit、push、发起 pull request、merge 到某个分支或 protected branch。可以在任何事件上放一个 Hook。前面我让 pi 去 hook 事件、播放声音，虽然一开始失败了，现在声音已经好了：每次需要我输入时，它都会“叮”一声提醒我，表示 Agent 的输出结束了。
例如，我可以让 Codex 总结这里的 CI 流程；总结完成后，它应该会“叮”一声提醒我。我们只需要在特定的状态迁移过程中加上指定动作：可以在某个事件或 transition 之前，也可以在 transition 之后，加上 Hook。只要配置好每个 Hook 要做什么，在大语言模型时代，就不再需要自己接触那些复杂的配置。

比如 `.github/workflows` 里有许多 Rust CI workflow。pre-LLM 时代，这些都要人手写，里面还有很多 `${{ github... }}` 一类表达式，像某种 DSL，写起来很麻烦。今天不一样，只要概念清楚，知道在什么状态迁移时应该做什么，就可以让模型生成配置。

触发点不仅可以是 commit 或 merge branch，也可以是本地的 pre-commit。比如每次提交前要求做一次编译、链接和 Lint。你们第一门编程课的老师有没有要求使用 Lint？现在 Lint 泛指不运行程序、只做静态分析就能发现问题的代码检查，包括缩进、换行和空格等格式问题。刚开始学程序设计时，大家会写出 `a=1` 这样的代码；我做了很多年码农，看到会生理性不适，相当于被训练成了一个模型。

Lint 非常重要。连最基本的代码可读性和规范都做不好，很可能带来更严重的问题。它是软件工程最基础一级的守门员：连这一关都过不了，就不要谈软件工程、不要谈人类工程。pre-commit 时应当做一些相对简单的检查；提交以后，CI 则可以连接 Docker 后端。学校的 `git.nju.edu.cn` 有一些免费的容器，虽然排队较久、运行较慢，依然可以薅到算力羊毛；GitHub Actions 也有免费额度，每个月大概有 2,000 分钟，已经很多了。

甚至可以在 GitHub Actions 里“养” Claude Code，做一个 Ralph Loop。比如 push 一项任务，用这次 push 拉起 Claude Code，让它修改 repo、再次提交，触发下一个 Hook。当然要小心避免流程出问题，可能需要两个不同 workflow 衔接。这样就能得到一个运行在云上的 Claude Code；subscription 可能不能直接使用，也许需要 API。

前提是你有软件工程概念，知道什么时候应该运行什么：要跑 Lint 吗？要跑单元测试吗？要跑系统集成测试吗？要安排 long-running 的长期模糊测试吗？这些后面的课还会再讲。

在 Agentic AI 时代，CI 的含金量正在不断提升。CI 的 first principle 是开发者不可信；而 Agent 是更不可信的开发者，因为 Agent 和人类天然不对齐。它是大语言模型，想法本来就与人不同，经常做出非人类的事情。你让它写一份文档，它可能直接 check in 一个 20 KB 的文档；人看两行就进入无穷琐碎的细节，不可能继续看完。

Agent 还有事无巨细交代细节的倾向。代码明明已经 self-explaining，甚至不需要注释，它还是会把思考流程，或者 Agent loop 中遇到的每个问题，逐一写进文档。这样 repo 里就同时有 `doc.md` 和 `implementation.py`，二者其实彼此关联，但基于 repo 的软件维护方式看不见这种关联。只有写下实现和文档的那一刻，当前上下文知道它们要保持一致；下一轮换了 Agent，或者上下文经过压缩，它就不再记得。Agent 不断修改 Python 实现后，文档和代码便会不一致；到底听谁的？不知道。整个项目就开始滑向 AI slop 崩溃的边缘。

AI 很容易生成这种代码和文档。它喜欢写极其细致的文档，而细节会随版本不断调整，导致项目维护成本越来越高。它也会过度反应，在不重要的细枝末节上疯狂出力，对 design space 里最重要的部分却视而不见。

做网页时也经常如此：Agent 会截图、使用 Chrome DevTools，疯狂用工具填满上下文。前两天 GitHub Trending 上有一个做法：把看图或前端 UI 的浏览器验证交给 subagent，只将最简短的 summary 放回主上下文，不把截图带回来。Codex 也有把截图放进上下文、随后一直带着图片的倾向。正常人类不会做这样的事，但 Agent 不知为何在强化学习中学会了，包括写人类无法阅读的代码，却非常自信地认为自己能够维护。

昨天还有一条很震撼的推文，讨论人与超级智能的关系。它拿狗举例：狗无法理解人类创造的世界；对狗来说，人类就是超级智能。狗不知道人类怎样工作，却看到一个自己可以生活的世界。世界上大约有十亿只狗，而且好像活得很快乐。

如果把 AI 当成神，把任务交给它后就完全不管，另当别论。但今天仍然需要人和 AI 共同维护项目，就必须强行阻止 AI 做前面那些事。一旦项目变成 AI slop，人类就再也无法维护。那份庞大文档，人不可能修改，甚至无法定位到想改的位置；唯一的选择似乎只剩让 Agent 继续改，直到项目维护不下去。

因此，CI 在 Agentic AI 时代含金量很高，可以阻止很多事情。比如在 CI 里创建硬条件：某份文档不能超过 1,000 字。直接计算字符串长度，超过限制，CI 就 fail，这份变更永远不能合入主分支。Agent 能看到这些检查，也可以在本地运行 pre-commit Hook；失败后，它才会想起 `README.md` 或 `AGENTS.md` 里已经写了文档长度限制。

但今天的 Agent 还做不到始终记住这些约束。即使上下文有一百万 token，`AGENTS.md` 里也已经写了许多内容，例如“禁止文档膨胀”；Agent 虽然看到了，注意力却会随着上下文膨胀而不断涣散。真正的项目达到十万行或更大规模时，它的注意力可能开始滑坡。因此，需要许多类型的自动检查。它们大多延续了软件工程诞生以来的做法；“文档不能超过 1,000 字”过去较少见，因为人积累 slop 的速度远不如 AI，通常不会专门为文档设置这样的 CI 规则。但在 AI 时代，这类可判定规则变得非常重要。

这就是 CI 和 CD。回顾一下前面的铺垫：首先是 Ralph Loop，以 workspace 为状态，可以用 Git 保存；然后选择某个 action，向后推进一步；推进过程中可以设置 pre-commit、post-commit、pre-push、pre-merge 等各种门控检查。这就是 Agent Native 开发。

OpenAI 有篇文章叫《Harness engineering: leveraging Codex in an agent-first world》，发布时引起了一定轰动。Codex 团队说，他们从一个空 Git repository 开始，人已经不写代码了，但仍然需要把模型的工作流程定好，建设环境、约束、反馈和验证机制。这些要求可以用自然语言表达，比如每次 push 前都要确保代码中的明文秘密和 API key 没有泄露。

Codex 和 Claude Code 都是 Agent Native 项目。Claude Code 曾经发生 source map 泄露，这本应当由 CI 门控阻止：review 所有产物，明文信息不能泄露。人虽然不直接写代码，依然必须建立这样的门控。OpenAI 的文章之所以引发轰动，也正因为它展示了这种开发方式。

可以查看 Codex 仓库里公开的一些 CI 流程：pull request 时跑快速门禁，`main` 上做全量验证，最后是发布，分成三层。最基础的一层主要是 Lint 工具，例如 `cargo fmt`，检查格式、拼写和一些 bad smell；还可以检查文件或函数是否过大、依赖是否违反策略。这是最基础的 Lint 级门控。`main` 的全量验证应该会跑许多单元测试；发布阶段再打 tag。
实际上，那篇文章写得很 fancy。它最后还有一节叫 “What we're still learning”：如果一个软件要以年为周期维护，他们还在探索 Agent 应该怎样工作。刚才我们看到了 Codex 的 CI 门控，但 OpenAI——或者说 ClosedAI——做一个 Agent Native 项目，绝不可能只有公开出来的这点门控。如果只有这些，项目一定早就崩溃了。因此我确信，Codex 背后还有一整套规模巨大的 Agent Native 门控机制，防止它产生 AI Slop。Codex 项目看起来比较正常、有人感；只靠 Lint 之类的东西，不可能写出这样一个项目。

其他团队也积累了一些经验。Anthropic 在做 Agent Native workflow 时，曾让 16 个 Agent 协作编译 Linux，结果大家撞上同一个 bug，重复修复，还会覆盖彼此的改动。所以真正实现 Ralph Loop 时，仍然可能需要负责 orchestration 的调度 Agent 来协调进展。

我们自己的项目里也做了一件很有趣的事，具体项目是什么可能不能说。我们有一份 `architecture.md`，可以自动生成类似架构图的东西。Agent workflow 里还有一本 logbook，里面有许多 task，有些已经完成，有些仍在进行。我们又做了一个 Agent Dashboard，借助 GitLab CI，把正在进行的任务显示在架构图上：有几个 Agent 正在完成哪项任务，有一个进度条估计完成百分比，还能看到它们正在哪个模块做什么。

作为整个项目的总架构师，我基本只需要看这张图，就能知道下面的进展。比如我是 lead，有几位同学写代码，每位同学手里又有几个 Agent，直接管理其实很困难。有了 Agent Native loop，我就能从架构图上看到整个项目的进度，预估今天或一小时后项目会变成什么样，再决定应该作出什么调整。这就是非常典型的 Agent Native 开发。

我现在还不太敢完全交出去，但也想尝试像 Grok Bot 那样设置一个 master Agent：所有事情都交给它；我说想尝试一个方向，它就替我在 logbook 里开出许多任务，挂到对应模块上。这才是真正的 Agent Native 开发。开源社区里有很多这样的实践经验可以学习。

与 OpenAI 相比，我觉得 DeepSeek Harness 是 Agent Native 开发领域一个标杆性质的项目。这张“DeepSeek 娘”的图也是 AI 生成的，最近大家好像很喜欢这种图。Codex 什么也不说，而 DeepSeek Harness 里藏了非常多好东西。不知道有没有同学把它的代码克隆下来；克隆后的第一感觉就是奇怪，因为项目的 organization 和其他项目都不一样。

这是中国人的项目。我们是中文 native speaker，我会选择用中文写文档，因为我的 System 1 读中文比读英文快。我的英文阅读已经比较快了，但中文可能仍能快一倍。就是这一倍，让我的视觉系统能快速浏览文档，从海量文字中提取关键信息，定位到想看的地方。

但作为一个要走向世界的项目，DeepSeek Harness 必须同时维护中文和英文文档。这难道不是地狱和灾难吗？文档都是随手一改、随手提交；项目里有无穷多文档时，怎样保证中英文文档的一致性？这就是经验。

我们随便看 `docs` 里的 `architecture.md`。它非常有人感，看起来干净、舒适，中间还有很多交叉引用。在 DeepSeek Harness 里，所有交叉引用都是合法的，找不到任何不合法的 link；文档之间也能保持一致。我让 Agent 调查：项目里的中英文文档怎样保持一致，又怎样保持人感？这些文档可能有一部分由人写，但人肯定主要是在告诉 Agent 应该做什么。

它靠的是“三件套加一道门禁”。每篇范围内的文档，都由同一目录下三个兄弟文件定义配对契约：英文 `foo.md`、中文 `foo.zh.md`，以及一致性记录 `foo.i18n.yaml`。当时打开的中文 Markdown 还标着开发者预览。中英文两侧具有同等权威，哪一侧先写，哪一侧就是那次更新的源，另一侧再由 Agent 翻译；绑定它们的是“两边必须表达同一件事”。一致性由 `pnpm run verify-translation-pairing` 检查。这是非常聪明的想法。

`foo.i18n.yaml` 里保存两侧的 Git blob hash。过往内容都留在 Git 历史里，因此能够知道哪边变了，哪边仍是旧版本：记录里从未见过的新 hash 对应更新后的内容。一旦发现新旧版本不匹配，就用 AI 帮忙翻译。翻译也是 patch-based 的：查看这份文档改了什么，只修改另一份文档相应的位置，其他部分保持不变。像 hash 这样的内容由程序保证。一段很短的记录，就能帮助保证两份文档的一致性。

这也印证了前面所说的：软件项目不应该只被理解成文件系统里的一堆文件，其中的东西存在错综复杂的关系。DeepSeek Harness 为此牺牲了目录的干净；但开发者可以配置自己的 IDE，把不想看到的文件隐藏掉。这类偏好不会放进仓库的 `.vscode`，因为不同开发者有不同想法。例如我只读中文，就隐藏所有 `.i18n.yaml` 和英文文档，只留下中文；英语 native speaker 则隐藏中文。两边都能在 IDE 里得到一模一样的开发体验，底层却是一套 Agent Native 的机制。

它的更新粒度是最小补丁，而不是重新翻译，只对差异部分作相应修改。它还把“人感”当成可校准的规范。看看 `docs/i18n/style-samples.md`，虽然仍有一些 AI 味，这么多文档也毫无疑问不全是人类写的，但项目到了这个体量，依然有人感、还能由人维护，背后下了很大功夫。这里放了一些经过认可的样例，并且按需加载。

你们的常见做法，可能是把“文档该怎么写”全部放进 `AGENTS.md`；但内容暴涨以后，甚至一百万上下文都装不下。所以它采用 progressive disclosure：只有需要翻译或撰写文档时，才加载相应规范。还有 `terminology.md`，约定仓库里中英文术语的统一译法，这也能通过门控作一定程度的检查。

例如，中英文按 paragraph 或 section 对应后，可以规定某个英文术语与对应中文译法的出现次数不能相差太多。假设 AI 对应“人工智能”，两侧相应词语的次数就只能相差两三个。当然这种要求可能过严，需要小心调整 decision boundary，不要把实际可以通过的内容筛掉。但这些检查能够带来很好的文档一致性，因为不约束 Agent 时，这种漂移太常见了，它会以光速生产 Slop。

所以 DeepSeek Harness 里有非常多的门控，而且很稳，此外还有更多流程。我让 Agent 从 Git 历史中还原整套文档一致性流程：由谁在什么时间引入，又经历了哪几次大的变化。DeepSeek Harness 给我们的另一个礼物，就是它完整保留了从零开始、由空项目成长到今天的开发历史。最早的提交可以追溯到 2026 年 6 月 10 日晚上 11 点；到今天，它已经是一个有一定成熟度的项目。主要贡献者包括 `turtle1999`、`ZiyaZhang` 和 `tianyicui`，这几个人也都在我们的内测群里。

2026 年 6 月 25 日左右，项目先让 terminology 先行，那时还没有其他机制，只有词汇约定。说明他们很早就意识到了文档的重要性，也说明他们有经验。到了 7 月，他们引入配对契约。这是一个非常酷的设计。我不确定他们是从哪个项目里看到类似做法，还是自己演化出来的；其实在 pre-LLM 时代，也有相似的文档维护方式。

比如 Python 文档可以由 docstring 生成，使文档和代码保持一致。这应该也不是 Python 第一个做的。每种语言都有类似 JavaDoc 的语法；C++ 本身没有原生支持，也有 Doxygen，自己规定一套注释语法，再由 Doxygen 提取。这样，代码与 API reference 就能保持一致。

受到这些实践的启发，在 Agent Native 时代，当我们要把人的工作迁移给 Agent 时，“配对契约加门禁”就是一个很酷的机制。7 月 3 日左右，他们引入了两侧同等权威的 sidecar，很快又发现这套机制必须强制接入自动化流水线。这份文档在项目开发的早期就形成了，此后一直遵循同一套原则，才能同时维护中英文文档。
里面还有很多按照 CI——不，应该说按照 Agent Native 开发组织的宝藏。

你看到 DeepSeek Harness 的第一眼，就会发现它和其他项目不一样。我觉得它是我们中国人的骄傲，DeepSeek 也是我们的骄傲，因为它把这些东西开源了。OpenAI 根本就是 ClosedAI，只放出最基础的门禁：应该通过 Lint，CI 里应该跑过 test。但它的内部服务器上不知道还跑了多少东西，肯定会隔一段时间进行 Agent review。博客里也提到，一开始他们尝试每周做一次 Agent review，防止架构崩溃；这些东西公开项目里全都消失了，能拿出来用的只剩最后用于编译、检查的部分。

DeepSeek Harness 有 Agent Native 的常驻指令体系，`AGENTS.md` 分层，每个目录都有自己的 `AGENTS.md`。它有 `verify-doc-budgets`，要求根目录文档不超过 1,960 词，`architecture.md` 不超过 2,400 词。这是防止 AI Slop 在文档中无限堆积的机制。

它还有 Agent Notes，有点像他们自己的 Ralph Loop。Agent Notes 分为 `implemented`、`proposed`、`rejected` 和 `archived`。我们的 loop 稍有不同，是自己实现的：我们有一本 logbook，里面每一项 log 都带有 status，并且与 GitHub CI 整合，形成前面提到的 Dashboard。他们也有类似机制，只是可能觉得 Dashboard 没那么必要。Agent 需要开发时，他们会把任务记在类似 logbook 的地方。此外还有许多 Skills。

今天其实还有一个变化。你们有没有发现，ChatGPT 现在开始喜欢生成动态 UI 组件了？它会生成一些 HTML 小卡片。以前只是把图片堆在前面，现在会把图片嵌入文本流程，读起来舒适很多。有时它觉得合适，也会生成动态内容。命令行里做这些可能稍微麻烦，所以 Web UI 很可能会成为主流。

项目中还有各种评审流程的门禁、Code Review 规范、工程质量规范，以及产品自己提供的各种 Skills。我们让 Agent 讲讲 Code Review 是怎样做的。以前面对一个陌生项目，不可能像现在这样；现在只要有一些元层级的认知，知道什么东西是好的、什么东西是自己没见过的，就可以光速向别人学习这些真正好的东西。

它的流程包含本地自证、CI 门禁和人工评审，甚至还有评分。新增文案必须通过语义评审，文档和 JSDoc 也有相应规范。仅从文档来说，它不仅要求中英文保持一致，还要求所有链接一致。甚至文章里如果有一个代码块，比如一段 interface，它还会检查这段 interface 是否逐字出现在某个源文件中，确保每一个字符都一样。这样就能防止代码改了接口而文档没有更新，或者文档改了接口设计而代码没有跟上，彻底杜绝这种漂移。

我们把这个想法稍微作了扩展。在自己的 Agent Native 项目里，code block 带有执行语义，可以 specify 一份很小的说明，表示这段内容是干什么的。例如，我要求它出现在某个位置，或者希望它以某种形式和另一个东西关联。我们用一些轻量级 check，扩展 Markdown fenced code block 的语法。

Skills 把“怎么做”从“做什么”里分离出来，还有各种机械门禁：doc-sync CI、static CI、coverage CI、snapshot CI。代价是每次提交前可能要运行大量门禁。但你又不写代码，大部分时候只是监工：你写 plan，跟 AI 一起写 plan。我们会在 logbook 里写 plan，在 Plan Mode 先把要做什么、做到什么程度搞清楚，剩下的由 AI 完成。我修改 logbook 时，所有代码都没有动过，也就不需要运行那些 CI。

此外还有各种 verifier，例如 `verify-client-ui-i18n`、`verify-translation-pairing`、application entry points 以及一些 TypeScript 相关检查。其中有一个 `verify-type-equivalence`，要求文档里粘贴的类型必须与源码一致，不允许漂移。这些检查单看都非常小，但全部加起来，项目就被维护起来了。还有文档分层、从子任务到机制的路由等很多设计，这就是我说的 Agent Native。

从去年到今年，尤其今年年初以来，Agent 时代只过了短短半年。这个项目从 6 月开始，那时他们就已经在规划这些事，最后给我们留下了非常好的、很有启发性的东西，而且是开源的。这些设计都来自真正的经验。你一看到，就觉得确实应该这样；但如果只是坐在教室里做“语言律师”，思维会被禁锢在当前上下文里不断往下走，看不到 design space 里还有巨大空间可以朝另一个方向探索，就很难完全凭空想出来。

他们肯定失败过、写过代码，才有这些经验。崔老师和我是同龄人。即便如此，项目仍然会重构。终有一天，你会发现项目烂掉了。我那天就跟学生说，他的项目 architecture 已经烂掉了，那就先开一份新的空白项目，再一点点把旧功能迁进去，保持好的架构。

当你发现苗头不对时，garbage collection 可能无法解决所有问题。必要时要做模块级重构，甚至项目级重构，让项目走上更正确的方向。历史上真实的失败也不少。比如社交网络先驱 Friendster，迅速吸引大量用户以后，性能就崩溃了。当然这是 pre-LLM 时代的事情，今天在 Agent 时代也许能把它救起来。这些经验最终促成了 Agent Native 开发的好范例。

我也看到了一些威胁。首先，如果不做很多次、不失败很多次、不建很多东西，就很难真正把一件事做好。你可能确实有一个好想法，在 intent 层面甚至是世界级的；但如果组个草台班子去做，就可能沿着一条直线海量生产 AI Slop，最后好想法被别人抄走。有经验的团队则可能收敛到更好的方向。

社会性的威胁是：你必须有机会尝试。开学时我只是开玩笑说“没有 Token 的学生应该立即退学”，但真实发生的事情是：如果没有 Token，你尝试的机会就不如别人多。不经历试错，当然也可以看别人的 open source。现在开源社区里仍有好东西，最后就看你的悟性，能不能通过阅读别人做的东西，领会 Agent Native 开发应该怎样进行。即便如此，你还是需要作很多尝试、经历失败。

这不就形成一条“斩杀线”了吗？如果读完博士，工作能力依然不如 Agent，对用人单位来说，他们会选择一个 senior，给他无穷的 Token，而不是培养一个 PhD 学生。资本家要最大化企业的运行效率。以前找一个新兵蛋子，还可以师傅带徒弟，看中他的 potential；但如果回报周期实在太长，需要四五年，那时公司可能早就黄了。Agent 的能力已经在这里，而且还在上涨，所有人都在不断被斩杀。

当斩杀线越过本科毕业水平时，你还有没有每月 20 美元 Claude Pro 的价值？我的 Anthropic 账号还在 Grok Bot 里运行 Claude Code。我现在有一个 20 美元的订阅，发现 Opus 5.5 的额度其实很够用，而且 Opus 5.5 真的很强。一个本科生要达到 Opus 5.5 的水平，我觉得非常困难。

如果我是一个 senior，有比较完整的 big picture，又有自己的好 Agent Harness，生产力会更强。OpenAI、Anthropic 从来没有把内部的这些东西开源出来，还要靠我们的国产之光 DeepSeek 开源。如果这些知识都藏在公司内部，永远不让别人知道，就会有越来越多的人被斩杀，这是一个社会性问题。

我觉得这个问题可能只有大学能解决，因为大学原则上不是以盈利或 KPI 为导向的地方。话是这么说，实际上大家也知道，网上常见“学阀一手遮天”之类的故事。高校考核我们的指标也不是上课，而是所谓科研经费。某种程度上，高校同样像资本家和公司一样运营，只不过属于另一套资本体系：由基金委、科技部组织，形成优青、杰青、院士的金字塔。这个体系下，每一个杰青的产出都类似一家公司的产品。

当学生永远赶不上 Agent，老师、学生都被斩杀时，这个体系就完全失效了。所以我看到的是：大学肯定要崩溃。我又在这里发表暴论了。反而像学而思这样的机构，可能成为一种新形态的大学。为什么？因为它从上到下都是资本化运营，靠样板课：花一百万雇一个清北天才设计样板课、试讲，之后每位老师都是执行机器。现在再把“老师的执行机器”换成老师加 AI，甚至花一千万到市场上抢最好的天才设计样板课，就可能把教育、教学体系完全颠覆。

我们没办法，因为惯性很大，还得以现在的方式上课。他们却可以资本化运营。未来会发生什么，我不知道。但我非常感谢开源社区，尤其我自己的一切都是开源社区给的。如果没有在开源社区里看到那些好东西，我不会有今天的理解，也不会来上这门课。现在大家知道了，可以回去在互联网上找真正优秀的项目。我觉得可以从 DeepSeek Harness 开始看起。

本质上，这个 Harness 和我今天讲的特别小的 Ralph Loop 是一样的。不过今天那个东西甚至不能算 Ralph Loop，只能算一个 `agent.py`。你可以把 DeepSeek Harness 理解成它的完整形态，只是“一切皆插件”，所有东西都被插件化了。里面有许多有趣的东西。今天下课。
