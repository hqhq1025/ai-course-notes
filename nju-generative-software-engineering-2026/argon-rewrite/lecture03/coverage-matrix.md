## 教师讲解摘要

| 来源 | 要点 | 去处 |
|---|---|---|
| slide-002 / 官方讲义“# 版本管理” / 课堂字幕开场 | 谈及 GPT-6 的使用感受时表示，虽然模型幻觉少了、品味和空间感知提升了，但面对极其开放的 intent-spec-impl 空间（例如“做一个好用的界面”），人们往往要看到第一版实现才清楚自己真正介意什么，设计上还是要不断批评和反馈，因此调侃“我好像还可以再苟活几个月”。 | 第一章 模型演进与软件工程项目的起点：从“一个目录”到版本管理 |
| 课堂字幕开场（百年前汽车与自动驾驶类比） | 用一百多年前汽车开十二公里就出故障、司机必须精通机械原理，对比今天在地下车库直接对自动驾驶汽车说“帮我开到某地”，回应“AI 时代还要不要学操作系统和数据库”，指出今天学习核心概念是为了理解人类积累的好设计，从而更好地解锁 AI 的创造力。 | 第一章 模型演进与软件工程项目的起点：从“一个目录”到版本管理 |
| slide-005 ~ slide-007 / 官方讲义“## 一个目录，为什么还不算管好了项目” / 课堂字幕 | 讲述自己第一个博士生（2012 年入学）大一去机房时把全部代码存在 U 盘里、大二 U 盘损坏导致启蒙作业全部丢失的故事，并穿插“我又做了多少个 killer 级产品，它们都位于 http://localhost:5173”的笑话，说明软件工程项目除了本地目录和文件外，还必须依靠 Git 管理历史状态，依靠项目 Makefile（如 `make submit`）组织验证与交付。 | 第一章 模型演进与软件工程项目的起点：从“一个目录”到版本管理 |
| slide-008 ~ slide-009 / 官方讲义“## 学习变容易以后，留意变得更重要” / 课堂字幕（香港路牌与 README 对比） | 用香港复杂地下通道在每个三岔路口正前方必有清晰路牌，对比在南京地铁站环顾四周找出口的体验，进而对比维护十余年的老项目简短清晰的 README 与充斥 Unicode 框图的“AI slop”，阐明“上课耽误学习”是因为课外真实项目信息密度极高，必须靠 Virtually Implement（先在脑中做一遍）和对细节的注意力来主动学习。 | 第二章 AI 时代的学习方法论：保持“留意”与脑中预演 |
| slide-010 / 官方讲义“## 从‘我想撤销’推导出快照” | 复盘上周保研推免面试：问什么是 Git 大家都能说两句，问 `git rebase` 是什么则是 0/10 答出；问 `git merge` 冲突后会观察到什么，竟无人说出冲突双方内容及尖括号、等号标记会直接写入工作区文件且 `git status` 显示 `both modified`，直言这是“第一没用过，第二没有留意”。 | 第二章 AI 时代的学习方法论：保持“留意”与脑中预演 |
| slide-011 ~ slide-015 / 官方讲义“## 从‘我想撤销’推导出快照”与“## 从 init、add、commit 到分支与合并” / 课堂字幕 | 对比 SVN 每次保存行级补丁（delta）、回退早期版本需逐步倒退的设计泥潭，强调 Git“一秒钟回到过去某个版本”的项目级快照第一性原理；并通过提问“先 `git add hello.c`，再改 `hello.c`，下一次 `commit` 提交哪个版本”，揭示会敲命令与真正理解暂存区（Index）状态变化之间的区别。 | 第三章 从“我想撤销”推导 Git：项目快照、暂存区与分支合并 |
| slide-016 ~ slide-018 / 官方讲义“## 哪怕只有 hello.c，也需要工程判断” / 课堂字幕（进组高血压时刻） | 列举研究生新生进组和论文审稿时的“高血压时刻”：把编译出的可执行文件、`dist/`、运行日志、写死 `C:` 盘绝对路径的 `.vscode` 配置、macOS 的 `.DS_Store` 乃至仍处于激活状态的 DeepSeek API key 一起 `git add .` 提交上来；建议新手在 `AGENTS.md` 中要求 Agent 在每次 Git 操作前逐文件解释是否符合 best practice。 | 第四章 跨越命令表面的工程判断：从 `.gitignore` 到命名规范的细节追问 |
| slide-019 ~ slide-020 / 官方讲义“## 大写还是小写，也值得追问” | 分享自己在严肃项目中面对 `[TYPO-CHECK]` 与 `[typo-check]` 时的真实犹豫：直觉觉得“大写似乎更好，但不是极强”，进而追问出大写有助于在视觉上区分“可引用的规则标识”与“自然语言解释”（类比 RFC 8174），同时指出若项目已有小写规范则一致性优先。 | 第四章 跨越命令表面的工程判断：从 `.gitignore` 到命名规范的细节追问 |
| slide-021 ~ slide-023 / 官方讲义“## 让工具把真实细节展开” / 课堂字幕（gitv 与少儿 Python 编程环境演示） | 现场演示用 Node.js 编写的 `gitv` 命令行工具，直接从 `/tmp/hello/.git/objects` 的原始字节出发，解压展示 `blob`、`tree`（含 `100644`/`100755` 权限模式）、`commit` 对象及冲突时 index 隐藏的 `base`/`ours`/`theirs` 三个版本；同时展示为三四年级小学生 vibe coding 的 Python 汉诺塔与 3D 方块调试器，批评大学里连真正好东西都没打开过、只会看公众号照本宣科的现象。 | 第五章 告别古法学习：用可视化工具展开 Git 底层对象与真实细节 |
| slide-024 ~ slide-026 / 官方讲义“## 提交要留下可以理解的变化” / 课堂字幕（提交信息与排版规范） | 在课堂演示中故意提交 “I added some cool stuff” 并让 Agent 现场批评其“毫无信息量、全是主观废话”，借此讲解 Conventional Commits 格式（diff 留下改动，message 留下理由）、特殊场景下的空提交（empty commit）以及 Markdown 文档中英文之间留空格的一致性要求。 | 第六章 提交规范与真实工程闭环：从 Conventional Commits 到 SWE-bench |
| slide-027 ~ slide-029 / 官方讲义“## 一行修复，背后是一整套工程工作” | 结合 SWE-bench 中的 Astropy 嵌套模型缺陷（`astropy__astropy-12907`），说明虽然最终代码只把矩阵拼接处的 `1` 改成了 `right` 一行，但背后包含理解布尔依赖矩阵、满足 `FAIL_TO_PASS` 与 `PASS_TO_PASS` 测试、补充 changelog、代码审查、分支回移以及通过 `gh`/`glab` 串联平台对象的一整套工程闭环。 | 第六章 提交规范与真实工程闭环：从 Conventional Commits 到 SWE-bench |
| slide-030 ~ slide-031 / 官方讲义“## 用原子变更推进项目”与“## Agent 能力之内的项目，怎样协作” / 课堂字幕 | 总结“项目是由 Atomic Change 推进的快照”，并分享开发 Pico Playground 的具体做法：架构设计阶段单线程与高智力模型收敛接口，把绝大部分接口设计为纯函数、核心全局状态控制在十几行，并禁止 Agent 查看库函数实现以节省 token；实现阶段开不超过 3 个终端，配合双屏实时刷新进行肉眼视觉验收。 | 第七章 原子变更与人机协作实践：架构收敛、有限并发与实验设计 |
| 官方 Lab1“# 实验 (1)：会成长的个人助手” | 在实验一中剖析为什么要做跨工具个人助手：若将半明确的需求直接丢给 Agent，大概率会生成一团乱麻的 AI slop，陷入《人月神话》式的软件焦油坑；同时严厉提醒在操作 `ehall.nju.edu.cn` 时行为必须保守，“万一 Agent 把你的课都退了，你就完蛋了”。 | 第七章 原子变更与人机协作实践：架构收敛、有限并发与实验设计 |
| slide-032 ~ slide-035 / 官方讲义“## 如果代码产能再提高一千倍” | 通过“Agent 产能提高 1000 倍”的思想实验与“至少一名值班员在岗，两个 Agent 各自看到对方在岗便将另一人改为离岗”的 Write Skew 例子，阐明合并无文本冲突不等于满足业务不变量，并提出“反正没有 Agent 能被开除、能坐牢，出什么问题修好就行”，探讨将项目管理重心从人工追责转向自动化不变量验证与快速恢复。 | 第八章 当代码产能提高一千倍：面向 Agent 的并发版本控制设想 |
