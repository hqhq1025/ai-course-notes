# 版本管理

前两讲讨论了模型能做什么，以及怎样通过提示词和上下文让它理解我们的目标。这一讲进入真正的软件工程任务：从零开始构建一个项目，并让它在持续修改中保持可理解、可恢复、可协作。

开场谈到 GPT-6 时，老师的使用感受是：幻觉少了，品味提升了，但遇到设计问题，还是需要不断批评和反馈。“我好像还可以再苟活几个月。”这句玩笑延续了前两讲的主题：从意图（Intent），到规格（Spec），再到实现（Impl），存在非常开放的选择空间。你说“做一个好用的界面”，常常要看到第一版，才发现自己真正介意的是什么。实现也在反过来帮助我们确定需求。

老师用“理应当做到的事就是能做到”形容一些生成结果带来的冲击，并把自己对模型发展路线的理解概括为向数学逻辑推理对齐。这是一种从使用经验出发的判断。对这门课更直接的问题是：模型进步这么快，我们还要学什么？答案仍然是，对世界建立正确的概念和理解。你要能看出一个设计好在哪里，知道该追问什么，也知道怎样把一个大目标分解成可以推进的工作。

## 一个目录，为什么还不算管好了项目

从最朴素的角度看，软件工程项目就是一个目录，目录里有文件：需求说明表达意图，接口文档和测试描述规格，源代码承担实现，构建脚本把它们组织起来。经过构建或运行，可以得到一个可交付的东西，例如打开 `npm run dev` 启动的本地网页，或者运行一个编译得到的可执行文件。

早期做课程作业，事情往往到这里就结束了。老师的第一个博士生在大一时，把代码保存在优盘上；优盘坏了，代码也就没了。大约在 2012 年，打包发邮件还是很自然的作业提交方式。今天改成网页上传，虽然交作业方便了，单靠“目录里存着文件”的项目管理方式，却没有发生根本变化。

即使优盘不坏，也还有别的问题。昨天的版本能运行，今天改坏了，怎样回去？一个功能改了一半，突然需要修复另一处错误，怎样暂时放下它？你和同学从同一份代码出发，各自修改了一些文件，怎样把结果汇合起来？

这些需求自然引出了版本管理：除了保存项目现在的样子，还要保存它经过哪些状态，以及这些状态之间的关系。Git 是今天必须掌握的基础工具。课程可以让同学用 `git clone` 获取作业，用 `git pull` 接收更新，再通过项目约定的 `make submit` 入口提交。这里的 `make submit` 由课程的 Makefile 定义，不是 Git 自带的命令。Git 负责版本，项目规则负责怎样构建、验证和交付。

## 学习变容易以后，留意变得更重要

现在到处都能看到 GitHub 链接，每一个真实项目都可能成为学习素材。问题在于，看到很多项目，不会自动把它们的设计变成自己的知识。你可能打开过几十个仓库，却没有注意过它们如何组织目录，为什么保留某些文件，又为什么忽略另一些文件。

一个很有效的技巧是 virtually implement：先在脑子里做一遍。读论文时，看到作者提出的问题，先停下来想：换成我，会怎样解决？需要哪些数据结构，哪些前提，可能在哪里失败？然后再看作者的方案。如果想法一致，就可以比较实现细节；如果不一致，就追问差异来自哪个约束、哪条自己不知道的经验。

这个方法也适用于读代码、看文档，甚至阅读 AI 生成的一段话。你能不能预测下一段会说什么？为什么作者在这里多检查了一次返回值？为什么一个看上去简单的功能，还配有构建说明和测试？每次多留意一个细节，原有的知识网络就可能向外长出一点。

课堂说“上课耽误学习”，背后是课外的信息量和信息密度已经非常大，而我们未必学过怎样使用这些资源。学习知识的门槛降低了，主动发现自己不知道什么的意识，就更重要了。Git 恰好是一个很好的例子：很多人听说过，甚至每天都在用，却没有真正观察过它做了什么。

## 从“我想撤销”推导出快照

老师在保研面试中问过几个问题：什么是 Git？什么是 `git rebase`？`git merge` 发生冲突以后，你会观察到什么？第一个问题，多数人还能说上几句；被问到 rebase 的十位同学却没有答出来。合并冲突时，也没有人主动说出：常见文本冲突的双方内容和冲突标记，会直接出现在工作区文件里。

这不只是少背了几个术语。真正使用过一个工具，也需要留意眼前发生的变化。否则，“知道 Git 是版本管理工具”和“能够预测下一条命令的后果”之间，会一直隔着很远。

先从自己已有的经验出发：人和 Agent 都会犯错误，对的代码会被改错，设计会推翻重来，所以我们希望项目具备“回溯时间”的能力。最直接的做法，是复制整个目录，分别叫作“作业-v1”“作业-v2”“作业-最终版”。只要旧目录还在，就能找回旧文件；但版本一多，谁从哪份改来、哪个文件该配哪个配置，就需要靠人记忆。

版本管理工具逐步接管了这些工作。RCS 等工具管理文件历史，CVS、SVN 等系统支持围绕服务器协作，Git 则让开发者通常在本地也拥有项目历史。Git 的诞生与 Linux 内核开发有关：内核曾依靠补丁和打包文件协作，后来使用 BitKeeper；2005 年，原有的免费使用安排结束，内核社区开始开发自己的工具。速度、大规模协作和分支支持，都是实际工作推动出来的要求。[Git 简史](https://git-scm.com/book/en/v2/Getting-Started-A-Short-History-of-Git)

最需要建立的概念是：**Git 管理项目的快照。** 快照描述纳入版本管理的文件在某个状态下的内容和目录位置。为什么要以项目为单位？因为源代码、接口和配置经常要一起变化。只恢复旧代码，却留下新配置，可能拼出一个历史上从未正常运行过的版本。

一次提交（commit）把这样的快照与作者、说明、父提交等信息联系起来。父提交记录它从哪里来，于是一个个状态构成了历史。你删除一个已经提交过的文件，再提交一次，新快照里虽然没有它，仍被保留的旧快照里却还有。编辑器里“存过盘”和 Git 里“提交过”，保存的是不同层次的状态。

Git 也不需要为每个快照机械复制全部文件。它用对象保存内容和目录结构，未变化的部分可以复用；逻辑上是完整快照，存储上可以共享数据。[Git 对象](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

## 从 init、add、commit 到分支与合并

`git init` 在目录中建立一个仓库（repository，简称 repo），最初还没有提交。`git clone` 从已有仓库建立本地副本。GitHub、GitLab 可以托管远端仓库，但在本地记录版本并不要求先连接这些平台。

接下来要区分三个东西。工作区是你正在编辑的文件；暂存区（Staging Area，也叫 Index）保存下一次提交准备采用的内容；提交历史保存已经记录下来的快照。`git add hello.c` 会把此刻 `hello.c` 的内容放入暂存区，普通的 `git commit` 再据此创建提交。

因此有一个很值得亲手试的问题：先修改 `hello.c`，执行 `git add hello.c`，然后又修改它，最后执行 `git commit`，提交的是哪个版本？答案是 add 时暂存的版本。后续修改仍然在工作区，要再次 add 才会进入这次提交。可以用 `git diff` 观察尚未暂存的修改，用 `git diff --cached` 观察暂存区相对当前提交的变化。暂存区让你能够组织一次提交的内容，而不是被迫把此刻所有编辑一并记录下来。[git add 文档](https://git-scm.com/docs/git-add)

分支则让项目能够从同一个起点沿不同方向推进。可以把分支名理解为指向某个提交的可移动引用；在通常的分支工作方式下，`HEAD` 表示当前所在的分支。你在这个分支上创建新提交，分支引用就向前移动。另一个分支仍然可以停在原处，或沿自己的路线前进。

假设你和同学从同一版本开始，一个修改界面，一个修复解析器。`git merge` 会结合共同祖先和双方的变化，尝试得到合并结果。双方已经分叉时，常见结果是创建一个有两个父提交的合并提交；如果一方只是另一方的后续，Git 也可能只把分支引用向前移动，这叫 fast-forward。

当双方对同一段文本做了无法自动协调的修改，Git 通常会在工作区文件里写入 `<<<<<<<`、`=======`、`>>>>>>>` 等标记，展示需要人工决定的内容，同时在 `git status` 中报告例如 `both modified` 的状态。解决冲突，就是阅读上下文，把文件编辑成最终应有的内容，移除标记，再用 `git add` 标记已解决并完成合并。二进制文件、删除与修改冲突等情况不一定呈现同样的文本标记，所以关键是同时检查状态和文件。[分支与合并](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)

`git rebase` 则把一串提交所代表的改动，依次重放到新的起点上。例如你基于旧主线做了两次修改，现在主线已经前进，可以把这两次修改重新应用到新主线之后。重放得到的提交通常有新的标识，过程中也可能冲突。它适合在约定允许的范围内整理工作；如果别人已经依赖原来的提交，你再改写它们，就会增加协作成本。[Rebase](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)

理解这些操作后，再回头看命令，就不再只是记住“输入什么”。你可以在操作前预测：工作区会变吗？下一次提交包含什么？哪个引用会移动？历史里会增加什么关系？这才是可以继续外推的知识。

## 哪怕只有 hello.c，也需要工程判断

教程把几个命令教完，似乎就可以开工了。但软件和系统里还有大量约定俗成的 best practices，也就是在实践中积累的良好做法。它们经常来自一次次踩坑，或者开发者对旧设计忍无可忍后的改进。

例如，目录里同时有 `hello.c` 和编译得到的 `hello`，要不要一起提交？如果两者都保存，下一次只改了源码却忘记重新编译，仓库就会出现两份不一致的状态。别人到底该相信哪份？如果只保存源码，也还要说明怎样构建，让其他人有条件重建结果。“我的目录里有什么”和“项目需要共同保存什么”，是两个问题。

对刚开始做项目的同学，可以在自己的 `AGENTS.md` 中加入这样一条学习约定：

> 在做任何 git 操作之前，都逐个文件检查变化，并为我（新手）解释是否符合 best practice，为什么，以及相关的概念。

这条约定的价值在于让具体变化成为学习入口。面对一个文件，先判断它承担什么作用，再决定是否提交。老师反复提醒新生的几类问题，可以放在一起理解：

* 构建产物和运行日志通常不提交，例如 `dist/`、编译得到的程序和调试日志；应让源码、依赖和构建方法能够重建所需结果。
* 个人配置通常不提交，尤其是包含自己机器上的绝对路径、私人偏好的设置；团队共享、可移植的编辑器配置则可以有意保留。
* 密钥不能提交。源码需要共享，并不意味着访问服务的凭据也应一起共享。
* `.DS_Store` 等临时文件不提交，它们既不表达项目意图，也不参与项目构建。

这些不是按文件名机械执行的禁令。依赖锁文件虽然由工具生成，却常常用于固定依赖版本；有些项目也有意保存生成的头文件或静态发布产物。需要解释的是，这个文件为何构成共同维护的项目状态，以及怎样保证它与其他文件一致。

`.gitignore` 可以把这些约定落实为忽略规则，但它不会让已经被跟踪的文件自动退出版本管理，更不会抹掉历史。[gitignore 文档](https://git-scm.com/docs/gitignore) 这也解释了为什么误提交密钥后，仅仅删除当前文件不够：旧提交可能仍保留它，别人也可能已经取得副本。版本管理帮助我们记住过去；不该公开的东西一旦进入过去，就不能假装它从未发生。

## 大写还是小写，也值得追问

真实项目里出现过一个很小的设计选择：

```
[TYPO-CHECK] Docs should be typo-free
[typo-check] Docs should be typo-free
```

这是同一条文档检查规则的两种写法。老师的直觉是“大写似乎更好，但不是极强”，一时又说不清原因。这样的犹豫很有价值：它提示我们，直觉背后可能有可以讨论的设计理由。

这里，方括号里的名字是固定的规则标识，后面则是解释规则的自然语言。大写让两者更容易在视觉上区分；讨论“违反了 `TYPO-CHECK`”时，它也更像一个明确的引用。这样，读者可以迅速区分“我们正在引用哪条规则”和“这条规则说了什么”。

不过，如果整个项目已经使用小写标识，或处理规则的工具要求小写，保持一致可能比局部的醒目更重要。我们得到的不是“大写永远优于小写”，而是理解了这个选择涉及的角色区分、可引用性和一致性。对一个微小细节多问一句为什么，也是在训练设计能力。

## 让工具把真实细节展开

课堂有一句半开玩笑的“计算机科学定律”：你想要的，就一定有人做。遇到难以理解的概念，可以先寻找有没有工具把它直观地展示出来。现在还多了一种可能：把自己的学习需要写清楚，让 Agent 制作一个工具。

这次的例子是 `gitv`。目标是一个用 Node.js 实现的命令行工具，接收真实 Git 仓库的路径，启动 HTTP 服务，在浏览器中展示仓库的主要概念。这里特意强调“真实”：展示对象前，要能从文件系统里的文件和原始字节出发，解释怎样解析成对象，再展示对象之间的关系。

一个 blob 保存文件内容，tree 把文件名与对象组织成目录结构，commit 关联根目录树和父提交。可视化要帮助学生把这些名字和磁盘中的数据联系起来。内容应能展开阅读，修改应能比较，大小文件都要合理显示。仓库发生变化时，页面持续监听，并用动画显示对象和引用如何变化。明快的浅色背景、可拖动的布局、尽量能自行说明含义的视觉关系，都是为了让课堂上的注意力落在变化本身。

于是，一个适合学习的实验就很自然了：先预测执行 add 后会发生什么，再观察；接着修改文件但不 add，看看哪些内容保持原样；提交以后，再找出新提交、目录树和分支引用。视觉工具降低了观察成本，预测与核对则让观察变成理解。

课堂把直接生成的工具与 [Learn Git Branching](https://learngitbranching.js.org/) 等已有学习工具作比较，也拿生成的编程环境与 [61A Code](https://code.cs61a.org/) 对照。这样的比较应该落在细节上：能否看清关键状态，交互是否顺畅，边界情况是否处理得当，能不能真的帮助使用者。一次课堂生成结果体现的是这次任务的表现，不能直接推成模型之间的普遍排名。

老师对“只是读过介绍，却从未真正打开好东西”的学习方式很不满意。没有使用过优秀工具，就很难知道“把细节做好”到底意味着什么。愿意亲自操作，发现一个细节，继续追问，这种愿意学懂的品质会越来越有价值。遗憾的是，即使学习让人快乐，每个人的学习时间仍然有限；更应该把工具用在值得理解的问题上。

## 提交要留下可以理解的变化

再来看一个日常问题：你会写 commit message 吗？`update` 当然能成为提交说明，但几个月后翻历史，它几乎不能帮助任何人。假设修复了命令解析器，可以写成：

```
fix(parser): accept repeated spaces between arguments
```

这是 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) 风格的示例：`fix` 表示修复，`parser` 标示范围，后面说明行为变化。固定结构既方便人浏览，也方便工具分类和生成更新记录。具体项目可以采用不同约定，关键在于形成稳定、可理解的表达。

标题之后，还可以解释：旧解析器把连续空格当成空参数，导致复制来的命令失败；现在忽略参数之间的多余空格，但保留引号内部的空格。代码 diff 展示怎样改，提交说明补上为什么改、想保留什么。将来有人想删除这段逻辑，就能找到判断依据，而不必重新猜一遍。

[Git Best Practices](https://sethrobertson.github.io/GitBestPractices/) 收集了许多实践经验。这些经验可以从几个工程问题来理解：怎样留退路，怎样让别人读懂变化，怎样让协作可预期，以及怎样让约定得到执行。

留退路，意味着探索过程中及时保存检查点。不要因为将来的历史想整理得漂亮，就让今天的工作一直只存在于工作区。误操作后先保护现场，再考虑通过记录引用移动的 reflog 等机制寻找原有提交。远端仓库可以保存已推送的历史，但不会自动备份你尚未提交的编辑。

让别人读懂，意味着把探索过程整理成围绕明确意图的提交。修复一个错误和对应的回归测试可以在一起，顺手格式化整个项目通常应该分开。整理后的每一步如果能构建、能验证，审查者就能逐步理解，出问题时也有可靠的定位单位。

让协作可预期，需要约定哪些历史可以整理，哪些已经成为他人的依赖；也要说明谁负责合并、如何发布、怎样把修复送到维护中的旧版本。让约定得到执行，则可以借助 hooks 和持续集成（CI）：前者在开发操作附近尽早反馈，后者在集成流程中自动检查构建和测试结果。

这些机制并不替代思考。你自己的修改测试通过了，合入更新后的主线还需要检查组合结果；一段提交说明符合格式，也不等于它解释清楚了行为。规则的价值，最终要落实到恢复、理解和协调的成本上。

## 一行修复，背后是一整套工程工作

这些习惯与软件工程日常任务直接相关。经典 [SWE-bench](https://arxiv.org/abs/2310.06770) 从真实 GitHub 项目的 issue 和修复构建任务：给定一个已有仓库的状态与问题描述，让模型产出补丁。它要求模型接手已经存在的设计，在上下文中完成修改。

可以把工作过程理解为：读懂现象，复现问题，找到相关调用路径和项目约定，修改实现，再验证修复及已有行为。评测中的 `FAIL_TO_PASS` 测试应从失败变成通过，`PASS_TO_PASS` 测试应继续通过。这两个名字说明了修复的双重要求：解决新问题，同时守住已有能力。[SWE-bench 评测实现](https://www.swebench.com/SWE-bench/api/harness/)

Astropy 的一个真实问题能把这件事讲得很具体。它的建模工具用一个布尔矩阵表示输出对输入的依赖：某个位置为真，表示对应输出依赖那个输入。两个独立的一维线性模型并排组合时，预期矩阵应只有对角线为真。可是，将这两个模型先组成子模型，再与另一个模型组合后，它们对应的区域却变成了全真，仿佛两个本来独立的计算突然相互依赖。仅仅多包了一层组合，依赖关系就错了。[Astropy Issue #12906](https://github.com/astropy/astropy/issues/12906)

根因在拼接依赖矩阵的代码中：右侧已经是子模型的矩阵时，原实现把对应区域填成了 `1`，丢掉了原矩阵的内部结构。修复只需把填入的值改为 `right`，保留那份已经计算好的依赖关系。实际 PR 同时增加了不同嵌套方式的测试和更新记录。[修复代码与测试](https://github.com/astropy/astropy/pull/12907/files) 这项修改随后合并进入项目主线。[PR #12907](https://github.com/astropy/astropy/pull/12907)

所以，“只改了一行”描述的是最终代码差异的大小。要找到这一行，需要理解用户遇到的行为和项目中的抽象；要让项目接受它，需要留下验证证据；要让用户得到它，还需要完成集成与交付。SWE-bench 主要通过测试验收补丁，真实工程则还包括这些沟通和发布工作。

Git 管理版本，但 issue、审查讨论和 CI 运行状态属于平台协作对象。为此，还有 GitHub 的 [gh](https://cli.github.com/manual/) 和 GitLab 的 [glab](https://docs.gitlab.com/cli/) 等命令行工具。一个完整流程可以从读取 issue 开始，经过本地修改、测试、提交和推送，再创建 Pull Request（PR）或 Merge Request（MR），查看检查与审查反馈，继续修改，直到合入。这样，人和 Agent 都能通过命令行把版本操作与平台上的协作过程连接起来。

## 用原子变更推进项目

回到软件工程，可以把这一讲的核心概括为：**项目是由原子变更推进的快照，可以分支，可以合并。** 原子变更（atomic change）在这里指围绕一个明确意图组织的完整修改，它应当能够被解释、验证，并在需要时单独撤销。它不一定只改一个文件，也不一定只有几行。

为什么强调这一点？因为人很难处理“一团混沌”。一次改了接口、重写了实现、更新了依赖、调整了格式，最后测试失败，应该从哪里找起？如果这些变化有清楚的边界，就可以分别理解、审查和处理冲突。

历史还可以成为调试工具。`git bisect` 在已知好版本与坏版本之间，通过不断测试中间提交缩小范围，帮助定位引入问题的变化；`git revert` 可以记录撤销某次变化的新提交。它们好不好用，与历史中的变化是否完整、是否可验证密切相关。

有些项目要求线性历史（linear history），将集成后的提交组织成较直接的一条主线。这样便于阅读和追踪，也方便用 `cherry-pick` 把指定提交的变化应用到其他分支，或结合 `blame` 追查代码行的来历。不过，线性只是组织形式。每一步都意义不明、不能运行，排成一条直线也不会自动变成好历史。

在模型能力还有限时，AI 参与开发同样需要避免“一团混沌”。一次交给它一个有边界的目标，保留可以检验的状态，发现偏差后及时反馈，这些仍然是有效的工程方法。代码生成速度提高了，并没有自动消除理解和集成的难度。

## Agent 能力之内的项目，怎样协作

如果项目已经落在 Agent 能力之内，例如课堂提到的 Pico Playground，人的工作可以怎样变化？老师的实践是，架构阶段先“单线程”：与能力强的模型反复讨论，直到接口、约束和总体设计逐渐收敛，再把结果写成文档、规则和示例，包括测试要做到什么程度。

这个阶段仍然需要人的知识。为什么还要学习操作系统、编译原理和数据库？因为这些领域积累了大量好设计：怎样划分职责，怎样表达不变量，怎样隔离变化，怎样协调并发。知道这些，才能在讨论中提出有效问题，判断模型给出的方案是否值得继续。

进入实现阶段后，可以打开少量终端并行工作。老师给出的实践范围是不超过三个终端，通过 `AGENTS.md` 说明协作规则，例如历史如何整理、任务怎样集成，再由人脑承担一部分并发控制：尽量安排相互不冲突的任务。这个数量是个人工作方式，不是并发 Agent 的普遍上限。

每一轮产出都应尽快检查；有界面的项目，立即打开看看，给出视觉验收反馈。无论你觉得模型这一次的质量高不高，都不要让未确认的设计选择积累太久。架构讨论收敛共同前提，有限并发推进独立工作，快速反馈纠正理解偏差，三者需要配合起来。

## 如果代码产能再提高一千倍

最后做一个思想实验：假设 Agent 生产代码的速度提高一千倍，会发生什么？“一千倍”在这里用来放大矛盾，并非一次测量结果。生成一分钟，人工理解和验收一小时，积压的就会是等待判断的变更。Git 本身还能保存它们，但围绕人工提交、审查和协调组织起来的工作方式，可能成为瓶颈。

如果从零开始为 Agent 设计版本控制系统，也许应该把快照、变更以及变更如何组合放到中心。所谓 change algebra，可以理解为描述变更组合规则的一套运算：两项变化能否独立应用？能否交换顺序？是否依赖某个前置变化？冲突以后应当重做哪一部分？

这与数据库中的多版本并发控制（MVCC）有相通之处：不同工作可以基于各自看到的版本推进，系统在它们生效时协调关系。但两者并不是同一个概念。MVCC 关心多个版本下的并发访问；变更的组合规则还要表达修改如何衔接。即使两项修改可以交换应用顺序，结果也未必符合项目要求。

考虑一个简单例子：项目要求至少有一名值班员在岗，初始状态是甲、乙都在岗。Agent A 看到乙在岗，就把甲改为离岗；Agent B 看到甲在岗，就把乙改为离岗。两项修改可以写在不同文件里，文本合并没有任何冲突，结果却是无人值班。这类似数据库中的 write skew：各自依据旧快照作出的决定，组合后破坏了共同约束。快照和局部检查之外，还需要检查组合结果或采用更强的并发控制。[事务隔离与并发异常](https://www.postgresql.org/docs/current/transaction-iso.html)

一种可能的设计是，让 Agent 在独立快照上生成变更，系统把变更与当前主线组合，验证候选结果，再原子地发布这个确切版本。发布时需要确认主线还是验证所依据的版本；如果其他 Agent 已经推进了它，就重新组合并验证。锁可以只保护短暂的版本读取或发布过程，耗时的生成和测试在锁外完成。否则，把整个开发过程锁住，只是把并发工作重新排成了长队。

Jujutsu 的一些设计更接近把“变更”放在中心的思路：它用稳定的 change ID 跟踪经过修改或 rebase 的变更，允许把冲突作为状态保存，也用 operation log 记录仓库操作并协调并发操作。[Jujutsu 教程](https://docs.jj-vcs.dev/latest/tutorial/)、[冲突模型](https://docs.jj-vcs.dev/latest/conflicts/)、[操作日志](https://docs.jj-vcs.dev/latest/operation-log/) 这些机制提供了值得研究的方向；课堂设想的自动组合、验证和准入流程，还需要进一步设计。

再往前想，人看到的历史也许只保留有意义的大步变化，机器则保存更细的操作和验证证据。老师用“反正没有 Agent 能被开除、能坐牢，出什么问题修好就行”挑战以追责为中心的审计习惯：如果生成和修复都足够便宜，工程流程是否可以把更多精力放在正确性保障和恢复能力上？

这仍然取决于错误能否及时发现、后果是否可恢复，以及验收标准能覆盖多少真实要求。测试全绿说明已有检查通过了；如果“至少一人值班”从未写进要求或检查，就不能指望文件合并替我们保证它。人的责任会更多落在定义意图、不变量和完成标准上，系统则需要解释：它凭什么接受这次变化？

未来的项目管理也许会更像持续运行的并发控制与验证系统。要参与设计这样的系统，今天学习快照、分支、原子变更和数据库并发控制，恰恰是在积累能够向外推演的概念。

【第三方字幕校订，仅补口述；第2-8讲未标人工校对，与官方材料冲突时以官方为准】
前几次课我们讲了一些使用 AI 的案例，就像我刚才现场演示的：怎样把 AI 整合到自己的生活流程中。生活中会遇到无穷多不顺心的事，而 AI 作为一个非常强大的 assistant，可以帮你挡掉这些事情。你只需要告诉它自己真实的意图，甚至还可以把流程蒸馏成 skills，让整个过程更顺畅。

在这个过程中，我们不断看到新模型的进展。GPT-6 真的发布了，大家用上了吗？我用了一下，还是有惊喜的。虽然它在编程上的提升可能有限，还没有学会很好的品位，我经常还要骂它，所以我觉得自己可能还能再苟活几个月；但它各方面的能力确实都提升了，完成更复杂的任务时也变得更快、更省 token，我还特意测量过，的确如此。

这也是我觉得要在这门课上讨论的问题：我们为什么有时会觉得 GPT 做得不好？还是因为我们面对的是一个非常开放的 intention space。比如同一个任务，我告诉你“给我做一个国民级的应用”，每个人脑中想的都不一样，哪怕顶级产品经理也一样。AI 没有办法直接和人脑对齐，因此总会按照自己的方式漂移。

而且我发现 AI 写出的代码越来越难读了。不知道是不是受思维链变短的影响，GPT-6 的思维链非常紧凑，写的代码也非常紧凑。从 GPT-5 到 GPT-5.6，再到 GPT-6，代码写得越来越紧凑，让人越来越不想看，根本没办法 review。我们曾经会用各种 prompt，让 AI 写出符合人类工程规范的代码；但现在好像觉得自己再也不会看 AI 写的代码了，索性随它去，只要能把代码写对就行。

GPT-6 给我最大的惊喜，是它的空间感知和理解能力。我一直认为，OpenAI 对 AGI 的理解大概是：首先让 AI 学会数学，因为数学是人类世界里最难的一种语言，有一套全世界都认同的推理系统。它和软件工程里的 intention–specification gap 恰好相反：数学有全球共识，一个定理的证明是对是错，全世界都会认同，因此它是非常好的 grounding，而且数学逻辑也可以解释人类生活中的各种行为。

比如你们马上会面临“今天中午吃什么”的问题。你可能觉得这是一个必须由灵魂作答的人类问题，其实不完全是，因为大脑在不停地让各种因素投票。我会选择在逸夫楼订饭，因为这对我来说最快，下午还要开会；如果时间来得及，中午还可以小睡一会儿。我其实是在各种因素之间投票，其中还包括“A implies B”这样的关系：如果做了 A，就会做 B。这些都可以 ground 到离散数学的命题逻辑里。所以 OpenAI 应该是先让模型学会数学，现在数学已经学会了，再通过强化学习获得其他能力。

空间感知也不是模型绝对学不会的能力。比如给你一个结构复杂的鲁班锁，问沿哪个方向可以抽出第一块；或者给你一个立方体或奇怪形状的投影，让你判断哪一块与它相同；再或者给你一个六面骰子，让你判断哪个展开图与之对应。人脑会在其中进行空间想象，只要从简单任务开始做强化学习，模型肯定也能做到。

当时 GPT-6 还没有发布，我看到一个例子后就开始心疼自己的 PhD student，因为我们已经做了小半年的 3D 打印工作。在 GPT-5.6 空间感知能力很差的情况下，我们通过直接对话，已经可以生成很像样、各方面都符合规范的 3D 打印模型，也有一些比较 killer 的 application。比如一种小型光栅玩具，从左边和右边看会是两个不同的图案；我们可以通过一棵很长的搜索树，帮你做出相应的光栅纸。结果昨天 GPT-6 one-shot 就直接搞定了，我们现在还在想怎样解决这个问题。

同样，因为它既有空间感知能力，又有数学能力，在具身赛道显然可以做得很好。所以第二天就看到很多人在小红书上发：直接用 GPT-6 控制机械臂，完成抓取、叠衣服之类的复杂动作。注意，GPT-6 是语言模型，虽然有视觉能力，也只是一帧一帧地判断下一步做什么；在 prompt engineering 还没有充分展开的情况下，它已经做得相当好，达到了 state-of-the-art 的能力范围。

模型一定会进步。也许上到某一节课时，我突然就可以说这门课不用上了，这样也好，大家就可以去做产品了。到今天为止，我们当然还是需要学习一些软件工程知识的，因为 AI 解锁的是你的执行力。

正好有人问我，在 AI 时代还要不要学数据库、操作系统这些东西。我的答案也不是特别确定。我打过一个比方：回到一百多年前，汽车刚发明时，开十二公里就会出故障，所以每个司机都必须非常了解汽车的工作原理。汽车一旦坏了，你就得知道它怎样工作。在那个时代，想开车就要掌握汽车的基本原理；同样，想学 Computer Science、进入软件工程的工厂，就要学操作系统、数据库，把基础知识打好。

但想想今天我们怎样开车：在地下车库里直接说“帮我开到某个地方”，自动驾驶汽车就出发了。作为一个人，你已经不理解整个系统栈怎样工作了。最终动力还是传递到机械装置上，和一百多年前的汽车有一点相似，但中间经历的一切你都不需要知道，也可以把汽车开起来。

人工智能也可以想象成类似汽车的东西，当然它比汽车更强，替代的不仅是人的腿，还包括人的智力。那我们还要不要学？今天我的答案肯定是要学，因为学过以后，可以更好地解锁 AI 的创造力；但以后应该怎样学，我暂时也不知道。如果你们有答案，欢迎和我探讨。至少现阶段，学习还是有好处的。理解正确的概念，可以帮助你从别处借鉴知识，创造更好的东西。

今天我们就进入真正的软件工程。既然讲生成式软件工程，那么要开始做软件工程、开始 vibe coding，第一件事是什么？做作业时，你一定会从课程网站或老师指定的地方下载一个东西，再从那里开始工作；如果真的想做一个项目，第一件事一定是先建一个目录，给它起个名字，然后开始 vibe coding。

什么是一个软件工程项目？面对空目录时，你们是怎样学会该做什么的？你可能看到老师打开过一个工程项目，里面有一些文件，于是不经意间记住了项目的样子；老师或同学也可能推荐某个刚发布的东西，给你一个 GitHub 或 Gitee 的链接。网页对人很友好，你看到里面有一些文件，就知道自己的目录里也应该有这些文件。

所以，当我们说要开始一个软件工程项目时，会建一个目录，里面有一堆文件，这些文件共同构成一个可以交付的东西，最终变成产品。它可能直接在本地运行：你神奇地对 Agent 说“请帮我运行”，窗口或网页就弹出来。有个著名的笑话是：“GPT-6 太厉害了，我又做了多少个 killer 级产品，它们都位于 `http://localhost:5173`。”然后发一条 Twitter。

这时你仍然需要知识。本机可以打开，但世界上其他人打不开，因为 localhost 指的是本机。当然，你可以把 intent 和 specification 说得更清楚：在文档里说明这个东西要让全世界看到。如果不说，GPT 可能会把你当作开发者，而开发者最正常的做法就是先在本地启动 development server、看到结果，直到觉得 ready 了才把它送到远端。这些都是你们在 Computer Science 各种课程中反复学习、最后内化的知识。

项目里有文件，最后会得到一个可交付的东西。最开始学编程时，你可能在某个 IDE 里一键编译运行；后来会知道，`build` 目录里的东西都由某些命令行工具创建。大二时会开始使用 GCC 之类的命令行工具，把一个 `hello.c` 变成 `hello` binary。这就构成了一个软件工程项目。

以前的老先生喜欢问：“什么是软件？”软件如此基础、无处不在。没有软件，今天这个屏幕就是黑的，连台子也启动不了；教室里的升降桌也升不起来、降不下去，旁边显示现在的高度是 106 厘米。

软件有一个标准定义，大意是代码、文档等一切与软件相关事物的集合。但我一直说，软件是人类世界的需求在信息世界里的投影。今天看到的投影是一个目录，里面有各种东西。你知道目录里应该有什么，比如有一个 `hello.c`，还能编译出一个 `hello`，就已经是在做软件了。这可能不符合现代软件工程的 best practice，但在早期，甚至十年前，大家确实就是这样做的。

我给大家讲讲第一个 PhD student 的故事。他 2012 年进入南大，大一时发现了一种很好的学习方式。他经常去机房，因为自己的笔记本屏幕比较小，用起来不舒服。现在买一块屏幕应该不贵，甚至淘一块二手屏幕只要几百块，就可以在宿舍获得很好的编程体验；但那时的标准答案好像是去机房，屏幕也没有这么便宜。

去机房就需要来回拷贝代码，比较麻烦，所以他想出一个妙招：大一时把代码存在 U 盘里。你们多多少少可能也做过这样的事，或者中学上电脑课时，会把自己的作品保存在 U 盘里。结果到大二时 U 盘坏了，里面的代码和作业全都没有了，他珍藏的启蒙作业也不见了，有一点伤心，不过好像也没有太大关系。

我们曾经很长时间都这样管理代码。我上学时，交作业的方式是打一个压缩包发邮件；现在你们好像会在网页上上传。这些都是管理项目的方式。但今天谈软件工程，已经有了标准答案：应该使用 Git。

项目是一个目录，里面有 `hello.c`、`hello` binary、文档等内容。Git 除了能保存目录，还能保留、比较和恢复历史版本，这是非常重要的软件工程特性，后面会详细展开。有了 Git，很多事情都变得容易。

我很难想象过去还在用邮件管理项目。现在是 Agent 的时代，有十倍、百倍的生产力提升。比如让它帮我写一份 complaint，我就选择信任 Codex，什么也不管了，甚至看都不会看，只让它结束后把浏览器关掉。这件事就过去了。但过去我们确实还在用邮件管理项目。

有了 Git 以后，效率提高了很多。我们可以用 `git clone` 从远端获取作业；作业更新时，我可以直接更新远端，不需要给每个同学发一个压缩包，只要在课上告诉大家“作业更新了，请用 `git pull` 下载”。以前我的课上还有一个 `make submit`，会自动用脚本打包，再上传到课程网站，非常方便。这有点像现代的 CI/CD 流程，CI/CD 应该会专门用一节课来讲。

这引出了一个我几乎每节课都要讲的事情：今天学习变容易以后，这门课讲的知识都不重要，重要的是你们的学习意识。你们肯定看过很多 Git 项目，哪怕只是打开课程作业，也会看到一个 GitHub 链接。你们有没有留意过不同项目之间的细微区别？有的项目有某个文件，有的没有；有的项目这样写文档，有的那样写。在信号不停进入时，你其实可以据此判断应该怎样使用 Git。

我不知道大家是不是总有一种心态：老师说什么就做什么。这可能和中学有关，因为那时老师要求的事情实在太多，必须听老师的话才能全部做完。但到了现在，比如去 GitHub 学习时还带着这种心态，老师说“把作业拉下来”，你就只拉作业，那就有点像今天干活的 AI：被强化学习成老师让你做一件事时就只做这一件，绝不会多碰一点，因为这样最省时间。

如果愿意多花一点时间点进去，看看里面的各种东西，你可能突然灵光一现：“这个文档写得很好。”今天 GitHub 上到处都是巨长无比的 README，里面还有 Unicode 字符组成的目录结构框图，一眼就是 AI slop。看过很多 AI slop 以后，突然发现一个维护了十几年的老项目，文档清新舒服，README 很短，但看完以后有三个链接，分别通向你想看的东西，不需要读很长的 AI slop。你就会学到文档应该这样写。

我不知道你们有没有机会对比不同城市的路牌。我觉得这很有意思，也体现了为什么有时我们觉得中国还是 developing country：这意味着提升空间很大。很多年前，我在香港找路时留下了非常深的印象：每当我产生不确定性，比如前面有三个路口，正前方一定有一块路牌告诉我三个路口分别通向哪里。香港有非常复杂的地下系统，但从来不会让你走到岔路口却无所适从。

回到南京，有时你会在地铁站里寻找下一步该走哪个出口，需要环顾四周，甚至移动很远去找地图。如果有一个范例比你做得好，你就可以从对比中学习。我从中学到的 lesson 是：做 UI 设计时，要站在人的角度，考虑一个人来到这个页面时会想什么。不同的人可能想要 A、B、C，趋向不同方向；我希望用最少的方式把 A、B、C 全部呈现出来。

README 也是一样。大家都会让 AI 生成充满 AI slop 感的 README，但看过几个好的以后，就会写 README 了。有了 AI，你还可以马上问它：“为什么这个 README 比那个好？为什么我看到这个项目的 README 时没有 AI slop 的感觉？”它会告诉你。

这也是我对“上课耽误学习”的理解：现在课外的信息量和信息密度，已经远远超过任何课堂能做到的事情。打开一个成熟的 GitHub 项目时，你面对的是工程师十几年的心血。也许十年前项目曾崩溃过一次，于是做了一次大版本重构；工程师发现以前的 practice 不够好，才有了今天呈现在你面前的成果。但传统教学没有教大家怎样利用这些海量、高信息密度的东西，大家也没有准备好拥抱这样的知识。

我现在做老师，可能就是因为有一种惊人的注意力。大家也应该训练这种注意力，在看到一个东西时快速判断。面对任何问题，在看现成答案之前，我的大脑会先忽略眼前的东西，想一遍：如果自己解决这个问题，我会怎样做？然后立即比较眼前方案和脑中方案哪一个更好。如果我做得更好，就认为眼前的是 slop；如果对方做得更好，我就很惊喜，追问它为什么比我做得好。

养成这个习惯其实很恐怖，因为你无时无刻不在疯狂接收外部信息。能留意生活中的各种小细节，就会不停提升。很早以前就有人推荐过一种读 research paper 的方法，它也适用于学习任何课程，包括高等数学、计算机系统基础，叫 virtually implement。

面对一个具体问题或需求，先在脑中自己做一遍，再看会得到怎样的结果。如果你的方法和作者一致，很好，说明已经掌握了这个知识；如果不一致，还有两种情况。一种是成熟教科书上的方案比你的更好、更精巧、更简洁，你会追问他为什么能想到，于是它变成你知识的一部分。另一种是真正的惊喜：你的方法比他还好。也许一万次才会有一次这样的体验，但它会给你很强的正反馈，让你突然想去做一些好玩的东西。

所以我觉得，在 AI 时代更应该对细节保持注意力。看到各种各样的 Git repo、读别人的东西，甚至读 AI 生成的东西，都要感知其中的细节。以此开头，我们就可以讲 Git 的具体内容了。

首先，为什么要 Git？GitHub 让分发代码变得前所未有地方便。创始人建立 GitHub 时可能已经想到了这件事，但没有意识到它会成为 AI 时代的底层基础设施。npm 包、各种 Neovim 配置，大多都放在 GitHub 上。

上周末我参加了推免面试，你们一两年后也会来到这个场合。我问大家“什么是 Git”，大家多多少少都能说两句：可以从 Git 上下载、分发代码；有的同学还能讲到 Git 管理项目目录的快照。能讲一些就可以，评价取决于你能讲多少。至于 `git rebase`，被问到的十位同学都没有答出来，这也在意料之内。

比较出乎我意料的是，我问：“`git merge` 发生冲突以后，会观察到什么？”你们观察过吗？比如老师更新了作业，而你已经把本地代码改得面目全非。这时你可能让 Agent 来处理，它自动把冲突修好，告诉你测试都通过了；我现在也会这么做，只看一眼结果似乎没问题。

这时，惊人的注意力就有用了。如果愿意在发生冲突时停下来，尤其作为学生，总想着“反正只花一秒，再学一点也没坏处”，就会看到很神奇的内容：很多等号和尖括号。merge 冲突并不会自动 resolve，责任会交到你手上；过去，这个责任会交到每个开发者手上，开发者有义务解决自己遇到的冲突，因此必须能看到冲突。

站在 Git 设计者的角度，假设一个文件原本每行都是 1，一个人把第二行改成 2，另一个人把第二行改成 3，到底该用 2 还是 3？Git 不能只说“对不起，冲突了，我不能合并”，然后躺在那里，否则人的负担会很大。怎样让人判断这一行该选 2 还是 3？这里和刚才地铁标识的例子遵循同一个 first principle：在一件事发生的地方，最好把处理它所需的全部信息都放进来。

所以，以文本方式查看时，你会看到由等号和尖括号组成的标记，以及 incoming、HEAD 等字样；冲突两侧的代码会同时显示在这里。如果使用 IDE，上面还会多出 `Accept Incoming Change` 之类的按钮，你可以在 IDE 里自己 resolve，决定保留哪边。完成后再创建一个 commit，把冲突解决掉。

你只需要投入一点注意力，看过一两次就会留下印象，至少能说出“两边冲突的代码会显示在一起”。但面试时大家对此答得不好，要么是没有真正用过 Git、没有开发过，要么是用过却没有留意。即便用 Agent 开发，只要让不同 Agent 在不同分支工作，也很容易遇到 conflict。所以比较重要的，一是多用，二是努力拥有更好的注意力。

我们来讲讲 Git 是怎么来的。把目录放在 U 盘上、每次打一个包，肯定不是很好的方式。但据我观察，我上学时同学们确实是这样做的。当然我上学比较早，那时 Git 还没有流行。大家会创建“作业 V1”“作业 V2”“作业最终版”，每次复制一个目录。这是一种非常直觉的做法，也的确可以找回旧文件。新手阶段出现误操作很正常，万一哪天手滑改错了，就会想回到上一个版本，看看之前是怎样写的。这不就是一个需求吗？

从这样的需求出发，你自己就能发明出类似 Git 的东西。项目就是一个目录，代码、文档、intent、spec、implementation、测试用例等各种东西都放在一起。如果能管理这个目录的版本，不再建立“作业一”“作业二”“作业三”，而是始终只有一个作业目录，再提供命令行工具列出作业的版本、把当前目录切换到另一个版本、回到过去的某个版本，就已经发明了一个简化版的 Git，哪怕还没有分支、合并和冲突这些概念。

用着用着，你会自然而然地发明出那些概念。比如需要和室友同步时，就会出现两个人同时修改一个文件的情况。你们坐下来想“一起修改同一个文件应该怎么办”，就可以继续发明 Git。当然，这也体现了人类的局限性。

Git 之前，我们还用过一个你们可能听都没听过的工具，叫 SVN，有 check-in、check-out 等操作。SVN 和 Git 的设计不同。SVN 说，我们存储的是项目的变化：先有一个最初的版本，此后文件每改一行就保存一个 patch，再改一行再保存一个 patch。这看起来是非常高效的实现，但随着项目增长，这种高效反而把大家拖入了泥潭。

Git 的模型要干净得多。回到 first principle：我想回到过去的某个版本，就应该一秒钟回去。如果每次保存的都是 delta，想回到一个很早的版本，就得把变化逐个往回退。当然可以用缓存之类的方法优化，但感觉这条路确实走错了。

Git 基本上就是这样来的。它的作者也是 Linux 的作者 Linus。1991 到 2002 年间，Linux 的维护方式有点像“作业 V1”“作业 V2”：大家在邮件列表上发补丁。比如我修改了 `a.c`，说自己有一个新版，就把它发到邮件列表；maintainer 看到后，把它放进核心仓库，再 release 新版本。后来他们还用过 BitKeeper 等其他工具，直到 Linus 终于受不了，认为应该有一个绝对简单、非常好用而且概念正确的版本控制工具，于是在 2005 年做出了 Git。所以 Git 比我们想象得年轻一些。

有兴趣的同学可以去看《Pro Git》，当然现在直接让 Agent 帮你看就行，不需要自己再读。我读书时，我们都是看过这些文档的。

我们需要项目级的时间回溯。每个人都会犯错误，只要能从 Git 历史里把原来的内容捞回来就可以了。你们可以试着用这种方式思考：从已有经验和自己的需求出发，推出下一个概念应该是什么样。你会发现这就是数学推理。我上课这样讲下来，每句话都和前面有逻辑关联，而逻辑关联多多少少都有数学上的联系。所以 OpenAI 认为要先把数学训练好，数学训好以后，模型也许能解决其他所有问题。现在这件事可能真的要成真了，我觉得连品位也可能是能解决的。

接下来还是具体讲讲什么是 Git。我建一个空目录，打开 terminal。今天要开启一个项目，就执行 `git init`。它会告诉你一些看起来奇怪的信息。这时有两种选择：让 Agent 帮你处理、回答不懂的问题，或者把信息忽略掉。显然，前一种学习方式更高效。

执行 `git init` 后，目录里会出现一个 `.git` 目录。`.git` 默认不显示，所以你看不到它。这就是全部了：做完 `git init`，项目就变成了一个由 Git 进行版本管理的 repo。之后可以从远端下载代码，也可以把代码推到远端。

最基础的操作是，假设有一个 `hello.c`，可以执行 `git add hello.c`，再通过 `git status` 看到工作区里有这个文件以及相关提示。Git 很重要的功能是创建项目快照，使你能在任意时间之间穿梭。我们可以创建一个带消息的快照，这很重要，也体现了软件工程的智慧。

以前用复制粘贴的方式，把目录命名成项目版本 V1、V2、V3，或者作业 V1、V2、V3。Git 的世界不是这样。我看到很多同学虽然在用 Git，却把它当成作业 V1、V2、V3 来用，但这不是 Git 推荐的 practice。

长期软件工程实践推荐的是：每次对项目做了改动，比如修改一个文件、修复一个 bug、增加一个功能、调整某个脚本或文档，都应该及时执行一次 `git commit`。执行后会打开文本编辑器。这里打开的怎么是 Nano？你可以在编辑器里说明自己做了什么，保存以后，提交就成功了。

这些都可以在现有项目里观察到。看看大家怎样协作：有些 Git 提交比较大，加入了一个 feature；有些比较小，只 fix 了很少的内容。面对这样的新工具，理解它的 best practice 还是需要花时间。你不能把所有事情都交给 AI，多多少少还要知道为什么这样做，什么时候应该 `git add`，什么时候应该 `git commit`，commit message 应该怎样写。

真正需要的是随时学习。碰到一个新东西时，可以追问：“你刚才做的符合 best practice 吗？”比如问刚才的 `git commit` 是否符合 best practice。配合豆包输入法，真的只需要一秒钟，但模型会给你很多解释。

它说这个 commit 不太符合 best practice，主要问题在提交信息，其次代码本身也有问题。提交信息的可读性有问题，因为我故意写了一个 “I added some cool stuff”，完全看不出做了什么。

Git 存储的是项目版本的快照，但项目本身还是从 V1 经过一次修改变成 V2。Git 鼓励在 message 里描述这次修改做了什么。沿着 message 一直读下去，你就知道项目如何发展到现在：修过多少 bug、加入过什么需求、经历过怎样的重构。你可以从 message 里看到项目的历史轨迹。这是一种好的软件工程 practice，让别人更容易理解你的项目。

如果每个提交都是 “I did some cool stuff”，那么有一万个提交后，commit message 就变成了 slop。如果一万个提交都这样写，commit message 这个特性就不应该存在，直接从 V1 变到 V2 就够了。不同情况下应该使用不同的 commit message，比如一个版本即将收尾时，可以用 message 说明要 finalize 这个版本。

Git 甚至允许你在完全不改代码、V1 和 V2 内容相同时再做一次提交。这件事可以吗？直接提交时，Git 会拒绝没有修改的空提交，但是 Agent 知道怎样创建它。你们需要保持惊人的注意力，继续追问：“从理论上说应该可以吧？比如我要发布一个版本。”这不是 best practice，所以尽量不要做；但如果确实需要，也可以故意创建一个 empty commit。

empty commit 可以在没有改动时产生一次提交，用来触发 CI 或 workflow。比如我要 release 一个版本，虽然 Git 可以直接在上一次 bug fix 的提交上打一个 `v0.1` tag，但也可以强行创建一个没有改动的提交，用来表示 finalize：为 `v0.1` freeze 所有内容。这样就把 bug fix 的提交和 finalize 的提交分开了。偶尔这样做是允许的，但显然不能创建大量 empty commit。

所以在 Git 里，基本模型很简单，学会 `git add`、`git push`、`git pull` 等命令就能开始使用；但水面下真正的冰山是各种 best practice，而每一个 best practice 都是血和泪的教训。反过来想一想，为什么 message 要这样写？随手问 AI，或者和更有智能的模型讨论这样做有什么好处。

很多时候，模型的表现比我好。这些知识我可能知道，已经内化在脑子里；给我两个小时，我也许能写出一份很好的解释。但我的智力、精力和注意力都有限。比如现在上课，为了专注地和大家交流，大脑中负责思考的那部分容量就不太够。所以很多时候，我在课上讲授概念时处于 System 1 mode，讲出来的不是最好的版本。

如果课后把“为什么 commit message 要这样写”之类的问题拿去和 ChatGPT 聊，就像我一开始说的：求助于一个自己无法掌控、但 somehow 知道世界上所有东西的存在。它能很好地把这些概念讲清楚。

接下来看看这些约定俗成的 best practice。我先做一点不符合 best practice 的事，这也是你们非常常见的操作。这里有一份应该可以编译的 `hello.c`，编译后，得到的 `hello` 成了 untracked file。你们在 tutorial 里见过一个很好用的命令，叫 `git add .`。如果改了三五个文件，就不需要逐个执行 `git add a.c b.c c.c`，直接 `git add .` 就可以全部加进去，然后提交。Git 不会阻止你这样做，这是完全合法的。

我再问问 Agent：“这个 Git 提交有什么不符合 best practice 的地方吗？”它看了一遍，按严重程度排序。第一，提交信息毫无信息量，都是主观废话。它还会告诉你应该怎么做：用祈使句和现在时描述变更动机，例如 “Fix off-by-one in array length check”。还可以考虑使用 Conventional Commits 的前缀，你能在更多项目里看到这样的 commit 方式。

第二，提交粒度和内容混杂。它开始批评我了。首要问题仍然是提交信息毫无信息量，接下来才是提交粒度：`hello` 是编译产物，根本不应该进入版本库，而应该加入 `.gitignore`，由构建系统生成。

所以，Git 的使用方式和“作业 V1”“作业 V2”不一样。作业 V1 和 V2 的目录里都会放着编译出的 EXE，但 Git 为了防止 repo 膨胀，通常不应保存这些产物。尤其当项目有一万个文件、一百个合作者时，每个人的环境都不一样，build 出来的东西也不一样。编译得到的文件可能带有日期、hash，甚至本机指纹，所以每次得到的二进制文件都可能不同。

如果把这些文件放进 Git，下一次就可能发生冲突：你这里有一个 `hello`，对方也有一个 `hello`，哪怕源代码相同，编译结果也可能不同，更不用说用不同源代码编译出的 `hello`。这会产生二进制冲突，而二进制冲突很难合并。如果生成的不是程序而是图片，图片又应该怎样合并？图片比较特殊，但同样说明 generated file 的处理有很多 best practice。

我让 Agent 看看它会怎样处理，不知道会发生什么。它思考了比较久，我一度以为网络断了，其实没有。最后它说：丢弃 empty commit 和编译产物这两段历史，把 `main` 分支重写为两个有意义、单一职责的提交。

它还贴心地发现当前历史没有 remote，也就是这个 repo 没有和别处同步，不会影响其他人。如果其他人也持有这段历史，重写历史就是一件比较糟糕的事。确认没有别人以后，它把整个项目改好了。

如果你的注意力足够好，会发现它换了一套 commit 方式。提交先有一行 headline message，后面还可以有更多说明。这里面有很多好玩的细节，比如在 message 里写 `Fixes #3`，GitHub 会自动 close 对应的 issue。只有反复使用，才能体现初学者和有一定经验者之间的区别。

当然，现在是 Agent 时代，你们都是 Agent Native 的人，肯定不会再用古法。我觉得 `git status` 之类的命令都已经成了古代手艺。现在一定是直接使用 Agent，不需要知道每个具体命令是什么，只要有“Git 能做什么”的概念，就可以要求它按照 best practice 完成。

这也带来一个问题：你根本分不清是自己真的能做，还是脱离 Agent 就做不了。但也许这并不重要。为了提高学习效率，可以要求 Agent 在做任何 Git 操作之前，逐个检查文件的变化。

比如我随便写一份不能编译的代码，再让它提交。我不知道模型会怎样处理，但它很聪明，甚至比你聪明。人改作业时很容易想：“只改了一个字，不要紧，直接提交吧。”模型见过很多好的工程项目，也读过很多软件工程书，所以它知道当前不建议直接提交，还顺手把代码修好了。

当然，这可能也受几个 prompt 影响。比如我的 system prompt 可能要求它使用中文；又因为我在上课，所以要求它解释得更详细。它给出了很好的解释：Git 提交应当是一个完整、自洽的快照，编译不过的代码相当于让 repo 处于坏状态。

它还提到了我在即兴上课时没有想到的内容：如果有人要使用 `git bisect`，每次提交能否构建和测试就尤其重要。Git 还有一个很有意思的功能叫 `git blame`，我很喜欢。比如对 `hello.c` 执行 `git blame`，它会告诉你每一行代码来自哪一次提交、是在哪里修改的。

哪怕只有一条线性的历史，也可以做很多有趣的事情。AI Agent 的一句解释，一下就把 Git 打开了。我们可以做二分查找。你们可能会在保研或工作面试时被要求手写二分查找，也可以把 Git 的提交历史想象成一个很长的数组。

假设在当前版本发现了一个 bug，它可能不是由当前代码引起的，而是过去某次提交引入的。这时只要有测试用例，或者任何能检查出 bug 的东西，就可以对整个 Git 历史做二分查找。历史里一部分提交是 OK 的，另一部分不 OK；某一刻引入 bug 后，从那一刻开始的提交就都无法通过，而之前的提交应该都是 OK 的。这就像在一个前缀全为 0、后缀全为 1 的数组里找第一个 1，可以用二分查找。

这就是 `git bisect`。找到出错的提交以后，还可以用 `git blame` 知道是谁改了这一行代码，以及当时发生了什么。Git 里有很多这样的软件工程实践。

所以我一直觉得，软件工程可能不需要在课上讲太多，应该把时间留给你们，让 Agent 在实践中告诉你。每次提交的代码都应该能够通过构建和测试，这是非常基础的要求。大家也会觉得本来就应该这样，经过反复强化和潜移默化以后，也就真正掌握了。Agent 还说 `AGENTS.md` 可以提交，符合 best practice，我就不再继续演示了。

好消息是，在 pre-LLM 时代，新同学进组时通常都会带来一些使用 Git best practice 的“高血压时刻”。比如欢迎你加入一个研究项目，让你新建一个 Git repo；第一周给一个很简单的任务，搭起架子、运行一两个东西。一般我打开 repo 后就会进入高血压环节。

比如我会看到 `dist` 或 `log` 被提交上来。log 也是 generated file，不应该提交。还有 VS Code 的个人设置，里面甚至会包含 `C:` 盘下某个位置的硬编码路径，显然无法在其他地方复现。更让人高血压的是，审稿时可能看到仍处于 active 状态的 API key；如果发现这是 DeepSeek 的 API key，我就知道这大概是一位中国兄弟。

有 Mac 的同学还会在不经意间提交 `.DS_Store`。在 macOS 上，如果用 Finder 打开一个目录，它会自动留下索引，例如展开过哪些子目录，并把这些内容放在 `.DS_Store` 文件里。这个文件以点开头，默认隐藏，所以看不到。我的 `ls` 还会贴心地给它显示一个苹果图标。

因为看不到它，执行 `git add .` 时就很容易出问题，`.DS_Store` 会被 Git 跟踪。这种行为本身也合理，因为以点开头的文件可能是配置文件，例如 `.github/workflows` 这类约定俗成的内容，不能默认全部忽略。但 `.DS_Store` 是经常变化的临时文件，不应该提交到 repo。

规则并不是简单的“所有 generated file 都不应该提交”。比如 `package-lock.json`，或者用另一套工具链生成的 header，有时应该 check in。把生成的 header 放进 repo 后，别人即使没有安装那套工具链、也不需要下载很多依赖，依然可以编译项目。所以这里没有绝对规则。

我自己做软件工程研究。一个非常标准的软件工程研究，就是检查 Git repo 是否满足这些 best practice，不满足时给出 warning。像 `.DS_Store` 这样的情况需要一条规则，许多规则组合起来，最终做成一个小工具，在 Git 提交前告诉你是否符合要求。

但这些工具都被大模型杀死了，因为大模型可以非常耐心地帮你检查，还会加一个 emoji 让你开心一点、缓和情绪。作为导师，如果把学生叫到办公室指出项目不符合软件工程实践，我首先会高血压，其次还得表现得 nice 一点。即使我情绪正常，只是在教授知识，学生也总会有压力，觉得老板批评自己做了不该做的事，而且这些是自己本来应该知道的。AI 确实把同学们从这种无法控制的力量中解放出来了。

而且 AI 真的很强。最近我在做一个更严肃、希望把每个细节都做好的项目，面临了一个选择。Git 提交前有一种机制叫 hook。大家可能用过各种 hook：可以 hook 程序的一次函数调用，在调用结束时做一件事；也可以在 Agent 里加入 hook，在某件事发生时执行操作。

比如我有一个 hook：Agent 完成工作、需要我输入时，就播放“叮”的提示音。现在可以直接要求它：“帮我配置一个全局 hook，在 Agent 需要输入时叮一声提醒我。”Claude Code、Codex 和 pi 都支持这样的 hook。

我也可以通过 Git 的 pre-commit hook 做检查，因为这个项目的工程标准更高。我可能有几十条 checking rules，需要给每条规则命名。比如同一条规则可以写成 `[TYPO-CHECK] Docs should be typo-free`，也可以写成 `[typo-check] Docs should be typo-free`，到底应该选全大写还是小写？从使用角度看，只要这句话本身没有 typo，两种都没有问题；但到底怎样写更好，是一个两难问题。学习和生活中会遇到无穷多这样的问题，如果每个问题都稍微多问一句，就会增加很多知识。

刚才让 Agent 配置提示音时，它处理了一会儿，然后说完成了。我一开始没听到，后来好像听到很轻的一声，再试一次又没有。不过它已经理解了我的意图，让它继续修就行，这里我就不修了。

关于规则名，我让 GPT 解释了一下。它说 `TYPO-CHECK` 是一个固定规则的标识，还给出了一些 RFC 引用，并分析了为什么我在心理上会觉得全大写更有力量。如果你们在学习 Git 时也能多问几句，把每个细节都做好，一定会成为一个 a lot better person。

接下来要开始学习 Git。现在 `AGENTS.md` 和 `ARCH.md` 都有了，我们要了解 Git 到底是怎样工作的、它的底层原理是什么。我会推荐大家去看我在操作系统课上讲 Git 的那一段，这里没有必要再完整讲一遍，只讲一个开头。

Git 是一种持久化数据结构，它持久化的是目录树。我们不断为目录树创建快照，得到版本一、版本二、版本三、版本四。从最基础的想法出发，假设一个很大的项目目录树里有 `A.txt`、`B.txt`、目录 `D`，而 `D` 里还有许多文件。现在要从 V1 创建 V2，不需要把所有文件都复制一份。假如只修改了 `B.txt`，当然需要创建一个新版本的 `B.txt`；为了用最小的代价记下整棵树，只需要复制从 `B.txt` 到根的路径，`A.txt`、`D` 等没有变化的部分仍然用指针指向旧版本。

这就是持久化数据结构。即使项目里有一百万个文件，目录也不可能特别深；从渐进式披露的角度，也没有必要建立一个极深的目录。目录树有足够的 fan-out；每增加一级索引，可容纳的条目数都会指数级增加，很快就能把所有类别分完。因此，只需要创建一个非常小的增量，就能得到一个版本的快照。

Git 底层的 `.git/objects` 里有各种各样的 object，它们就是按 hash 索引的普通文件，包括目录节点、文件节点，甚至 commit 节点。Git 有三类主要对象：commit object、tree object 和 blob object。blob 就是 binary，也就是字节序列。这个数据结构可以不断向后生长，问题就解决了。从 first principles 出发，一个大学生完全有可能设计出这样的东西。

但这只是纸面上的讲解。Git 真的是这样实现的吗？老师讲的 commit object、tree object、blob object 真的存在吗？如果版本发生分叉，我们可以从 V1 创建另一个版本 V1'，世界由此分叉；分叉以后合并又会发生什么？当你开始想象这些问题，根据计算机科学定律，你想要的东西就一定有人做。

我以前上课也会用 Learn Git Branching。这是古法编程的巅峰之作之一，它以可视化方式展示 Git 怎样工作，甚至模拟了各种命令。比如执行 `git status` 后可以看到一个文件被修改了；执行 `git commit`，右边的动画里就多出一个版本；用 `git checkout` 点击某个版本，还可以看到版本的变化。它用这种方式教你 Git 的工作原理。

到了今天，我觉得这些东西可以直接 vibe coding 出来。虽然 vibe coding 的质量可能还没有那么好，但我直接做了一个可视化整个 Git repo 的工具。这里甚至还有一些未提交的代码。GPT-6 虽然有视觉能力，但 one-shot 直出还是产生了一些 slop。

我给它的提示词是：用 Node.js 实现一个 `gitv` 命令行工具，把一个真实的 Git repo 里的主要概念彻底、完整地可视化展示出来，可以使用 Git 命令，但任何 object 都要来自文件系统中的真实文件。这和刚才的 Learn Git Branching 不一样：后者是模拟出来的，自己建立了一个 Git 模型；今天我们有办法在一个真实、live 的 Git repo 上直接看到发生了什么。工具要从真实文件的原始 bytes 出发，展示它们一步步怎样解析、解析成了什么；还要持续监听目录中 Git 的变化，并在发生变化后用动画展示 repo 的变化。

我先删除一个文件，你看，右边的文件马上没有了。再看这棵树，这是 `main` 分支，和我刚才画的一样。最早的一次提交叫“I did some cool stuffs”，里面有一个简单的 `hello.c`。这个文件确实来自 `/tmp/hello/.git/objects` 下的一个 object，真的是 blob object。你可以看到它的原始字节序列，工具会帮你解压缩。对于很小的文件，压缩反而是一种浪费：磁盘上是 31 字节，解压后是 23 字节。解压后的内容以 `blob 15` 开头，说明这是一个大小为 15 的 blob object，后面就是 `int main` 等正文。

除了这样的 blob，还有 `hello` 二进制文件。它的 blob 大小是 158 字节，以 `7F ELF` 这个可执行文件的 header 开头，你也能看到它的内容。它还有 tree object，同样可以查看磁盘上的原始数据：52 字节解压出 43 字节。tree 中的 `100644`、`100755` 代表文件的 mode，里面有 `hello.c` 和 `hello`。解压后能看到每一项的 mode、name 和它指向的 object；这个版本的根 tree 里有两个文件，一个 mode 是 `100755`，另一个是 `100644`。

这些指针链接都可以在界面中拖动查看。视觉效果还不完美，因为它基本是 one-shot 直出，我只在第二个 prompt 里让它去掉了一点东西，其余问题都没有修。但我们已经可以在这里探索 Git 的方方面面。

比如，我让它创建 A、B 两个分支，左右两边会实时同步，并直接出现动画。这里可以看到 `.git/refs/heads/A`：分支就是 refs 下的一个文件，本质上是指向 commit 的指针，而 `HEAD` 是指向这个指针的指针。界面会显示它在磁盘上的字节、它所指向的 commit object，以及 commit 指向的 tree object。分支 A 对应一棵树，根目录中包含新版本的 `hello.c`；分支 B 也一样，指向另一个修改过的 `hello.c`。视觉效果虽然不好，但我相信多对话几轮就能搞定，得到一个近乎完美的 Git visualization。

我还可以让它展示 merge conflict。假设两个开发者都对同一份代码不满意，各自重构了它，就会发生冲突。A 在这里，B 在那里；把 A 拉到本地时，就能看到 `hello.c` 的冲突现场。未提交区域的 index 里实际上悄悄保留了三个版本，分别叫 base、ours、theirs，这是平时看不到的；工作区里的 `hello.c` 则带有尖括号形式的冲突标记。

让工具 resolve 冲突后，那些临时条目就没有了。merge 创建了一个新的 commit object，它有一个 tree、两个 parent 和 author。界面正确保留了所有指向关系，tree 也指向解决冲突后选定的版本。

今天虽然好像在讲 Git，其实讲的是 best practices，这里面还有很多内容。如果刚才有注意，你会看到 AI 给出的 commit message：前面的都是英文，都是一行总结加上详细解释；后面 AI 开始自由发挥，混用英文和中文。不过还好，它仍然遵循了带 scope 的格式：先说做了什么，给出一个总结，再有 message body。

这种格式是有标准的，叫 Conventional Commits。它的 specification 很短：commit 必须以 type 开头，例如引入 feature 或 fix bug；也可以带 scope，后面接冒号，而且冒号后一定要有一个空格。这些都是规范。

我和同学合作时，经常会进入高血压时间。比如 Markdown 文档中的英文和中文之间要有一个空格。我不知道大家什么时候开始采用这个 convention，但好像都会用。这对我已经是肌肉记忆。最难受的是，一个文档里有些地方有空格、有些地方没有。哪怕统一不留空格，我都会认为你是在遵循某种 convention、保持一致；但如果不一致，我真的很头大。

AI 会把这些细节做好。这些工程细节是为了让工程师面对更大的项目时保持一致和规范：代码要以相同方式排版，文档自然也要以相同方式排版，人维护起来会更容易。虽然在 AI 时代可能不再那么重要，因为 AI 都会帮你解决。至少用了 AI 的学生不会生成那种不一致的 slop。

这里还有很多 best practices。比如可以在网上找到“Commit Often, Perfect Later, Publish Once”等经验。回去读这些文档，让 AI 帮助你，就能学到更多。

为什么要及时 commit？因为在复杂项目里，修改得越多，出错的地方就越多。小项目刚开始时不要紧，一次提交两三千行代码也可以；但是项目有错综复杂的关系以后，一个大 commit 可能会 break 多处内容、引入多个 bug，后面还要再引入多个 fix。假如 V2 是一个一万行的 commit，之后修了一百个 bug，你都说它们是 V2 产生的，就很糟糕，甚至修不过来，也不知道 V2 到底修好没有。

如果每次 commit 都很小、只做一个修改，就冤有头债有主：这个 bug 是这次提交引入的，修完也就修完了，两个 commit 可以配对。这样既有审计能力，也能降低丢失工作的风险。假如你的电脑物理损坏，而修改还没有推到远端，就会丢失；做一个小提交后立即 push，就能在互联网上得到备份，电脑马上坏了也不要紧。

AI 很清楚这些做法。它知道可以 review、revert，也可以用 `git bisect` 二分查找问题。后面可能还会讲 hooks 和 CI。

如果你们有惊人的注意力，还会观察到：项目可能托管在 GitHub 或 GitLab 上，AI Agent 会尝试调用 `gh` 或 `glab` 命令；如果看到 `command not found`，它又会退回古法编程，开始写 Git 命令。GitHub 很 popular，也很好用，因此值得为它做一个命令行工具。

Git 管理了许多代码快照，但 GitHub 上还有 issue，可以发布文本，也可以对代码写 comments；这些 non-Git 的内容不会随着 Git 一起 persistence。如果要管理它们，可以用命令行工具 fetch issue、查找 assign 给自己的 issue，并在登录后 close issue。这样的命令行工具对 Agent 很好用。安装 `gh` 后，就可以在 Agent 里设置一个 goal，让它完成很长的任务，同时要求它做小步、可审计的提交，并规定分支规则、linear history 等。我的项目里就有大量这样的提交，很多时候我已经不管它们了。

我们讲了很多 Git，但这门课讲的还是软件工程。最后这段总结更加重要：Git 本质上是一个软件，它告诉我们要把项目组织成由 atomic change 推进的一系列快照。这是今天要记住的事情，其他一切都是从这句话推出来的。

组织一个软件项目时，需要管理很多快照。这样就可以随时开启一个新分支做尝试：失败了，就安全地扔掉；成功了，就合并进来。甚至可以同时推进多条主线，再通过合并完成，而不会互相干扰。古法做大作业时肯定有这种感受：需要改好几个地方，改着改着很可能就乱了，这个部分和那个部分不断冲突。

项目管理的本质在于，人类没有办法处理一团混沌。面对许多需求和代码，如果一次做一大波，就很难管理。因此很自然地，要把需求分解成可以理解、可以审计的小任务，一小步一小步地推进。出了问题可以 bisect，可以 blame；协作时可以 blame，发生冲突也容易解决。若多个小任务从同一个公共祖先出发，每一个 commit 都很小，那么发生冲突时，就能知道是哪个小提交冲突，其余不冲突的部分也更容易合并。

有些项目会要求 linear history。合并可以产生一个有两个 parent 的 merge commit，分支也可以不断分叉、合并，最后形成典型的 Git 结构；但现在大家似乎更流行 linear history。反正都是 AI，resolve 和 rebase 都很容易，于是可以强制要求整个 commit history 看起来是线性的。这并不全是优点，但至少对目前维护项目来说，历史更容易追溯，对 cherry-pick 和 blame 也更友好。

在无限能力的模型到来之前，把 Git 记录拆分好仍然有益。这样很容易找到某次修改是谁引入的，AI 维护项目的效率也更高，还能省一些 token，因为有些文件它不必再读取。

再分享一些经验。虽然知道项目要小步向前推进，但具体应当怎样管理？在架构设计阶段，我会先用单线程，用一个智力较高的模型和我讨论。这很重要，因为如果软件设计得不好，后面就会有无穷的迭代。第一节课展示的例子里，我把组件库的接口定义得非常好。

我为什么这么信任 AI 写的代码？这个项目中有很多互相关联的组件：程序运行并产生结果；拖动进度条时，不仅要联动程序编辑器，也要联动可视化界面。但我把绝大部分接口都设计成 functional 的，也就是 pure function。比如 trace 是程序的一个 pure function；我还有一个标准的程序 derivation graph，要求它按这种方式展开。

所有会在全局互相影响的状态，我都注册到一个全局位置。比如光标的位置会怎样影响可视化，以及菜单条等，都被组织成非常干净、非常小的状态。因此，这个 playground 的核心共享状态只有十几行，再加十几行组装代码，剩下所有东西都是黑盒子。

我直接要求 Agent 在设计这些 visualization 时，禁止查看任何库函数的实现，只看接口。因此它非常节省上下文，只用几万个 token 就可以做出这样的 playground。

这样的架构设计完成后，我会开三个或更多 terminal，并在 `AGENTS.md` 中规定明确的协作规则。例如，不需要调用视觉模型检查，因为 Agent 很喜欢这样做，会花很多 token；也不调用浏览器任务，而是在旁边另一块屏幕上放一个能实时刷新的浏览器。我同时开三个 Agent，哪里不满意就告诉它们；你可以肉眼看到右边的东西不断变好，最后问题就解决了。

这是一个在 Agent 能力范围内的项目。我非常确信 Agent 的能力会不断增长，越来越多的项目能通过这种比较轻量的讨论交给 Agent 完成。这是一件非常可怕的事：如果 Agent 快了一千倍，我们又该怎样管理版本控制？这个问题可以留到下一节课讨论。今天下课。

# 实验 (1)：会成长的个人助手

本课程的实验是建议性质的实验，不记分。你可以直接将实验要求交给模型，配合一个 Grill Me 之类的技能，让它追问你的需求，再一起完成实现。怎样把“我想要”变成可以验收的软件，也是实验的一部分。

## 1. 背景

课堂上，我们已经展示了通过浏览器自动完成日常信息化流程的案例。有了 Agent，我们可以期待更多：让个人资料、邮件、办事大厅和手机连接起来，把一次成功的尝试变成随时可用的能力，并且在被你纠正之后，下次能把事情做对。

## 2. 实验要求

🗒️**实验要求：实现会成长的个人助手**

实现一个持续为你工作的个人助手，具备以下五项基础能力。可以基于现有 Agent 配置工具、脚本和技能；语言、模型和交互形式不限。

1. **个人数据库。** 能索引、检索你的资料，并随资料变化更新索引，回答时能定位到原文。格式不限，推荐 Markdown + 目录结构：你可以直接阅读、修改文件，也更容易观察 Agent 读了什么、写了什么，以及如何组织记忆。
2. **持续关联 smail 邮箱。** 能持续获取新邮件、关联历史往来，结合个人资料拟好回复草稿。你可以编辑草稿，再直接发送；发送的应当是你确认的最终版本。重复检查邮箱不应重复处理或发送同一封邮件。
3. **办理 ehall 事务。** 能在 `ehall.nju.edu.cn` 中查询信息，并完成至少一种事务的材料准备和表单填写。行为要保守：提交前展示关键字段及后果，由你明确确认；退课、撤销申请等操作尤其不能自行决定——万一 Agent 把你的课都退了，你就完蛋了。
4. **手机端联动。** 能方便地从手机发起任务、查看进度、编辑草稿和确认操作。可以做 App、网页，也可以借助手机已有功能。例如，在 Mac 上用 AppleScript 操纵备忘录，再通过同步与手机联动。任务不能依赖桌面端某个始终开着的对话窗口。
5. **能力组合。** 上述功能应当能共享必要的上下文，完成跨工具的任务。如何组合由你决定，但至少做出一条你愿意反复使用的完整流程。

例如，收到办事通知后，助手检索个人资料，整理待补材料，在手机上向你追问，准备 ehall 表单和邮件草稿；你核对后分别提交、发送，结果再归档到个人数据库。也可以设计完全不同的流程：**这是一个发散的任务，组合方式本身就是你的设计。**

将成功流程和你的纠正保存成可阅读、可修改的脚本、技能或记忆，用 Git 管理实现和规则。例如，你指出“不要把报名截止时间当成活动开始时间”，助手应当能在新会话中将这条规则用于另一份通知。

## 3. 为什么要布置这个实验？

因为如果你直接把这些需求 (在明确和不明确之间) 给 AI Agents，你将大概率得到一团乱麻的 AI slop——它也许的确可以工作，但每一次修改都会消耗大量的 tokens，Agents 会在泥潭中反复阅读代码、试错，像极了《人月神话》中的软件焦油坑，从而迫使你思考应该如何重新组织项目——但这是好事，因为 AI 重构的能力极强，一旦你找到一个更好的架构，瞬间就会改进。

请留存好你的项目，它可能会是你成为 AI-native 新人类的起点——之后我们也会持续地改进它。

## 问题、修复与回归边界

Issue 先构造两个并列的一维线性模型 `cm = m.Linear1D(10) & m.Linear1D(5)`。它们各自依赖自己的输入，依赖矩阵为 2×2 对角阵。把 `cm` 放到 `m.Pix2Sky_TAN() & cm` 的右侧后，旧代码却把右下 2×2 区域变成全真。这会错误地表示两个线性模型的输入输出相互依赖。

根因位于 `_cstack(left, right)`。右侧已经是依赖矩阵时，旧代码把目标区域统一填成 `1`。PR 将赋值右侧改为 `right`，保留子模型已经计算出的内部依赖结构。修复行是 `cright[-right.shape[0]:, -right.shape[1]:] = right`。

PR 的实现改动只有一行，但交付并非只有这一行。它增加 `cm8` 到 `cm11` 四个测试条目，并补充更新记录。前三个条目比较 `rot & (sh1 & sh2)`、`rot & sh1 & sh2`、`(rot & sh1) & sh2`，要求不同嵌套方式得到相同的 4×4 依赖结构。第四个条目加入右侧嵌套缩放模型，检查 5 维组合。预期结果同时覆盖可分离标记和依赖矩阵。

这份证据支持“理解组合抽象后，以局部修复保留已有结构”。它不支持把一行补丁当作全部开发工作，也不证明所有复合模型性质已经验证完毕。课程可把它连接到问题复现、根因定位、回归检查、更新记录与合并过程。
