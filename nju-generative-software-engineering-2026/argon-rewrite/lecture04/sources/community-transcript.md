这个例子是每个同学都会需要、我自己也有的东西：一个能够持续为你工作的个人助手。这里列出的需求只是供你参考，如果实现出来，还是会有一点成就感。比如你可以建立自己的学习数据库。这个学期你们可能会上一些比较困难的专业必修课，如计算机网络、数理概率等，可以把专业课资料放进个人数据库；参与研究组课题时，也可以把研究组的论文、相关文献和教科书整理成个人数据库。数据库采用什么形式并不受限。

为什么要布置这样的实验？这些任务看起来都在 AI 的能力范围之内。我今天会尝试把实验要求直接交给 AI，此前还没有试过。AI 一开始就会做出很多它认为合理的决定，但这些决定可能让项目越来越难维护，最后陷入焦油坑。因此，每个同学都有必要体验一下软件工程里的焦油坑：当 AI slop 开始不断消耗你的 token 时，你终有一天会下定决心删掉项目从头重做，或者回退到某个很早的版本重新开始。这就是这个实验想告诉大家的事情。当然，我相信这个项目对每个同学都有用，这也是我设计实验的初衷。

可以提前预告一下，下一个 Lab 会和这个 Lab 有非常大的关联，而且你们暂时猜不到。假如你把 Lab 1 的实验要求都做好了，它已经成为一个非常舒适的个人助手；我突然增加一个需求，这个需求和前面的所有需求都有关联，并且存在一定冲突；你一改就越改越崩溃。后面的 Lab 就是要提供这样的体验。如果现在选择躺倒，完全不管 Lab 1，直接让 AI 做，下次再把成品直接删掉，就体会不到软件工程了。

我们回顾一下上节课的软件项目管理。项目是各种文件的集合，你的 intent、设计文档和 `README` 都在项目里。我不喜欢 AI 写出的那种特别长的 `README`。对我来说，`README` 应该写明设计项目最初的意图：你想做什么产品，以及产品能够达到什么效果；可以放两张截图，再说明最重要的设计。

假设有一天你突然想到一个很好的点子，真的想用它挣一个亿，于是需要组建创业团队，并说服计算机科学领域的人加入，例如说服我一起干。其实你只需要一份比较短的 `README`，说明自己的 intent 和想做的东西。假如我有架构和编码能力，就可以补出剩下的内容。你不需要知道整个软件系统具体是什么样、它的 specification 是什么、使用什么数据库，以及怎样支持用户数量从一个、十个、一百个扩展到一百万乃至一亿。你可能没有计算机科学知识，但只要有最原始的设计和 intent 就够了。接着从 intent 到 spec，就会涉及数据库、编程语言、项目结构等各种选择，小到每个模块的接口也属于 spec；再往下是代码实现。这些东西现在都在项目里。

有了这样的项目，自然需要一个容器来管理各种文件。大家用文件系统管理项目，其实真的只是图方便：回到 1950、1960 年代，操作系统提供的存储功能只有文件，关系型数据库还没有发明，程序员别无选择，只能以文件形式保存项目。这更多是历史不断延续造成的结果。我认为文件系统可能并不是组织项目的正确方式，因为它丢失了许多不适合用文件表达的信息。

有些信息比较容易表达。例如 intent、spec 可以写成文档，说明某处的设计思路；测试用例可以描述输入、输出，以及在程序运行过程中必须满足的断言。但项目里还有许多隐藏的关联。举个例子，当 AI 编写代码时，你让它把某个实现从 linked list 换成更高效的 tree 结构来优化性能。现在的 Agent 稍微好一点，但也未必总能处理好。AI 很快就把代码改了，你却可能忘记某个 Markdown 文档里还写着“这个项目使用 linked list 管理数据”。于是文档、代码和测试之间形成了关联。编写文档时可能还没有代码，你只是随手写下“这是 linked list”；代码实现以后，这种关联却没有被强制建立起来，这就是技术债，即 technical debt。

随着文档和代码不断演进，两者的不一致只会越来越多，软件便陷入维护的泥潭。以后人或 AI 看到一份代码时，会不知道究竟是文档正确还是代码正确。当初的聊天记录已经消失，你也可能换了电脑；Git repo 里或许还有一些 change 日志，但到最后，你真的不知道代码和 `README` 哪个正确。

软件工程对这个问题已经研究了很长时间，它叫 traceability。这篇 2014 年的综述回顾了更早的论文，讨论的就是 software traceability，即软件可追踪性。我们把项目保存在文件系统里，只是为了方便；但软件项目中的测试用例、文档，乃至文档中的一行内容彼此有什么关联，以及能否在软件系统演进过程中维持这些关联，是一个非常典型的软件工程问题。

文件系统就这样将错就错地沿用了下来。总有一天，大家会发现用文件系统管理代码让人无法忍受：打压缩包发布，再把压缩包发给合作者，根本维护不下去，于是有了 SVN 和 Git。那么下一个是什么？今天稍后我会讲 `jj`，这是另一个版本控制工具，甚至可能比 Git 更好用。

结合刚才说的 traceability，如果未来我们不再亲自编写代码，软件就不应该再像现在这样，在 Git repo 里管理许多 `README.md`、`hello.c` 和 `docs` 下的文档。如果人类几乎不再管理这些内容，我们能不能把软件部件之间的关系显式表示出来？也许仍然需要文档，但文档可以由许多切片组成，并被转换成许多对象，即 object 或 entity。文档和实现之间存在关系：代码实现了文档；测试用例也有文档，测试文档与测试用例相关，测试用例又与某部分代码实现相关，不同文档之间同样有关联。

这会形成一个完全结构化的东西，无法在文件系统里用树形结构表达；它是一个可以任意连接、带 cycle 的 graph。我们可以把它放进一个数据库，例如叫 `repo.db`。显然，人类无法使用当前 UNIX 世界里的工具来维护这样的 repository，但可以用魔法打败魔法：人类理解不了的东西，只要存在强化学习的反馈信号，我们就可以训练 AI，让 AI 理解这个 repo。

这个 repo 可以代表一个非常大的项目，例如 Linux 内核、数据库，或者你想做的价值一个亿的产品。软件系统投入运行以后，我们通常不会要求它一下子变成另一个产品，而是增加或修改一个功能。这和 Git 的 philosophy 很像。Git 管理文件目录的快照以及快照之间的关系，并鼓励我们小步前进。每完成一件事，如修复一个 bug 或修改一份文档，就产生一个 commit。这样，多个人可以协作，每个人产生自己的 commit，再用 rebase、merge、fast-forward 或普通 merge 等方式，创建整个项目可追踪的修改历史。

如果未来不再使用文件，或者仍用文件系统保存，但让 AI 自动维护所有 software artifacts 之间的一致性，那么代码和文档必须始终一致：文档写的是 linked list，实现里就必须是 linked list；文档要求从 A、B、C 三方面测试，test case 就必须覆盖 A、B、C。所有这些内容都应关联起来。

每次完成这样一小步修改时，我们都知道这一小步要做什么，因此可以在 chat 中告诉 AI：“我现在发现一个 bug”，或者“我做了一个产品，但对今天的幻灯片样式不满意”。这就是一个小步。在大型软件系统里，绝大部分内容都与这一小步无关。

例如，当我说对幻灯片样式不满意时，可以直接看我的 repo 顶层结构：里面有一些 assets、`.cache` 缓存目录、P1、P2、P3、P4、P5，还有一些脚本。任何软件系统在只做一小步时，都只需要看到系统的一小部分，大部分内容应该与当前任务无关。既然无关，就可以让 AI 根据我们的 chat 摘出相关内容。它能判断当前只需要某个文件、某个 test case 和某份文档，其他东西都不需要。

AI 有动态生成任何内容的能力。Everything is code，content as code，code 可以表达任何东西。因此 AI 可以根据我的 chat，生成一个与当前这一小步修改相关的 view，即视图。大家在各种系统课程里学到的概念仍然有用。不是所有同学都学过数据库；数据库里有一个叫 view 的概念：数据本身就在那里，但可以创建不同的查询，用另一种形式把它展示出来。这里也是同样简单的想法。我希望以另一种形式展示这些数据，看到的不再是代码、文档、diff 等内容，而是一个可视化看板。看板列出与这一小步相关的内容，再问我要改什么。

修改完成以后，整个项目仍然从 V0 变为 V1，还是同一个 `repo.db`，但这一小步会修改所有相关联的内容。比如我要增加一种测试用例，它可能在几个地方添加测试，也可能修改其他地方。项目从一个内部关系错综复杂但一致的状态，经过一次小步修改，到达下一个一致的版本。软件工程也就彻底改变了。我认为未来有可能在 AI 内部这样生产软件，从此我们再也不用看代码。

现在的现代 IDE，例如 Cursor，默认打开就是 Agent mode，我其实不太喜欢。原先熟悉的 IDE 界面被弱化了，工具强迫你用类似 chat 的方式与它沟通。因为我还相对精通古法编程，有时对代码仍有一些掌控欲；这可能不好，也可能不对。但未来的确可能沿着这个途径发展。

同学们肯定也会焦虑：如果这件事真的发生，而且也许一两年后就有公司把它做出来，我们学那么多东西还有什么用？其实，在思考和创造这些东西的过程中，我们使用的正是经典、集大成的计算机科学课程知识。我刚才使用了数据库中的 view、entity 和 relation 等概念，也借用了 Git 的模型。Git 长期积累的开发经验告诉我们要一步一步向前。在这个模型下，如果大步向前，结果就会很糟。当然也有另一种可能：模型非常强，一个非常大的项目也能一步变成下一个版本。现在还不知道怎样做到；至少在初期，我们可能仍要沿用过去积累的软件工程智慧，小步走向那个极乐世界。我仍然相信这个极乐世界确实可能到达。

这引出大学教育里一个很有意思的评论。上上节课我问同学们 `git rebase`，大家都不知道。一个应该已经毕业的同学提出了一个 valid point：学生时代大多数人不会与他人共同合作，主要只是做作业，所以 rebase、merge 的使用场景很少。这个观点是对的，你们做作业时确实不太会用到。

我的回应是：如果你真的到外面的世界走一走，就会看到互联网开发者社区铺天盖地的文档。总有一天，你浏览别人的项目时会看到 `CONTRIBUTING.md`。它是仓库根目录下的一份贡献者指南，通常回答“我怎样参与这个项目”，其中会说明项目总体结构、分支与提交信息，以及 PR 的规范和流程。如果你看过很多项目的 `CONTRIBUTING.md`，随手打开一份，发现里面的东西都知道，那就可以了；如果不知道，就会在其中学习。

例如，你一定会看到某个项目要求你在自己的分支上 rebase，以保持线性历史，禁止直接创建分叉的 merge。这样你就会知道 rebase 是做什么的。我们的社会变化太快。有些学生还保留着高中形成的思维：老师不教的就不需要会，考试不考的就不用学。为了升学利益最大化，这样做没有错；但如果到了大学还带着这种思维，就会在“新人类”和“旧人类”之间产生 gap。我相信每个同学都可以成为新人类，只需要投入一些注意力，主动留意更多东西。

现在存在一个危机：在 AI 时代，斩杀线以下的价值会全部归零。当然，目前的斩杀线可能还触及不到各位 985 大学计算机科学专业的同学，但一些较低层次的智力劳动已经面临风险。例如我看过一个报道，中国可能有一千万或其他数量的会计从业者。行业顶端的人暂时肯定没有威胁，但底层的大量从业者都面临被 Agent 替代的危险。因此，你们需要从操作系统、编译器、软件工程等经典课程中学习经典知识和软件工程智慧，最终形成自己的理解。以上是一些评论，也是对 Git 的复习。

现在继续回到软件工程。不论是我刚才畅想的未来模型，还是 Git 本身，Git 管理的都是快照，也就是整个目录的一个快照。开发者可以基于快照做开发，而且要求小步前进。假设现在有 A、B 两名开发者，他们可以分别独立开发并创建 commit。

要把两路工作合起来，在 Git 原始的模型里，rebase 相对不那么受提倡。通常会创建一个有两个 parent、继承两边修改的 merge commit。但这会带来一些问题。例如 merge 由 A 完成，那么其中 B 编写的部分内容，作者可能就变成 A，发生一次隐藏的作者变化。B 加的一行代码原本也许还能追溯到 B；但如果发生冲突，冲突由 A resolve，产生的 change 就是由 A 完成，B 所改代码的 ownership 最后也可能归到 A。这会带来一点小麻烦。

Rebase 解决了这个问题。假设 A 先改了文档，又添加了测试，形成两次提交和两个快照，即 delta 1 和 delta 2；与此同时，B 添加了一个 feature，又添加了一个测试。Rebase 不直接创建一个把两条线路合起来的提交，而是先尝试把 B 的 feature 放到 A 的提交之后。如果能加上，就成功了；但这里存在很大风险：A 可能加入了与该 feature 不兼容的测试用例，或者双方修改了同一个地方，做出了两个完全不兼容的改动，因此 rebase 可能失败。

如果 feature 成功应用，再把 test 放过来；如果两条线上的修改完全没有冲突，就可以一路合并过去，形成线性历史。一旦发生冲突就很危险，因为你必须 resolve，并进入 rebase 模式。没经历过的人一进入这个模式，瞬间就不知道该怎么办，只能打开 Agent 问：“我现在发生了什么？”Agent 会细心解释。更麻烦的是，即使成功搬过来了 feature，搬 test 时仍可能失败，需要再次处理。

而且，每一次 rebase 都会创建新的 commit。每个 commit 都有自己的 ID。如果使用有两个 parent 的 merge，原有 ID 都会保留，只额外创建一个新的 ID；但 rebase 时，原 commit 的 base 被改到了新的位置，因此每一步都会创建新的 commit ID，历史也随之改变。这会让人感觉存在一点轻微的不一致，因为我们真正关心的是修改：希望把这个修改搬过来，再把下一个修改搬过来。

Git 用 commit 表示修改：一个 commit 与其 parent 之间的关系就是一次修改，它没有一个专门叫 change 的对象。大部分情况下，这种用 commit 代替修改的方式都能满足需要。但如果把 change 也变成 first-class citizen，会发生什么？这就产生了下一代更好用的版本控制系统 `jj`。

`jj` 不仅有 commit ID，也能使用 Git 仓库；它还增加了稳定的 Change ID。同一个 change 即使经过修改或 rebase，commit ID 会变化，Change ID 通常仍然保持不变，因此它的身份可以继续被追踪。rebase 时，`jj` 搬运的是 change。冲突本身无法消除，但 `jj` 可以把冲突的逻辑表示记录在重写后的 commit 中，让 rebase 先完成，之后再统一 resolve。底层仍然保存快照，但使用起来舒服很多。

然后它还有一个很好的特点：不需要 staging area。Git 里面最讨厌的是什么呢？我上操作系统课的时候会讲这个例子。假设你现在有一个工作区，也有一个 repo。你修改 `hello.c` 改到一半，项目还不能编译、不能运行，测试也通不过。此时导师突然给你打电话，说现在有一个优先级很高的 bug，客户那边马上就要交不了差了，让你一分钟之内修好。那怎么办？你不应该 commit，而是需要把当前改动放进 index，再执行 `git stash`，它会把改动压栈。这其实是一个比较讨厌的操作：你 stash 一份改动，去修原来的 bug；刚修到一半，导师又打电话说这个 bug 先别修了，还有一个优先级更高的 bug。你又要 stash 一次。`git stash` 是一个栈，里面会有好多份改动，你还需要管理这个栈。

如果换一个角度想：在任何时候，你都在编辑这个 repo，这不就是一个 change 吗？你修改 `hello.c`，加一行、减一行，都是 change。Jujutsu 好像是在做这样一件事：把 working copy 本身也表示成一个可以持续修订的 commit，多数命令执行时会自动把当前文件变化保存成新的 snapshot。它不会因此产生一长串需要人管理的线性历史，而是持续修订当前 change。也就是说，当前始终有一个 change 和对应的 snapshot，工作区一直处于已经提交的状态。这样就很舒服，连 staging area 都不需要了。

从“我要把 change 作为 first-class citizen”开始往后推，你就可以发明自己的版本管理系统。当然，这不是 Jujutsu 的全部，从别的路线也可以推导出它的其他设计。不过你们可以适当地质疑一下 Git：它有哪些地方做得不够好？如果可以做得更好，还能采用怎样的设计？这些都是非常有趣的设计。你们可以在 Agent 的带领下，或者在我给出一点开头和 motivation 之后，把最重要的 prompt 交给 Agent：“如果我要学习 Jujutsu，我想从 change 开始理解。”如果看它的 tutorial，它一开始也会告诉你，它没有 staging area 等机制，管理版本更加自然。它首先对人类更友好，实际上可能也对 Agent 稍微更友好一点。

这就是为什么你们作为 AI Native 的人类能够淘汰我们这一代人。我已经形成了 Git 的肌肉记忆，比我更老的一代人已经形成了 SVN 的肌肉记忆。人一旦形成肌肉记忆，就很难把习惯改过来。我现在对 Git 有肌肉记忆，即便能够理解 Jujutsu 的概念，甚至可能比初学者理解得更好，也可以从 first principles 思考它，相当于 virtually reimplement 这个系统，但我没有足够的时间再训练另一套肌肉记忆。你们正好反过来，应该在还没有形成肌肉记忆的时候，直接使用那个更正确的东西。

人类历史是不断积累的：SVN 实在用不下去了，才有了 Git；发现 Git 的缺点以后，又有了 Jujutsu。你们可以先用肌肉记忆记住一个更正确的设计，再回过头理解过去的设计，届时会发现 Git 原来这么蠢。Git 出现的时候，大家觉得它很先进，因为它使用 persistent data structure；SVN 从一开始走纯 diff 那条路线就走错了。现在再回头看，Git 也犯了一些设计上的错误。当然，这是因为 Git 最早没有想到 rebase 会产生这么大的影响；当时有 merge 就已经很好，足以解决手上的问题，因此它可能没有把概念模型想得更加清楚。这些评论也给了你们一些学习建议：尤其在 AI 的辅助下，学东西时可以不断往前走。

但这门课不是软件工程，而是生成式软件工程。我们真正要做的，是在 Agent 时代重新设计版本管理系统。你当然可以让 Agent 使用 Git 或 Jujutsu。Jujutsu 对人类来说是很大的进步，但对 Agent 来说进步可能相对小一些，因为 Agent 很会做 rebase。我们一路走过来，SVN 有局限，Git 有局限，那么在 Agent 时代，我们的局限是什么，要实现的改进又是什么？

前面所有 version control system 都有一个假设：使用者是人类。人类是 single-threaded 的生物。我在操作系统课讲并发程序时，会把线程比作一个人。线程可以访问共享内存，访问共享内存的两个基本操作是 load 和 store，或者 read 和 write。我可以从变量中读一个值，例如把 `x` 读到临时变量里；也可以写 `x = 1`。两个操作不能同时进行，除非有一条原子指令。

绝大部分 shared-memory access 都可以这样类比：如果我想观察世界，就要把手背在后面，只能看。看到一个同学之后，我想对他施加一个效果，例如用粉笔“导弹”射击他。当我真正要 write、要写一个变量时，就必须把眼睛闭起来。闭眼扔粉笔的时候，刚才读到的值其实已经失效了，它已经是旧值。从上一个时刻读到它，到这个时刻之间可能发生了很多事：我可能被换下 CPU，被中断打断，另一个线程上来执行了一秒钟，我才恢复过来。但恢复后，我在寄存器里看到的仍是上次读取的 `x = 1`。此时把粉笔扔出去，很可能就扔错了。单线程变成多线程并共享内存，就会带来无穷的问题。

人类也是如此。人与人之间有无法逾越的物理屏障：你不能理解我的思想，我也不能理解你的思想。我是一个由分子紧密连接起来的独立个体。我们只有一套 I/O 设备，一双手、一张嘴和一对眼睛。因此，我们编辑代码库、产生 change，是以小时为单位的。一个软件公司里，负责一个模块开发的团队多则十几个人，这已经是不小的团队了。十几个人都以小时为单位开发，最多也就是平均十分钟产生一个提交。

以十分钟为单位产生提交，意味着它比人与人之间沟通的速度慢很多。尤其一个 team 的工位都在一起。你写一个东西要一两个小时，写之前肯定可以用十秒、二十秒或三十秒跟师兄说一声：“师兄，我要做这个行不行？”师兄说：“行，你去改吧，我们现在不改。”到公司以后，可能每天早上都要开会，leader 把任务分出来：今天要做什么，你做什么、他做什么。在半小时内划定 scope，把项目切开，每个人领一部分去产生 commit。当然，这是“古法编程”。

在古法编程时代，stash 是合理的设计。导师在你工作中途打电话，这件事可能发生；但在你修到一半时，导师再次打电话的概率很低。绝大部分时候，stash stack 里只有一层。如果有很多层，管理起来很麻烦，你还需要逐一处理这些 stash。你会尽可能保证 stash 不要太深，因为你可以拒绝一个工作，说手上有优先级更高的任务，暂时不能做；完成以后，自己可以给任务排一个队列。所以 Git 是给人用的。

但在 Agent 时代，这件事变了。对一个 Agent team 而言，单个 Agent 生产 AI slop 的速度就远远快于人，以分钟甚至更短的时间为单位。有时让它修一个东西，在上下文还是热的时候，可能只要几十秒；DeepSeek-V4-Flash 干活时甚至几秒钟就做完了。当 Agent 能以秒为单位产生一个原子提交，并且你可以轻易得到十倍、百倍规模的 Agent team 时，Git 或与 Git 兼容的 Jujutsu 这种为人设计的模型，就有些跟不上了。

大型项目可能有一些门控：改完一个部分后，必须经历测试流水线，而测试本身就要运行几分钟，这可以放缓 Agent 的提交速度。但毫无疑问，Agent 加速了软件开发过程。那么，我们应该怎样为 Agent 设计版本管理系统？

首先可以让 Agent 沿用人的模型。把 single-threaded 的人类和 Agent 做严格的一一对应，让每个 Agent 都有一台独立的开发计算机，可能是一个容器；再把项目放到 `git.nju.edu.cn` 上，直接 instruct Agent：“remote 仓库在 Git 上，你现在是一名单人开发者，可以从 tmux 里收到命令，收到以后就开始工作。”这件事其实非常容易实现。

我直接让 Agent 开始工作。Agent 时代有一点很好：每个人都是领导。现在有两个 tmux session。实际开发时，它们可以位于两台不同的机器或不同的容器中，彼此在物理上隔离，看不到其他人。我给它们命名为 master 和 slave，再分别启动一个 pi coding agent，让两个 Agent 都开始工作。

当 AI Agent 变快时，如果你的指挥发生一点点差错，影响就会很快扩散。现在一种流行的 paradigm，是设置一个监工 Agent 和多个子 Agent。为了最大化模型的智力、防止 AI 生成不想要的东西，可以放两个比较强的模型，例如由 Codex 设计、Claude review，让它们互相讨论并达成一致。只要开两个 tmux 就行，主 Agent 负责协调，观察它们的输出或总结报告，并向其中 inject prompt，一个多 Agent 系统就这样运转起来了。

我看一下这个 repo status。你会发现，如果大家工作在同一个 Git 仓库上，就会有一些麻烦；但如果它们工作在不同的 repo 上，就完全可以。它们可以去远端拉取别人的提交，如果发生冲突就自己修复，必要时甚至可以给 master Agent 发消息。你们立即就可以构建出这样一个多 Agent 系统。

今天也有一些相应的 workaround，例如 Git 有 worktree 功能。我可以问 Agent：“老师说 `git worktree` 可以改进这样的并行工作方式，能让这两个 tmux session 都工作在 worktree 中吗？”提问其实是关键。你们可以从各种信息中获取灵感：比如今天早上走到教室时正在看微信公众号，上面提到 `git worktree` 或某种 sandbox container，你就可以立即让 Agent 帮你试一试。

我来看它在做什么。这是一个相对容易的任务，它确实正在写脚本，并且退出了 pi。现在应该已经完成了。

这是当前的 Git worktree。Git 允许我们创建另一个 working tree，可以把它理解成同一个 Git repo 的独立工作副本。我可以在里面独立修改和提交，在一个隔离的环境中工作。大家都知道 `.git` 是什么：通常它是一个目录，里面有 `logs`、`objects` 等内容。那么 worktree 里的 `.git` 是什么？打开以后会发现，它是一个普通的文本文件。

如果继续追问 Agent，它会告诉你——这也是我刚刚才知道的——`.git` 除了可以是一个目录，也可以是一个特定格式的文件。这个文件包含一行 `gitdir:`，指向主仓库 `.git/worktrees/` 下的一个目录。那个目录是一个小型 Git 目录，依然有 `HEAD`、`index`、`logs` 等内容，但它依附于原有的 `.git` 目录而存在。你可以看到，Git 最大程度复用了操作系统里的机制。

这个特性在 AI 时代突然变得有用了：各 worktree 的提交在本地直接互相可见，不需要彼此 pull 和 push。像我刚才所说，也可以开好几台虚拟机，在每台虚拟机中放一个 Agent，再直接向各个 tmux session 注入指令，这当然完全可行；但 worktree 提供了一种更轻量的协作方式。如果存在冲突的修改，仍然需要 merge 或 rebase 才能合并，不过整体效率会更高一点。

回到 Agent team 或 Agent swarm：除了 `git worktree` 这样的现成 workaround，还要重新思考为什么需要版本控制。人类的限制是，一个小团队哪怕合起来也要十分钟才产生一个 commit。人的限制塑造了工具。人与人之间的 communication 使大家每天早上都要开会，同步每个人的进展，再分发任务。即便做了沟通，成本仍然很高。比如室友向你请教一道数学题，明明你会做，却怎么也无法给他讲明白；除非你是一个很好的老师，能共情别人，站在别人的角度思考。

这也解释了为什么初创公司或小团队效率可能更高。软件系统变大、人员变多后，沟通效率降低，产出速度也会下降。一个一百人的团队不可能达到十人团队的十倍效率，能达到两三倍就已经很不错了，团队规模无法无限扩大。

因此，我们需要 Git 的各种 best practices：保留快照，小步前进；改一个 typo 也做一个 commit，做其他小改动也做一个 commit。这些小 commit 都可以追溯。一旦出现问题，需要回溯到某个人提交代码的时间。开发者会回想起，那天早上开过会，自己收到一个需求，做需求时沟通出了问题；大家再找到当时的沟通记录或文档，商量这个地方应该怎样修正。因此才有 `git bisect`、`git blame` 这些专门为人设计的特性。

但如果项目由 Agent team 或 Agent swarm 实现，我们还需要 `git blame` 吗？人是可以被 blame 的：某个人被 blame 多了，可能就会被开除，实习生也可能背锅。但 Agent 没有坐牢或被开除的问题，模型就变了。我们不再需要 blame，只要项目能继续前进即可。有时甚至不需要知道究竟是哪一个提交引入了错误，只要知道这个地方错了，把错误修好即可，不必追究历史上是怎样造成的。

Agent 之间的 communication 还有一个有趣之处：现在每个 Agent 往往使用相同的模型，也就是说，它们是完全相同的克隆体。同一件事让它们来做，虽然模型存在不确定性，结果可能有细微差别，但方向上大概率会收敛到相同结果。因此不再需要 blame，项目永远是一个向前推进的过程。

快照肯定仍然需要。比如方向走错了，如果没有保留历史上的某个 snapshot，一下子往前走了很远，再回去的代价可能比从错误方向上一点点往前修更低。因此我们要保留快照，但整体上不断大步向前，几乎永远不看过去。Git commit 里只需要留下一些 lessons，或者记录项目经历了怎样的演化，然后不停向前走、不断合并。历史的价值可以从“谁写错了”变成“怎样把它修好”。只要知道从现在开始怎样继续前进就可以了。

这时，计算机科学中学到的知识又会起作用。回到操作系统中的并发，再看看数据库：现在 Git 的模型更像数据库里的并发控制。比如有两段程序，各自执行一个很大的 transaction，transaction 中间可以混入任意代码。它可以先 `SELECT` 读取数据，再运行 Python 或 JavaScript 代码做计算。代码是图灵完备的，你永远不知道它会根据读到的结果算出什么，甚至还可以结合当前时间从外部计算一个值，最后再执行 `UPDATE`。

`UPDATE` 时可能发生冲突，也可能出现死锁。如果两边互相读取、互相依赖，就会形成循环依赖；也可能是我想锁你的对象、你想锁我的对象，从而产生死锁。此时数据库可能 abort 其中一个 transaction，说：“检测到循环依赖，这个 transaction 不能继续执行，需要回滚。”也就是 rollback。

Git 的模型有一点像 optimistic concurrency control。所谓“乐观”，是执行时假设两个 transaction 不会冲突。在数据库系统中，这个假设大概率成立。以教务系统为例，每个同学读写的通常是自己的那块数据：选自己的课，查看自己的课表。即使两个同学同时选课，也主要是各读各的、各写各的，全局冲突不太容易发生。

Git 也是如此。大家事先开过会，约定一个人沿着这条路做，另一个人做另一部分，所以合并时大概率不会冲突，无论 merge 还是 rebase 都能顺利完成。这是古法编程时代的情况。

但如果 Agent 快了一千倍，而主 Agent 协调不够好，一下子又分发很多任务，它们就可能更频繁地触发 transaction abort。发生 abort 或 conflict 在 AI 时代也不是大问题，Agent 出错或发生冲突后可以自己修好。但在 Agent 时代，我们是否可以换一种并发控制方式？数据库里常用 transaction；操作系统中的并发控制还会用锁。锁与 optimistic transaction 不太一样。我上课时常说“一把大锁保平安”。访问可能冲突的资源时，先把它锁住。锁一旦被持有，其他线程再次 lock 时就必须等待，直到前一个线程 release，建立 release-acquire 的顺序关系。它不是让大家先往前跑、发生冲突后再处理的 optimistic 模型，而是要求在使用资源前先声明用途，用上锁的方式取得资源。

只有真正学会操作系统课、数据库课里的这些内容，回头看软件工程时，才会发现相同的概念又出现了。如果 Agent 动作非常快，我们其实应该采用更偏向 pessimistic concurrency control 的方式。主 Agent 规划好要做的事情后，立即锁住项目的某个部分。一个 Git repo 或 snapshot 可以支持 lock 操作，Agent 声明需要哪些 scope，先把它们锁住，做完并 commit 后再释放。

另一边也可以上锁，但它想处理的内容一旦被别人锁住，就必须等前一个 Agent 释放锁以后，才能再次取得锁。这样几乎可以避免所有冲突。例如可以在文件级上锁，防止两个 Agent 同时写同一个测试文件或配置文件。因为 Agent 数量足够多、速度足够快，仍然可以保证整个项目继续推进，也许还有其他 Agent 可以继续运行。

这和操作系统里的并发程序一样。“一把大锁保平安”，或者把锁拆细，互斥锁的本质都是让冲突的操作不要并行、不要并发，它与多处理器并行存在根本矛盾，要把原本可以并发的那一部分退回串行。但当系统中有很多互不冲突的线程运行时，即使每个线程都持有一把锁，整体仍然可以高效运行。即使采用悲观并发控制，系统依然可以高效。把这些知识关联起来，就可能看清楚 Agent 时代应该怎样重新设计版本控制系统。

我觉得在 Agent 的时代，我们又可以重新设计一种版本控制系统。在 Agent 时代，软件工程肯定会发生很大的变化。从 first principles 出发，我们要管理快照、版本和 change，还要管理飞快发生的 change。答案是什么？Git 可能是一条线；如果采用刚才所说的方式管理软件，那可能是另外一条线。

所以你会发现，学习操作系统、数据库这些东西是有用的。虽然学起来很痛苦，你可能怀疑：在 AI 时代为什么还要学这些，AI 都会写数据库和 SQL 查询了，我早已不亲自写任何 SQL 查询了，学数据库还有用吗？答案是有用的，还是要好好学习。数据库里也有 advisory lock 这样的机制。

这也是我喜欢上课的原因。如果我不来上操作系统课、生成式软件工程课，可能就不会在备课时把这些事情重新在脑子里过一遍，思考是不是地球上所有人都错了。因为要讲给你们听，我必须共情听众，考虑到你们只能接受比较平实、朴实的逻辑，不能一上来就讲某个系统是怎么设计的。我必须把最顶层的 idea 提炼出来，试图让大家理解。当然我可能做得还不够好，你们可以在 AI 的帮助下重新理解。

版本管理基本讲完了：从历史和动机，到过去的 Git、现在，再到未来可能发生的事情。但版本控制本质上还是一个工具，哪怕是刚才那种基于乐观锁或悲观锁的版本控制，真正困难的其实是进度，也就是团队管理。

我们现在为什么还需要软件工程？因为还不能用一句话直接生成一个高质量的产品。如果斩杀线到了，老板随口说：“我要做一个 Agent 用的微信，或者 AI 时代的微信，让它成为社交爆款，以后人们社交不用微信，都用我的产品。”当然他可能还有更具体的想法。如果这时 AI 能直接做出微信级的产品，软件工程就已经死了，我们也都没活干了。但现在这个斩杀线暂时还没有到，至少没有到团队管理这一层，所以我们可能还要学。

也许有一天我真的也要被裁掉。摩尔定律本质上也是一种 scaling law，现在仍然成立；模型肯定会更强、更小、更快，也许算力有一天能够换来我们的智能。但至少今天，AI 还不知道怎样做团队管理。

每多一个人，沟通关系的数量都会平方级上升。因此软件工程团队里最难招的不是码农，而是能分解任务的 team leader。最稀缺的是能把“做一个微信”这样的国民级应用拆给一个一百人团队的人：分成十个小团队，由十个 team leader 去做，最后还能把各部分拼成完整产品。其次，能够带领小团队的人也很稀缺。《人月神话》讲的就是人与人两两之间存在平方级的沟通关系。

就算你能做好分内的事情，其他人也在做各自的事。当你不能完全知道别人正在做什么，或者对整个团队了解得不够好，最后就会发生各种冲突，例如你写的代码过不了我写的测试。

如果我们想管理一个团队，或者你们希望毕业时具备一定的团队管理能力，现在就可以把自己当成主 Agent。刚才我给了一个不好的示范：我创建了两个 slave。你现在也可以立即拥有 DeepSeek-V4 这样的 slave，然后思考怎样通过任务分解，尽可能发挥两个、三个甚至更多 Agent 的能力；还要确定提交策略，决定 Agent 何时应该提交、何时应该合并。这样就可以把刚才讲过的所有版本控制概念带入自己的开发流程。

重要的是：版本控制是工具，它蒸馏了人类多年软件工程实践的经验，告诉我们应该怎样开发。在这个工具之上，你可以形成自己的软件工程直觉和经验。学习这些东西仍然有用，至于具体怎样做软件管理，我可能之后再讲。

最近我看到一个很有意思的题目，有些烧脑，也很好玩，很多公司似乎喜欢把它当作面试题。我是在网上刷到的，它一般是小学生考级题：带额外限制的汉诺塔递归。额外要求是所有盘子只能沿一个方向移动，不能折回去。

两个盘子时还很简单；三个盘子时问题就明显了。正常的汉诺塔解法会先把两个小盘移到中间，再把最大的盘子直接移到目标柱。但在这个限制下做不到，因为盘子只能沿指定方向移动。很难想象小学生要做这样的题。如果你们在保研机试里碰到它，就要输出移动方案或者移动次数。虽然 n 不大，但确实需要理解问题并找出方法。

这个带限制的汉诺塔仍然可以递归。为了把最大的盘子移到目标位置，先把上面的盘子移走，让最大的盘子向右移一步，再调整上面的盘子，接着让最大的盘子再向右移一步，最后把其余盘子移回来。也就是说，在最优解里，最大的盘子总是向右移动一步、再移动一步。最大的盘子已经用了不可避免的最少移动次数，剩余部分再用 induction，也就是归纳法，可以证明整个方案最优。这个题有点难，很难想象小学生可以做出来，但这不是重点。

重点是我们现在要推出一个产品。比如我想把这个东西卖给小学生，怎样才能卖得最好？当然是提供付费增值服务。小学生可以在这里写代码，代码随时能编辑，可视化会随着代码运行。比如代码写错了，系统能定位到那条试图把大盘放到小盘上的语句，同学就能找到 bug。

如果要挣钱，就要提供增值服务。现在它只是一个纯粹的 playground，用户可以写代码并运行。接下来可以提供一个 AI 助教：小朋友实在做不下去时，就点击“我要助教”，这时 DeepSeek 的 token 开始燃烧，我可以收取比 DeepSeek 原价更贵的 token 费，记在用户账户上。当然这是开玩笑的，我们还是尽可能以低成本提供给小朋友。因为我的 prompt 是独门的，我可以作为有经验的老教师，把自己蒸馏成 prompt，敏锐地知道小朋友的问题在哪里，再提供个性化指导。

做到这里就涉及一个信息系统。我让学生来做这件事，自己没有时间；明明有这么大的市场，我却不想挣这笔钱。学生做了设计，我看过学生和 AI 对话后产出的那版，也让 GPT 梳理了一下需求。GPT 的原话大意是：需要一个 API 应用、一个关系数据库和一个对象存储；需要异步点评时，再加后台任务进程。数据库保存关系和记录，大课程包与完整轨迹放在对象存储。任务量小时，数据库任务表就够用。这是非常正常的软件工程课式设计，毕竟 GPT 是一个语言模型，但我不喜欢这个设计。

不知道你们是否用过 Overleaf 和别人协作文档。Overleaf 可以把项目当作 Git repository 导出，我很喜欢这个功能。我要给学生改论文时，可以把论文克隆到本地，不用忍受网页界面；然后打开 Codex，让它直接启动 sub-agent，逐个修复每个 `.tex` 文件里的语法错误。我还可以给出很长的 prompt，让它遵循，整篇论文就改好了，再告诉学生改稿已经结束。

对于这个 Pico Playground，学生每改一次代码，或者进入 idle、点击运行、切换页面时，难道不应该自动做一次 Git 提交吗？当学生申请 AI 助教、界面开始转圈时，我可以让 AI 的点评从这个 Git 提交上产生一个分叉，并作为一条 comment 保留下来。

GPT 没有算到的是，生成一次 AI 点评的成本远远高于把其余数据 persist 下来的成本，后者几乎可以忽略。数据库确实有一些好处，比如总体压缩得更小、性能更高，但这不是我真正想要的，因为我的本质需求是版本管理。

所以在项目最早期，我甚至可以把代码库和学生数据放在一起：小朋友的代码直接存在代码库里，在上面探索性地创建 Git 历史记录。等文件目录格式、commit message 格式以及文件的使用方式都收敛了，再迁移到数据库，完全来得及。

这件事很好玩。学任何东西都有用：学 Git 有用，学 multi-agent 管理也有用，它让你有机会想到一个与别人不同的设计。

接下来我们真的做一件事。项目早期肯定不能一开始就用 multi-agent。你是包工头，应该先找一个自己能用到的、能力相对最强的 Agent，和它进行多轮对话。我想告诉大家，现在开始动手比什么都好，所以我决定完全不事先准备，直接打开课程作业做一次演示。

有两种办法。第一种是把需求直接交给 Agent，然后按回车，每个同学都可以体验，今天我替大家体验。我觉得另一种方式会更好。接下来我们观察一下它会做什么。

我们来观察它会做什么。有时 AI 的直觉和人的直觉不太一样。一线模型会进入 plan mode，和你确认一些事实，再生成 workflow。其实这很有意思，比如 Claude Code 执行复杂任务时会生成一段 JavaScript 或 TypeScript；TypeScript 里有一个叫 `agent` 的函数，函数内容是一段自然语言。用这种方式组织 workflow 时甚至可以写循环：如果有很多任务，它可以在循环里逐个解决。

你看，它直接开干了。只能用魔法打败魔法，300 token/s 实在太恐怖了。先让它做一会儿。

这就是前面讲上下文工程或提示词工程时最危险的一点：提示词里的每一句、每一个词，self-attention 都会看到。AI 现在已经被训练成了 prompt 的“舔狗”，有一种很难往外拉、必须遵循指令的倾向。当你把需求交给它，尤其是讨论稿式、比较开放的需求，它会过度遵循指令，最终生成一个确实满足字面指令、却不是你真正想要的东西。

回头看实验要求，它的言外之意其实只有一句话最重要：“实现一个持续为你工作的个人助手。”其他内容相对没那么重要，只是对这句话的解读。至于一个好的个人助手需要哪些能力，每个人都有自己的观点。

对你们来说，如果想实现自己的个人助手，第一个 feature 是什么？你最近一个月遇到的最大痛点可能是学习，尤其是高效学习和复习。因为你们要卷成绩，这毫无疑问最重要。你可能希望 Agent 自动从外网收集数据，以层次化方式归档，最后提供一个比较好的界面。这才是你最想要的功能，但我估计它十有八九没有实现。

于是我要问它：“其实我想要的是一个比较好的学习助手，能够收集外部信息、综合总结，并根据我的进度帮助学习。看看哪部分能实现这个功能。”让它重新读一读。你看，它正在做 database。

可以这样说：没有经过你的精心设想和讨论时，AI 基本只会按常见套路生成一套方案。你脑袋里想的东西，也就是 intent，与 specification、implementation 之间存在巨大的 gap。但模型一旦明确看到你要实现什么，就会真的去实现。

我觉得它肯定做了一些不好的事情。比如当我提到 e-hall 时，我真正需要的是一个 browser-use Agent，它能帮我在各种网页上处理事务；e-hall 只是一个测试入口，用来测试它能否把我的个人信息填到 e-hall 上。所以第一步不需要针对教务系统做太多设计，过度设计反而不好。

这和刚才给大家看的例子非常相关。它做的所有事情看起来都是对的，从 `README.md` 来看没有一个错误，但最终得到了一个你不想要的东西。我看了一下现在有没有 Git 提交，它甚至没有创建 Git repository。你不跟它说，它就不会做。当然，如果是 Codex，它可能会初始化一个目录，或者询问项目应该怎样管理。

如果我是一个成熟的产品经理，老板把任务交给我以后，我肯定会和团队沟通项目怎样管理。甚至在写下第一行代码之前，就要讨论好怎样协作、怎样管理项目、每天什么时候开会。Agent 很有意思，它会直接上手，觉得这只是一个用一次就丢掉的东西。

它烧了我不少 token，不过也无所谓。我参与 DeepSeek harness 首批内测，他们送了我一千块额度，到现在还没有完全用完。

所以项目刚开始时，脑袋里要回到项目管理，建立这样的模型，不能直接把任务丢给 Agent。第一件事一定是创建一个空的 repository，创建后再想下一步要迈向哪里。下一步也不能像刚才展示的那样一下迈得太大，而要向前再迈一小步。

现在让 AI 从零开始做一个东西、做出不那么 slop 的结果，比让它进入成熟项目完成维护性任务难得多。我们对软件工程真正的要求是：当我和一个 team 或学生讨论要设计什么软件时，要看它能不能以不变应万变。现在设计的架构或流程，能否抵抗未来需求发生根本性变化？

刚才的数据库例子也是如此：我说要生成一个挣钱的产品，挣宝妈们的钱，但真正需要的是一个可扩展的架构。未来可能出现别的需求，AI 模型可能变化，合作模式也可能变化。AI 助教可能是文字的、图像的，可能有交互，也可能没有交互。面对不断变化的需求，架构能否用最少的改动来应对？这恰恰是数据库课、操作系统课不会教的内容。那些课会告诉你操作系统、数据库长什么样，以及数据库为什么要做并发控制；软件工程最不同的地方，是应对未来需求的变化。

这两节课讲版本管理时，希望你们记住它做的三件事：记住现在，记住历史，记住教训。这在 Agent 时代和古法编程时代都成立。记住现在，是因为你必须有一个 repository。不管是刚才这种形式，还是 C、C++、Python、JavaScript 项目，都需要把文件管理起来。

记住历史，是为了将来某天发现被删掉的东西还有用时，可以把它捞回来。通过提交历史，你能看到自己怎样演进到某个点，怎样发现这条路线失败；失败的尝试可能留在那里，而你回到另一个点，重新开始一条正确路线。这些都在版本控制里。历史中的 lessons 会不断警示你应该怎样做，告诉你从第一步开始该如何向前迈出一小步。

再看 Agent，它已经实现完了吗？它实现了“提交人民奖学金申请”“准备退课”等功能，也做了一个 Git 提交，不过只有一个提交。它声称引擎全是真代码、服务走真实 HTTP，pi 已经集成；有些部分仍是模拟的，邮箱功能则没有。

它设计了入口层、编排层、能力层和数据层，是非常典型的架构。我不打算现在 review，但它显然把项目当成业务逻辑系统来做，风险很大。它看起来已经像一个教务系统了，下节课我就会讲教务系统。

如果真的要从零开始构建，更符合主流 best practice 的方法叫 MVP，即 Minimum Viable Product，最小可行产品。有句话叫：The biggest risk in product development is building something nobody wants。你看，它做出来的就是我不要的，绝大部分功能都不是我要的；刚才它生成代码时，我已经解释了真正想要的是什么。

做最小版本会逼迫你想清楚，哪些需求是绝对必要的。如果我要做个人助手，最想要的是提升学习效率和工作效率。总结出这两条后，第一个 MVP 里可能没有任何数据库。因为文件系统膨胀时，随时可以直接告诉 Agent：“按照现有数据组织，帮我提炼出一个数据库。”问题就解决了，不需要一开始就做数据库。

一旦加入数据库，每次数据库重构都需要 Agent 做 database migration。文件系统不同，你自己就可以在文件管理器里调整目录结构，逐渐梳理成舒服的结构。调整文件和调整 database schema 的心智负担不同。人类已经很习惯操作直观的文件目录，从小学电脑课开始就在做这件事；很多同学还没有学过数据库，根本不知道 database schema 是什么。面对未知事物时，还要强行做一次概念翻译：脑袋里是这样的概念，翻译到数据库里又是什么。还不如先用已经熟悉的系统，以最简单的方式管理学习资料的进入、通知消息的进入等内容。

甚至我现在用来回复邮件的 Agent 都没有任何数据库。流程大致是：mail Agent 收取邮箱，把 `.eml` 文件放到共享云盘同步；`.eml` 文件旁边会有 Agent 解析出的信息，例如回复草稿、邮件分类、是否为垃圾邮件等，再由下一级流水线处理。也就是说，我先要弄明白系统里有哪几级流水线、各级之间应该怎样协作，以及哪些东西通过云盘传递。

因为我很喜欢自己的云盘，我接着向 Agent 提出需求：“引入云盘是否需要修改架构？我希望邮件、资料等都和云盘保持同步。”这就叫需求变更。我现在不知道它的架构做得好不好，所以让 Agent 帮我看一看。

什么是好的软件架构？当前实现可能满足当前需求，但需求变更时，相应改动究竟是摧毁性的，还是会背上技术债，就不知道了。我们看看它的设计：它有一个 `assistant.db`，个人资料、邮件归档、索引和草稿仍然放在数据库里。目前看起来还不会引起很大问题，因为绝大部分系统都是这样设计的，数据库确实应该不会立刻造成特别大的问题。

但随着项目推进，你会发现有一种开发方式是上来就迈很大几步，把需求全都实现，再拖着技术债不断迭代、不断加功能；另一种方式是从最小的实现开始，得到一个特别精巧的架构。

为什么我举刚才那个例子？当你发现可以用 Git 管理学生提交后，很多事情都变得非常容易，自己控制起来也轻松很多。在遇到性能瓶颈之前，我都不想把它迁移到任何数据库。

这也意味着，早期 prompt 对整个项目走向的影响最大。最初是否直接把 `README.md` 交给它，是否明确说要做一个 MVP，都会对项目造成很大影响。下一节课，也就是周日，我们会进入软件架构和构造的内容。今天下课。
