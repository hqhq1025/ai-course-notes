## 教师讲解摘要

| 来源 | 要点 | 去处 |
|---|---|---|
| 官方课件 slide-001；第三方字幕（开场关于 Lab1 与研究生自动填表系统的讲述） | 布置 Lab1“会成长的个人助手”时，老师回忆疫情期间曾有一名研究生花了三年做自动填表系统，临近毕业恰逢 ChatGPT 问世而陷入恐慌；借此说明时代演进极快，今天个人助手的目标不是做成唬人的下一代商业概念，而是切实“能帮上自己”，并且直接把模糊需求丢给 AI 必然会体验到难以维护的软件焦油坑。 | 一堆文件，够不够表示一个项目 |
| 官方讲义《一堆文件，够不够表示一个项目》；官方课件 slide-003、slide-004；第三方字幕（关于文件系统历史与 repo.db 的设想） | 老师指出用目录树和文件管理项目只是沿袭 1950–1960 年代尚无关系型数据库时的“将错就错”；当代码把 linked list 改成 tree 而文档未改时就会失去 Traceability，进而设想未来或许可将制品及其带环图关系存入 `repo.db`，借助数据库的 View（视图）概念由 AI 动态生成与当前小步修改相关的看板。 | 一堆文件，够不够表示一个项目 |
| 官方讲义《从快照理解分叉与合并》；官方课件 slide-006；第三方字幕（回应毕业学生关于 git rebase 的评论） | 针对“学生时代大多独自写作业，不懂 rebase/merge 很正常”的观点，老师批评了“老师不教就不用会、考试不考就不用学”的应试学生思维，指出只要去开源社区阅读项目根目录下的 `CONTRIBUTING.md`，就会遇到要求 rebase 保持线性历史的规范，大学学习必须走向主动探索的第一性原理。 | 从快照理解分叉、合并与第一性原理学习法 |
| 官方讲义《把变化的身份纳入版本管理》；官方课件 slide-007、slide-008 | 老师引导大家体会 Git 在概念上的“轻微不和谐”：cherry-pick 和 rebase 真正想搬运的是“修改（change）”，但 Git 只能操作 Commit；一旦变基，Commit ID 就会改变，唯有像 Jujutsu（jj）那样引入稳定的 Change ID 并保留底层快照，才能在多次修订与变基中延续同一次修改的身份。 | 把变化的身份纳入版本管理：从 Git 到 Jujutsu |
| 官方课件 slide-009；第三方字幕（导师连续打电话要求修紧急 Bug 的 git stash 例子） | 老师用“代码写到一半无法编译时，导师突然打电话要求一分钟修好紧急 Bug，修到一半又来电话打断，导致 `git stash` 栈越压越深难以管理”的场景，对比说明 jj 将工作副本（Working Copy）直接视为可修订提交、无需 staging area 以及将冲突直接存入 commit（Killer Feature）的优雅之处。 | 把变化的身份纳入版本管理：从 Git 到 Jujutsu |
| 官方讲义《把变化的身份纳入版本管理》；官方课件 slide-010 | 老师结合棋手眼动实验中的定势效应（Einstellung effect）拿自己开玩笑，坦言“老登”已经形成了 SVN 或 Git 的肌肉记忆，即便从第一性原理理解了 jj 也没时间重练习惯；而同学们可以倒过来学，先掌握更自然的正确抽象，再回望历史理解旧工具的局限。 | 把变化的身份纳入版本管理：从 Git 到 Jujutsu |
| 官方讲义《当开发者可以并行复制》；官方课件 slide-011、slide-012；第三方字幕（并发编程闭眼扔粉笔类比） | 老师将人类称为只有一双手、一张嘴、一对眼睛的“Single-Threaded 生物”，并用操作系统课上“看世界时手背在后面、闭上眼睛扔粉笔时位置早已过期”类比并发读写冲突；指出人类十分钟甚至数小时才出一个提交，工位间喊一声就能协调，但分钟级甚至秒级提交的多 Agent 团队共用工作区会立刻互相踩踏。 | 当开发者可以并行复制：从单线程人类到 Agent Worktree |
| 官方讲义《当开发者可以并行复制》；官方课件 slide-013；第三方字幕（现场演示 tmux 双 Agent 与检查 worktree 中 .git 文件） | 老师在课堂上演示用两个 tmux 会话分别运行 Agent，并揭秘 `git worktree` 子目录中的 `.git` 其实是一个写着 `gitdir:` 路径的普通文本文件；各 worktree 拥有独立工作区、HEAD 和暂存区，同时共享底层对象库和大部分引用，让多 Agent 在本地无需 push/pull 即可并行开发。 | 当开发者可以并行复制：从单线程人类到 Agent Worktree |
| 官方讲义《先分开做再合并，还是先上锁》；官方课件 slide-014、slide-015、slide-016 | 老师提出“既然没有 Agent 会被开除或坐牢，能否不再需要 blame，借鉴 NASA 航空安全报告系统（ASRS）把历史价值转向故障恢复”，进而对比类似数据库 MVCC 的事后合并与操作系统/数据库咨询锁（Advisory Locks）式的“主 Agent 规划、子 Agent 先上锁再干活”，强调锁粒度、跨文件不变量与死锁问题正是系统课程的核心基本功。 | 先分开做再合并，还是先上锁：面向 Agent 的并发控制重构 |
| 官方讲义《人多以后，困难转移到了协作》；官方课件 slide-017、slide-018 | 老师将 AI 比作不断上移的“斩杀线”（甚至调侃数学工作者和基础会计面临的替代压力），指出只要一句话还不能直出微信级产品，团队管理就是核心壁垒；借《人月神话》的 $n(n-1)/2$ 潜在沟通边公式和“我的部分已经好了”四类乱象，说明版本控制只是工具，真正的难题在于对齐目标、依赖、完成定义与跨模块责任。 | 人多以后，困难转移到了协作：AI 斩杀线与团队管理 |
| 官方讲义《Git 还可以记录小朋友怎样解题》；官方课件 slide-020、slide-021；第三方字幕（单向汉诺塔与 Overleaf Git 批改论文经验） | 围绕 Pico Playground 中小学生做单向汉诺塔题“一片哀嚎”的付费助教需求，老师对比了 GPT 给出的“API + 关系数据库 + 对象存储”常规方案，并结合自己把 Overleaf 论文导出为 Git 仓库用 Codex 批改的习惯，提出直接用 Git 树状历史、`git diff` 和 `git notes` 管理学生解题动作序列与点评的轻量构想。 | Git 还可以记录小朋友怎样解题：跨界复用版本管理抽象 |
| 官方讲义《从零开始，你就是包工头》《用一个最小版本检验想法》；官方课件 slide-022 至 slide-025；第三方字幕（课堂实时 Vibe Coding 实验一演示） | 老师在课堂上不加准备地将 Lab1 需求直接发给 Agent，观察其以 300 token/s 狂飙生成出包含 `assistant.db` 和“人民奖学金申请”的复杂系统，以此警示 AI 是“Prompt 的舔狗”：早期 Prompt 中的任何确定性假设都会被放大为技术债；作为包工头，应先用无需数据库的简单文件与云盘做出最小可行产品（MVP），并靠自动提交与架构决策记录记住现在、历史与教训。 | 从零开始，你就是包工头：技术债、MVP 与早期 Prompt 的锚定效应 |
