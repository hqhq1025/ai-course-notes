\section{上午场 Panel：模型、Harness、奖励与环境谁先演化}

上午场 Panel 汇集杨梦月、张少坤、钱成、董冠霆与胡梦康，讨论前四场报告之间最直接的冲突：短期效果往往来自 harness 与 context 优化，长期能力却需要 model update；Agent 需要自己设计任务和 reward，但自评又最容易产生 reward hacking；真实应用要求开放探索，却又必须有可验证边界。

\subsection{Auto-Research 为什么成为自进化试验场}

嘉宾普遍把自动科研视为高价值场景，因为研究任务包含问题发现、检索、实验、代码执行、结果解释和报告生成，天然形成长周期反馈。更进一步的 ``auto-research for auto-research'' 让 Agent 不只完成实验，还尝试改进研究流程、benchmark 或自身工具。

\begin{importantbox}{Panel 共识：自进化必须改变未来行为}
无论更新的是 prompt、harness、memory 还是模型参数，都必须在后续任务上观察到可复现变化。只生成反思、总结或新想法，但没有改变执行策略，不构成有效自进化。
\end{importantbox}

\subsection{Model evolution 还是 Harness evolution}

Panel 给出的工程答案不是二选一，而是分时间尺度处理。Harness 修改成本低、反馈快，适合验证新工具、新流程和约束；当某种结构在大量任务上稳定有效后，再考虑通过训练把它内化为模型能力。这样既能快速迭代，又避免每次产品变化都重新训练基础模型。

\begin{knowledgebox}{从外部化到内化的路线}
一个常见路径是：先用 prompt 或 workflow 实现能力，收集真实轨迹并验证收益；再把稳定行为蒸馏或通过 RL 写入模型；最后简化 harness。Harness 因此既是产品组件，也是探索未来模型能力的数据生成器。
\end{knowledgebox}

老师们同时提醒，harness 与 model 并非完全正交。Harness 改变观察、动作和反馈分布，训练后的模型也会反过来改变最佳 harness。真正成熟的系统需要共同版本化并进行联合评估。

\subsection{Reward 能否由 Agent 自己设计}

开放任务很少有连续、无歧义的奖励。若让 Agent 自己生成 proxy reward，它往往会优化最容易测量的指标，而不是人真正关心的目标。Panel 将这视为 self-evolution 的核心风险：任务生成、作答和判分如果由同一模型控制，系统可能在封闭循环中持续确认自己进步。

\begin{warningbox}{Reward hacking 的三种来源}
第一，代理指标遗漏真实目标；第二，验证器存在可利用漏洞；第三，评估器与策略共同漂移。应尽量引入程序执行、环境状态、人类抽查和多评估器交叉验证，并保留对旧版本任务的回归测试。
\end{warningbox}

\subsection{环境、世界模型与主动探索}

因果世界模型强调 Agent 应主动寻找能区分假设的干预，Agent-World 强调持续生成新环境与任务。Panel 将两者连接起来：环境生成器提供探索空间，world model 预测信息价值，rollout infrastructure 执行交互，reward/verifier 判断是否获得新知识。

\begin{importantbox}{开放性与可验证性的张力}
越开放的任务越可能产生新能力，但越难自动判分；越容易验证的任务越适合 RL，却可能过窄。实用课程应混合强验证任务、弱验证探索任务和人类审阅样本，而不是只选择其中一端。
\end{importantbox}

\subsection{近期产品形态：垂直 Agent 的联邦}

嘉宾判断，近期更现实的形态不是一个无所不能的 Agent，而是多个垂直 Agent 通过 MCP、skills 或服务接口互相调用。代码、数据分析、检索和科研等领域会先形成高可靠单元，再逐步组合为更复杂系统。这种联邦结构也要求明确能力声明、权限和失败传播边界。

\subsection{本章小结}

上午场 Panel 给出一条务实路线：先在 harness 层快速试验，用可验证环境收集 on-policy experience，把稳定模式内化到模型，同时让环境与课程随策略能力增长。任何自进化机制都必须防止自评闭环、保留回滚，并把开放探索与外部验证配对。
